## Детально

### 2.1. Мои билеты — 🟡

**Есть:**
- ✅ Список билетов: `GET /lk/mytickets` → `TicketService.getTickets()`; UI — `profile-tickets.component`
- ✅ Детали билета: `GET /lk/getticketinfo?ticketid=` — маршрут, вокзалы, время, место, платформа, ФИО, документ, стоимость, номер заказа
- ✅ Карточка сворачивается/разворачивается по клику (`toggleDetail`)
- ✅ Скачивание PDF: `GET /main/getticket?ticketid=&uuid=` (генерация через отчёт iDempiere «PDF Ticket» / «PDF Reserve»)
- ✅ Возврат с подтверждением кодом: `GET /lk/startreturn` (расчёт удержания) → код на email (`TicketService`, `randomString(5)`) → `POST /lk/returncode`

- ✅ Скрытие билета без удаления заказа: `POST /lk/delete` → `ticket.setIsAvailable(false)`

**Нет / не соответствует:**
- ❌ **Проверка принадлежности PDF сломана.** `MainResource.getTicket` не требует сессии, условие `if (!uuid.equals(ticket_UU) && !paymentstatus.equals("commited")) → 403` означает: у любого оплаченного заказа PDF отдаётся всякому, кто знает `ticketid`. ТЗ требует проверку по текущему авторизованному пользователю.
- ❌ **Отладочный код в проде:** каждый скачанный билет дублируется письмом на `vladislav@siberium.ru` (`MainResource.java:299`).
- 🟡 Кнопка «Удалить» на десктопной вёрстке закомментирована (`profile-tickets.component.html:32`), работает только в мобильной.
- ❌ Подтверждающего попапа «Вы уверены?» перед удалением нет.
- ❌ Скрытия кнопки «Вернуть билет» для прошедших рейсов на уровне UI нет.

Отсутствует. Проверены все 37 фоновых процессов: `SendTickets` отправляет PDF билета после покупки, `SendEmails` — разовая рассылка «Технические работы завершены». Напоминания за N часов до отправления нет, настройки времени напоминания нет.

### 2.26. Билет «туда-обратно» одной покупкой — ❌

Отсутствует. Модель заказа (`sib_order`) рассчитана на один рейс: одна пара станций (`sib_db_stations_ID_dep`/`_arr`), один `sib_route_ID`, один `sib_db_stations_api_ID`. Переключателя «в одну сторону / туда-обратно» на форме поиска нет. Логики компенсации (отмена первого сегмента при сбое второго) нет.

Это самый тяжёлый пункт: требует надстройки над моделью заказа и согласованного управления двумя бронями в системах разных перевозчиков.

## Технические требования (раздел 3 ТЗ)

### 3.1. Консолидация дублированных модулей — ❌

Дублирование подтверждено и описано в [02-архитектура-backend.md §2.8](02-архитектура-backend.md): модуль `ru.siberium.personalaccount` (19 105 строк) — форк-предок `ru.siberium.donbilet.webservices` из проекта ЖКХ Барнаула, содержит посимвольные копии `AuthenticateProcessor`, `AuthorizationRequestProvider`, `JSONValidatorProvider`, `CorseRestful`, `Search`, `MainResource`, `LKResource`, `ReserveResource`, `OrdersResource`, `TicketResource`.

При консолидации нужно учесть: у `personalaccount` есть собственный живой домен (ЖКХ: лицевые счета, приборы учёта, задолженность), плюс ЖКХ-классы физически лежат и в билетном модуле (`PersonalAccountResource`, `MeteringDevicesResource`, `ValueMeterReadingResource`, `OrdersResource`/Unitailer).

### 3.2. Обратная совместимость API для мобильного приложения — 🟡

API существует (`/DBInterface/services/donbilet/V2`, публично `https://donbilet.ru/WSv2`), мобильный сценарий в нём предусмотрен (`GET /reserve/statusmobile`).

Риск: **контракта нет** — ни OpenAPI, ни WADL, ни DTO. Ответы формируются как `List<Map<String,Object>>` и разбираются клиентом по индексам массива. Зафиксировать совместимость нечем.

Первоочередное действие: снять фактический контракт с прода (записать реальные запросы/ответы мобильного клиента) и покрыть контрактными тестами **до** начала работ, иначе п. 3.2 не проверяем при приёмке.

### 3.3. Отдельная панель администрирования — ❌

Сейчас всё администрирование (новости, FAQ, баннеры, промокоды, справочники, конфигурация) ведётся **через web-интерфейс iDempiere** — это именно «встроенная техническая консоль платформы», которую ТЗ прямо исключает. Отдельного интерфейса для нетехнического персонала нет.

Панель нужна для пунктов 2.3, 2.7, 2.8, 2.12, 2.13, 2.14, 2.15, 2.21, 2.23 — то есть это самостоятельный продукт внутри проекта, а не довесок.

### 3.4. Единообразие доработок формы заказа — ❌

Сейчас сценариев оформления как минимум два, с разной логикой и разными компонентами: покупка (`booking.component`, `/reserve/addpass` → `/reserve/buy`) и бронь (`ticket-reservation.component`, `/reserve/addpassreserve` → `/reserve/reserve`). Купон, например, продублирован в обоих компонентах отдельно.

Требование ТЗ (страховка 2.11, отель 2.22, промокоды 2.23 — единообразно во всех сценариях) означает предварительное выделение общего шага оформления заказа. Это отдельная работа, не учтённая в пунктах раздела 2.

### 3.5. Оформление ЛК по айдентике — ❌

Зависит от п. 2.16 (Брендинг), которого нет.

## Расхождения в архиве, влияющие на оценку

1. **Фронт и бэк не синхронизированы.** Фронтенд вызывает 4 эндпоинта, отсутствующих в backend-коде: `/reserve/doctype`, `/lk/startreturninsurance`, `/lk/returninsurancecode`, `/return-insurance`. Либо бэкенд в архиве старше, либо часть кода вне этих модулей.
2. **11 из 22 Resource-классов не зарегистрированы** в `rest-context.xml` — в том числе `AcceptCodeRestful` (нужен для п. 2.10) и `FileResource`. Возможно, на проде конфигурация другая.
3. **Раздел Авиа отсутствует в репозитории** — по п. 2.20 оценка невозможна без аудита на месте.

**Что проверить на боевом окружении перед фиксацией объёма:**
- фактический `rest-context.xml` (какие ресурсы включены);
- реальные запросы мобильного приложения (для п. 3.2);
- где живёт раздел Авиа (для п. 2.20);
- есть ли на проде реализация страховки (для п. 2.11).
