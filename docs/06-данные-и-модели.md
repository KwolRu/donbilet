# 06. Модель данных

## 6.1. Как устроен слой моделей

Схема данных живёт **внутри словаря iDempiere** (Application Dictionary): таблицы регистрируются в `AD_Table`/`AD_Column`, а Java-классы генерируются кодогенератором ERP. Отдельных SQL-миграций, DDL-скриптов или файлов схемы в репозитории нет — воспроизвести базу можно только из дампа iDempiere.

Для каждой таблицы существует триада в `ru.siberium.models/src/ru/siberium/model/`:

| Префикс | Что это | Пример | Правится ли вручную |
|---|---|---|---|
| `I_*` | Интерфейс: константы `Table_Name`, `COLUMNNAME_*`, геттеры/сеттеры | `I_sib_tickets` | Нет, генерируется |
| `X_*` | Реализация-обёртка над `PO` iDempiere | `X_sib_tickets` | Нет, генерируется |
| `M_*` | Модель с бизнес-логикой поверх `X_*` | `MTickets`, `MOrder` | Да |

Регистрация в рантайме — через SCR-компонент `SiberiumModelFactory` (`OSGI-INF/ModelFactory.xml`, `service.ranking=100`), который подменяет фабрику моделей ERP.

Всего 57 собственных таблиц с префиксом `sib_` / `SIB_C_`, около 207 Java-файлов моделей (69 201 строка — большая часть автогенерирована).

### Заказы и билеты

**`sib_order`** (`MOrder`) — заказ:
`Name` (номер), `Help` (префикс номера для шлюза), `Description` (session_id платёжной сессии), `orderstatus`, `paymentstatus`, `sib_ordertype`, `Price`, `CostAmt`, `EMail`, `Phone`, `T_DateTime`, `DateTo`, `Session_ID`, `idinapi` (номер заказа у перевозчика), ссылки на `sib_route`, `sib_db_stations_ID_dep/arr`, `sib_db_stations_api`, `sib_paymethod`, `sib_frontendapi`, `sib_coupons`, `AD_User`.

**`sib_tickets`** (`MTickets`) — билет на одного пассажира:
ФИО (`sib_firstname`, `sib_secondname`, `sib_lastname`), `Birthday`, `sib_gender`, гражданство (`sib_cztnid`, `sib_ctznname`), документ (`sib_doctype`, `sib_docseries`, `sib_docnum`, `sib_docissueplace`, `DateDoc`), место (`sib_seatnumber`, `sib_placeid`), деньги (`sib_tarif`, `sib_total`, `sib_discount`, `sib_agent`, `sib_agentprincipal`, `sib_agentsubagent`), багаж (`sib_bagcost`, `sib_bagplaces`, `sib_bagticketnumber`), `sib_ticketnum`, `sib_ticketstatus`, `StartTime`, `InsuredAmount`, флаги возврата `sib_returnbtn` / `sib_returnforcedbtn`, `sib_passanger_category`.

Модель разбиения агентского вознаграждения на «принципала» и «субагента» заложена на уровне билета — это основа расчёта возвратов в `DBCommon.getRefundCalc`.

**`sib_payments`** (`MPayments`) — платёжные операции по билету (`getCurrent(ticketId, "income")`), **`sib_paymethod`** (`MPaymethod`) — реестр шлюзов (`payler`, `sber`, `sbernew`, `alfa`; `Value` — код, `Help` — ключ мерчанта).

**Скидки и промо:** `sib_discount` (`MDiscount`), `sib_coupons` (`MCoupons`), `sib_coupon_apply` (`MCouponApply`), `SIB_C_Corp_ConversionPercent`.

**Справочники документов:** `sib_doctypes`, `sib_doctypesinapi`.

## 6.3. Домен «Пользователи и сессии»

| Таблица | Модель | Назначение |
|---|---|---|
| `SIB_C_LKSubscriber` | `MLKSubscriber` | Пользователь ЛК (расширение `AD_User` iDempiere) |
| `SIB_C_LKSubscriberProfile` | `MLKSubscriberProfile` | Профиль |
| `SIB_C_Subscriber` | `MSubscriber` | Подписчики рассылки |
| `sib_sessions` | `MSessionsSib` | Сессии: `SID`, `XCrfsToken`, `TTL`, `Created`, `IsActive`, ссылка на подписчика |
| `SIB_C_AcceptCodeModel` | `MAcceptCodeModel` | Одноразовые коды подтверждения |
| `SIB_C_RecoveryPasswords` | `MRecoveryPasswords` | Токены восстановления пароля |
| `sib_usercode` | `MUserCode` | Пользовательские коды |
| `sib_frontendapi` | `MSIBFrontendAPI` | Клиентские приложения: `apiname` + `apitoken` |

Пароли пользователей хранятся в стандартной таблице `AD_User` iDempiere. Способ хранения зависит от системного параметра `USER_PASSWORD_HASH`: при выключенном — открытым текстом (`user.getPassword().equals(password)` в `LoginService`). Собственное поле `ProtectedPassword` (`MUserSib`) заполняется **MD5 без соли** через `PasswordProcessor.generateHash`. Коды подтверждения генерируются `java.util.Random`, а не `SecureRandom`.

## 6.4. Домен «Контент и обращения»

`sib_news` (`MNews`), `sib_banners` (`MBanners`), `sib_webabout` (`MWebAbout`), `sib_webfaq` (`MWebFaq`), `sib_messages` (`MMessages`), `sib_feedback` (`MFeedback`), `sib_requests` (`MSIBRequests`), `sib_lkrequests`, `sib_lkfiles`, `sib_lkconsulatationQuestion`, `sib_lkreceptionQuestion` (последние четыре — ЖКХ-наследие).

Изображения хранятся в ERP и отдаются методом `/main/getimage?imageid=`.

## 6.5. Домен «ЖКХ» (наследие, живёт в той же схеме)

`SIB_C_PersonalAccount` (лицевые счета), `SIB_C_MeteringDevices` (приборы учёта), `SIB_C_MeterReading` / `SIB_C_ValueMeterReading` (показания), `SIB_C_Debts` (задолженность), `SIB_C_VidUslug` (виды услуг), `SIB_C_Orders` / `SIB_C_OrdersDetail` (заказы оплаты ЖКХ), `sib_c_scales`, `sib_c_points`, `sib_c_district`, `sib_c_street`.

Эти таблицы обслуживают модуль `ru.siberium.personalaccount`, но их модели лежат в общем бандле `ru.siberium.models` и подмешаны в тот же словарь iDempiere, что и билеты.

## 6.6. Конфигурация

`sib_c_barnaul_config` (`MBarnaulConfig`) — таблица «ключ-значение» для всех настроек приложения: `API_URL`, `RESERVE_RESULT`, `PAYLER_KEY`, `PAYLER_PASS`, `PAYLER_URL`, `EMAIL_*`, `UNIT_SHOP_ID`, `UNIT_PASSWORD`, `UNIT_TTL`. Загружается в память один раз при старте (`MainConfig`). Секреты не шифруются.

## 6.7. Вспомогательные типы

Не-ORM классы в том же пакете: `Document`, `Seat`, `Ticket` (легковесные DTO для обмена с API перевозчиков), `TrxUtil` (генерация имён транзакций), `IChainModel` / `ChainModelProcessor` (цепочка обработчиков моделей), `MConversionRateSib` / `MConversionTypeSib` (курсы валют), `MCitySib` / `MCountrySib` / `MRegionSib` / `MLocationSib` / `MStreet` / `MDistrict` / `MPoints` (география, дублирует стандартные `C_City`/`C_Country` iDempiere).

## 6.8. Замечания по модели

1. **Нет версии схемы и миграций.** Развернуть окружение с нуля по репозиторию невозможно — нужен дамп iDempiere со словарём.
2. **Смешение двух доменов** (билеты и ЖКХ) в одной схеме и одном бандле моделей.
3. **Перегрузка стандартных полей**: `Description` заказа хранит `session_id` платёжной сессии, `Help` — префикс номера, `Name` — номер заказа. Смысловая нагрузка на служебные поля iDempiere не документирована нигде, кроме кода.
4. **Дублирование географии**: собственные `MCitySib`, `MCountrySib`, `MRegionSib` сосуществуют со стандартными `MCity`, `MCountry` iDempiere, и обе иерархии используются в одном и том же коде (`SearchService` импортирует `org.compiere.model.MCity` и `ru.siberium.model.MCitySib`).
5. **Регистр имён таблиц непоследователен**: `sib_tickets` и `SIB_C_Debts` — в одной схеме. На PostgreSQL это работает за счёт приведения к нижнему регистру, но усложняет поиск по коду.
