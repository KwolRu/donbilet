# 05. Внешние интеграции: перевозчики, платежи, уведомления

## 5.1. Общая картина

DonBilet — агрегатор. Собственного «инвентаря» мест у него нет: расписание, схема салона, бронирование и выкуп делаются в системах перевозчиков. Backend выступает оркестратором:

```
Клиент → REST API DonBilet → TotalAPI (диспетчер) → адаптер конкретного перевозчика
                           → Payment (диспетчер) → платёжный шлюз
                           → EmailSender / SMSSender
```

## 5.2. Интеграции с перевозчиками

### Структура

Два уровня:

| Уровень | Пакет | Роль |
|---|---|---|
| Транспортный SDK | `ru.siberium.dbapi.<провайдер>` | HTTP/SOAP-клиент к API: `*Main`, `*Order`, `*Return`, `*Trip`, `Seats`, собственный `Logger` в каждом пакете |
| Фасад | `ru.siberium.apis.*` | Приведение к внутренней модели iDempiere: `updateRace`, `parseSeats`, `parseDoctypes`, оформление и возврат |

Диспетчеризация — класс `ru.siberium.apis.TotalAPI`: большой `switch` по `sib_db_stations_api_ID` рейса. Один и тот же `switch` продублирован в каждом методе (`updateRaceByAPI`, получение мест, типов документов, оформление, возврат) — около десятка копий.

### Справочники соответствий

Так как у каждого перевозчика собственные идентификаторы, в БД ведутся таблицы-мостики: `sib_db_stations_api` (реестр API), `sib_db_stationinapi` (станция ↔ ID у перевозчика), `sib_cityinapi`, `sib_route_stops_inapi`, `sib_doctypesinapi`. Их наполняют процессы `*dir_binder` («связыватель направлений») из `ru.siberium.processes`.

### Синхронизация расписаний

Процессы `*loader` (`DBloader`, `BFloader`, `RBloader`, `ABloader`, `ABALoader`, `ABNLoader`, `ABProloader`, `Krasloader`, `YHLoader`) запускаются планировщиком iDempiere и наполняют `sib_schedule`, `sib_route`, `sib_routecosts`, `sib_routestops`. `PingAPI` проверяет доступность провайдеров, `UpdateDepartures`/`UpdateArrivals`/`UpdateDirection` обновляют справочники пунктов.

### Собственная касса (провайдер 1000000)

Класс `DBservices` общается с внутренним API по адресу из конфигурации `API_URL` протоколом собственного формата — JSON с полями `version`, `keyword`, `container`, `parameters`, `signature`, `recipient`:

```json
{"version":"5.2","keyword":"RSRV ","container":[{"place":"12"}],
 "parameters":{"session":"<sid>","places":"1"},"signature":[839,2931,0],"recipient":["<depid>","0"]}
```

Известные команды: `RSRV` (занять место), `EXCL` (освободить место), запрос причин возврата, статус заказа. Запросы формируются **конкатенацией строк** — без экранирования значений. Отправляются через нестандартный `MyHttpGetWithEntity` (GET с телом), используется `DefaultHttpClient` (deprecated с HttpClient 4.3), соединение закрывается вручную, пул не переиспользуется.

## 5.3. Платежи

### Диспетчер

Класс `ru.siberium.donbilet.common.Payment` (849 строк). Выбор шлюза:

```java
private static int CheckMethod() {
    int[] pmethods = MPaymethod.getAllIDs("sib_paymethod", "isactive='Y'", null);
    return pmethods[pmethods.length - 1];   // берётся ПОСЛЕДНИЙ активный метод
}
```

То есть активный шлюз определяется тем, какая запись в `sib_paymethod` имеет наибольший ID среди активных. Ни выбора пользователем, ни правил маршрутизации, ни фолбэка нет. Далее `switch (pm.getValue())`:

| Значение | Шлюз | Класс-клиент |
|---|---|---|
| `payler` | Payler | `Payler` (`PAYLER_KEY`, `PAYLER_PASS`, `PAYLER_URL`) |
| `sber` | Сбербанк, старый REST | `Sber` |
| `sbernew` | Сбербанк, новый REST с корзиной/чеком | `SberNew` |
| `alfa` | Альфа-Банк | `Alfa` |

Каждый шлюз реализует один набор операций: `registerDo` (регистрация платежа), `getOrderStatusExtendedDo` (статус), `getRefundDo` (возврат). Общего интерфейса `PaymentGateway` нет — `switch` по строке продублирован в `StartSession`, `Refund`, `Status`, `getRefundReceipt`, `getPayReceipt` (5 раз).

### Сценарий оплаты

```
1. Клиент: GET /start/ticket           → сессия у перевозчика, схема мест
2. Клиент: POST /reserve/addpass       → пассажиры, создание заказа (sib_order)
3. Клиент: GET /reserve/buy            → Payment.StartSession(orderID, amount)
                                          → регистрация в шлюзе, сохранение session_id в order.Description
                                          → возврат ссылки на платёжную форму
4. Пользователь платит на стороне шлюза
5. Шлюз → GET/POST /reserve/merchantcallback  (dynamicCallbackUrl)
6. Клиент: GET /reserve/result?orderid=  → поллинг до 40 с, затем выкуп билета у перевозчика
7. Билет: GET /main/getticket?ticketid=&uuid=  → PDF (iText)
```

Возвратный URL и callback берутся из ключа `RESERVE_RESULT`, но частично захардкожены в `Payment.java`: `https://www.donbilet.ru/WSv2/reserve/merchantcallback`, `https://donbilet.ru/callback`, `paymentAddress: https://donbilet.ru`.

### Проблемные места платёжного контура

- **`/reserve/result` держит поток до 40 секунд** (`while (i < 10) { … TimeUnit.SECONDS.sleep(4); }`). При всплеске трафика это исчерпание пула потоков CXF.
- **Идемпотентность callback не обеспечена**: обработчик `merchantcallback` не проверяет, был ли заказ уже обработан; повторный вызов шлюза приведёт к повторному выполнению логики.
- **Подпись callback не проверяется** в билетном сценарии (в ЖКХ-сценарии `/orders/accept/` подпись есть — `OrdersService.accept(orderId, signature, …)`).
- Нет распределённой транзакции между «деньги списаны» и «билет выкуплен у перевозчика». Компенсация вынесена в ручные процессы `ManualReturn`, `ManualReturnForced`, `ReturnAll`.
- Ключи шлюзов лежат в таблице `SIB_C_Barnaul_Config` открытым текстом. В `OrdersResource` пароль агрегатора Unitailer оставлен в комментарии прямо в исходнике.

### Фискализация

Методы `Payment.getPayReceipt()` и `Payment.getRefundReceipt()` формируют чек по 54-ФЗ и отправляют его через API шлюза (`Payler.getReceipt` / `checkReceipt`, корзина `cartItems` в `SberNew`/`Alfa`). Данные компании (`paymentAddress`) захардкожены.

### Возвраты

`DBCommon.getRefundCalc(subscriberId, ticketId)` считает удержание по шкале (см. [03-api-справочник.md §/lk](03-api-справочник.md)), затем `Payment.Refund(...)` вызывает возврат в шлюзе и `TotalAPI` — возврат у перевозчика. Расчёт использует `SimpleDateFormat("yyyy-MM-dd hh:mm:ss.SS")` — строчная `hh` означает 12-часовой формат, что для времени отправления после полудня даёт неверный разбор. Класс не потокобезопасен и используется как локальная переменная — здесь без гонки, но паттерн повторяется по всему проекту.

## 5.4. Уведомления

| Канал | Класс | Реализация |
|---|---|---|
| Email | `EmailSender implements ISender` | JavaMail (`mail-1.4.7.jar`), параметры из конфигурации: `EMAIL_FROM`, `EMAIL_USER`, `EMAIL_PASS`, `EMAIL_HOST`, `EMAIL_PORT`. Поддерживает вложения (`File attach`) — так уходит PDF-билет |
| SMS | `SMSSender implements ISender` | **Заглушка**: класс из 14 строк, метод `send` не реализует отправку |

Общий интерфейс — `ru.siberium.donbilet.common.interfaces.ISender`. Массовые рассылки — процессы `SendEmails` и `SendTickets`. Очередей, ретраев и учёта доставки нет; ActiveMQ и amqp-client присутствуют в classpath, но в коде не используются.

Коды подтверждения (регистрация, удаление аккаунта, возврат) — `AcceptCodeProcessor` + таблица `SIB_C_AcceptCodeModel`, доставка через email.
