# ADR-0003. Prisma: сборка схемы из частей и стратегия миграций

**Статус:** принято
**Контекст:** базовое решение шаблона. Меняется только новым ADR.

## Контекст

Prisma требует одну `schema.prisma`. На реальном проекте это быстро становится
файлом на 2000+ строк, который правят все и в котором постоянно конфликты при
merge. При этом Prisma Client и миграции — общие на все сервисы (ADR-0001 §3).

## Решение

### 1. Каноническая схема генерируется, а не пишется

`prisma/schema.prisma` — **артефакт сборки**. Редактировать его руками нельзя:
изменения затрутся при следующем `db:schema:build`.

Источник правды — `prisma/schema-parts/*.prisma`, склеиваются по алфавиту
скриптом `scripts/build-prisma-schema.mjs`:

```txt
00-base.prisma       generator + datasource
05-platform.prisma   Workspace, User, Session, SystemEvent
10-example.prisma    доменный пример (Project, Task)
20-*.prisma          ваши домены
```

Нумерация с шагом 10 оставляет место для вставки между частями без переименований.

Любой скрипт `db:*` вызывает сборку первым шагом, поэтому забыть пересобрать
схему нельзя.

### 2. Один part-файл = один домен

Правило нарезки: часть соответствует владельцу моделей из
`prisma/ownership/model-ownership.yml`. Тогда PR, добавляющий фичу, трогает один
part-файл, и конфликты в git становятся редкостью.

### 3. Миграции применяются к прод-БД только через `migrate deploy`

| Команда | Где |
|---|---|
| `npm run db:migrate` | локально, создаёт миграцию |
| `npm run db:push` | локально, черновые итерации без миграции |
| `npm run db:migrate:deploy` | **единственная** команда для стейджа/прода |

`db push` в проде молча приводит схему к текущему виду без записи в историю —
после этого история миграций и реальная БД расходятся навсегда.

### 4. Baseline вместо накопленной истории

Шаблон отдаётся с тремя миграциями:

```txt
00000000000000_init_extensions        pg_trgm, btree_gist
00000000000001_init                   таблицы из schema-parts
00000000000002_rls_and_search_indexes RLS-политики + GIN-индексы
```

Когда история миграций проекта становится длинной и все окружения на последней
версии — её схлопывают в новый baseline, а старые файлы архивируют. Это
нормальная операция, а не потеря истории: история изменений схемы живёт в git.

### 5. SQL, которого нет в Prisma-схеме, пишется руками

RLS-политики, GIN/GiST-индексы, триггеры, расширения — Prisma их не генерирует.
Они живут в SQL-миграциях и не должны пропасть при следующем `migrate dev`:
Prisma сравнивает схему с БД и попытается «починить» расхождение.

Практика: такой SQL добавляется отдельной миграцией и повторяется для каждой
новой tenant-таблицы (шаблон блока — в `00000000000002_rls_and_search_indexes`).

### 6. Сид разделён на base и dev

- `db:seed:base` — минимум для работы окружения (workspace + владелец).
  Безопасен для прода.
- `db:seed:dev` — base плюс демо-данные. В прод не попадает.

Учётные данные владельца берутся из env (`SEED_OWNER_EMAIL` / `SEED_OWNER_PASSWORD`),
а не хардкодятся.

## Последствия

- `prisma/schema.prisma` можно коммитить (удобно для code review), но правки в
  нём всегда теряются — это ожидаемо.
- Новая модель требует правок в трёх местах: part-файл, `model-ownership.yml`,
  RLS-блок в миграции.
- Prisma Client общий, поэтому любой сервис технически видит все модели.
  Ограничение — организационное (реестр владения), а не техническое.
