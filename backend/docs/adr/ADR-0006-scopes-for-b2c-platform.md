# ADR-0006. Скоупы данных для B2C-платформы: global, workspace, customer

**Статус:** предложено — требует утверждения владельца (вопрос Q6 в `audit/ROADMAP.md`)
**Дата:** 2026-09-07
**Решение нужно до:** Ф5 (customer-service) — первого доменного сервиса с бизнес-данными
**Контекст фазы:** Ф0, долг D2

## Контекст

Шаблон `arch-saas` спроектирован под **многотенантный SaaS**: `Workspace` — организация-
тенант, каждая бизнес-таблица несёт `workspace_id`, RLS не даёт данным одного тенанта
утечь другому (ADR-0002).

DonBilet — **B2C-платформа с одним владельцем**:

| Кто | Сколько | Природа |
|---|---|---|
| Анонимные посетители | основная доля трафика | Ищут рейсы, читают контент. Ни сессии, ни JWT, ни тенанта |
| Покупатели (customers) | много | Клиенты одной компании, **не тенанты** |
| Сотрудники DonBilet | десятки | Работают в CRM. Одна организация |

Если применить шаблон буквально, `workspace_id` во всех таблицах будет иметь одно и то
же значение. RLS в этом виде не изолирует ничего, но каждый tenant-запрос всё равно
открывает транзакцию с `SET app.current_workspace_id` — включая публичный поиск,
который вообще не имеет пользователя.

При этом отказаться от изоляции нельзя: **основной класс дефектов этого домена — утечка
данных между покупателями**. В legacy это подтверждено фактом: `/main/getticket` отдаёт
PDF билета любому, кто знает `ticketid`, если заказ оплачен (`docs/07`, H7/S-раздел).
Именно от таких ошибок и защищает третий рубеж.

## Решение

**Три скоупа данных вместо двух. Механика шаблона сохраняется, но ключ изоляции для
клиентских данных — `customer_id`, а не `workspace_id`.**

### Скоуп `global` — публичные справочники

Без `workspace_id`, без RLS. Читаются анонимно, пишутся только фоновыми синхронизациями
и CRM.

```
transport:  City, Station, Route, RouteStop, Trip, Fare, Seat, SeatMap, Carrier
provider:   Provider, ProviderMapping
content:    Page, News, FaqCategory, Faq, Banner, SeoPage, Redirect, LegalDocument, AirDirection
```

Обоснование: это каталог и контент витрины. У них нет владельца-тенанта и нет
приватности. Публичный поиск — самый нагруженный маршрут проекта, и заворачивать его в
workspace-транзакцию значит платить за изоляцию, которой там нет.

ADR-0002 §2 такое исключение прямо допускает: «Модель без `workspace_id` — осознанное
исключение (глобальные справочники), требует записи в `model-ownership.yml` в скоуп
`global`». Этот ADR и есть та самая запись.

### Скоуп `workspace` — данные оператора

Механика шаблона без изменений: `workspace_id`, RLS, `WorkspaceContextMiddleware`,
`WorkspaceTransactionInterceptor`.

```
platform:   Workspace, User (сотрудник), Session, SystemEvent, AuditLog
operator:   Role, Permission, PromoCode, RefundRule, Setting, NotificationTemplate
```

Сейчас workspace ровно один — DonBilet. Тенантность здесь не выключается сознательно:
у бизнеса уже есть история мультиарендности (в legacy на одном iDempiere жили и
donbilet, и ЖКХ Барнаула; таблица `sib_frontendapi` — реестр клиентских приложений).
Если появится white-label для агентства или перевозчика, структура это выдержит без
переезда. Цена сохранения — один столбец в десятке низконагруженных таблиц.

### Скоуп `customer` — данные покупателей

Новый скоуп. Повторяет три рубежа из ADR-0002 §3, но ключ — `customer_id`.

```
customer:   Customer, Passenger, FavoriteDirection, FavoriteTrip, Message, CarrierRating
booking:    Booking, Order, OrderItem, Reservation, BookingPassenger
ticketing:  Ticket, TicketPassenger, TicketDocument, TicketRefund, TicketFile
support:    Conversation, ConversationMessage, Attachment
payment:    Payment, Refund, FiscalReceipt
```

| Рубеж | Где | Что ловит |
|---|---|---|
| 1. Фильтр в коде | `where: { customerId }` в каждом запросе | Типовые ошибки |
| 2. Проверка владения | `assertBelongsToCustomer(...)` для id из тела запроса | Подстановку чужого id |
| 3. RLS | Политика по `app.current_customer_id` | Всё, что пропустили первые два |

Механика третьего рубежа — зеркало существующей: `CustomerContextMiddleware` ставит
контекст из claim `customer_id` проверенного JWT, `CustomerTransactionInterceptor`
открывает транзакцию с `SET app.current_customer_id`, RLS-политики fail-closed при
пустом контексте.

**Именно это закрывает дефект H7 архитектурно:** запрос PDF чужого билета не вернёт
строку даже при ошибке в коде контроллера.

### Пересечения скоупов

Заказ принадлежит покупателю, но виден оператору в CRM. Решение: таблицы скоупа
`customer` несут **и** `customer_id`, **и** `workspace_id` оператора. Активна одна
политика в зависимости от контекста запроса:

- публичный/клиентский запрос → установлен `app.current_customer_id`, видны свои строки;
- запрос из CRM → установлен `app.current_workspace_id`, видны все строки workspace.

Оба контекста одновременно не устанавливаются. Отсутствие обоих — ноль строк.

## Отвергнутые альтернативы

**(а) Один служебный workspace на всё.** Проще всего в реализации, но `workspace_id`
становится константой: RLS не изолирует ничего, а публичный поиск платит за
workspace-транзакцию. Главное — не закрывается основной класс дефектов домена
(утечка между покупателями), ради которого изоляция и нужна.

**(б) Убрать тенантность из шаблона полностью.** Ломает `auth-service`, построенный
вокруг Workspace, ломает `test:rls`, и отнимает возможность white-label. Экономия —
один столбец в низконагруженных таблицах.

**(в) Клиентские данные без RLS, только фильтр в коде.** Ровно та модель, при которой
в legacy возник H7. Отвергается по факту наличия воспроизведённого дефекта.

## Следствия

1. **`model-ownership.yml` расширяется четвёртым скоупом `customer`.** Комментарий-
   инвариант «любая новая бизнес-модель попадает в `tenant`» переписывается под три
   скоупа с правилом выбора.

2. **Требуется реализовать `CustomerContextMiddleware` и `CustomerTransactionInterceptor`**
   в `microservices/shared` — по образцу существующих workspace-аналогов. Работа фазы Ф5.

3. **Требуется негативный тест `test:rls:customer`** по образцу существующего
   `test/rls-isolation.test.mjs`: чужой билет не читается, не обновляется, не удаляется;
   без контекста — ноль строк. Без этого теста скоуп считается нереализованным.

4. **Публичные маршруты не подключаются ни к одному middleware контекста.** Поиск,
   расписания, контент идут напрямую через `prisma` — не `prisma.db`.

5. **JWT покупателя несёт claim `customer_id`, JWT сотрудника — `workspace_id`.**
   Это два разных типа субъекта; `auth-service` должен различать их явно, а gateway —
   проставлять соответствующий заголовок.

6. **ADR-0002 не отменяется.** Он продолжает описывать workspace-скоуп. Этот ADR
   добавляет два других и правило выбора между ними.

## Правило выбора скоупа для новой модели

```
Данные читаются анонимно и одинаковы для всех?      → global
Данные принадлежат покупателю?                       → customer
Данные принадлежат оператору (сотрудники, настройки)?→ workspace
```

Модель, не подходящая ни под одно правило, не заводится до записи в ADR.

## Что требуется от владельца

Утвердить или отклонить до начала Ф5. При отклонении назвать альтернативу из
отвергнутых — от этого зависит структура `customer-service` и всех последующих
доменных сервисов.
