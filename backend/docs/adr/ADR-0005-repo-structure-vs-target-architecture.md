# ADR-0005. Структура репозитория DonBilet и её расхождение с целевой архитектурой

**Статус:** принято
**Дата:** 2026-09-07
**Контекст фазы:** Ф0, долг D1

## Контекст

Целевая архитектура DonBilet (`docs/plan-tz/DonBilet — технологический стек и целевая
архитектура.md`, §44) фиксирует структуру монорепо:

```
donbilet/
├── apps/{web,crm}
├── backend/{gateway,auth-service,customer-service,...}   # каталог на сервис
├── workers/{booking-worker,refund-worker,...}
├── integrations/{max,1c}
├── packages/{contracts,validators,ui,observability,shared}
└── deploy/
```

Фактическая реализация ведётся на шаблоне `arch-saas`, структура которого другая:

```
don-bilet/
├── frontend/                         # одно Next.js-приложение
├── backend/
│   ├── microservices/{gateway,auth-service,example-service,...,shared}
│   ├── prisma/{schema-parts,ownership,migrations}
│   └── scripts/
└── deploy/traefik/
```

Расхождения по существу три:

1. Один каталог `backend/` с общими `node_modules`, `tsconfig.json`, `package.json`
   и единой Prisma-схемой вместо каталога-пакета на сервис.
2. Одно frontend-приложение вместо `apps/web` + `apps/crm`.
3. `packages/*` отсутствуют: их роль выполняет `backend/microservices/shared`
   и `frontend/components/{ui,common}`.

## Решение

**Сохраняем структуру шаблона. §44 целевой архитектуры считается описанием
логических границ, а не физической раскладки каталогов.**

### Обоснование

Что §44 действительно требует и что шаблон обеспечивает:

| Требование §44 | Как выполняется в шаблоне |
|---|---|
| Сервис владеет своим доменом (§2.3) | Каждый сервис — отдельное NestJS-приложение со своим `main.ts` и `app.module.ts` |
| Сервис не читает чужие таблицы напрямую (§26) | Обеспечивается `model-ownership.yml` и код-ревью, а не физическим разделением каталогов |
| Логическое разделение данных в одном PostgreSQL (§25) | Шаблон использует одну БД и одну схему — соответствует §25 |
| Общий код только технические примитивы (§45) | `microservices/shared` содержит auth, prisma, s3, crypto, proto, фильтры — технические примитивы |
| Gateway — единственная публичная точка входа (§6) | `microservices/gateway`, проксирование через `proxy.routes.ts` |

Чего физическое разделение на пакеты дало бы дополнительно: независимую версионность
и независимый деплой сервисов. Для соло-исполнения (решение R6) и деплоя одним
Docker-образом с выбором процесса по `SERVICE_NAME` это накладные расходы без выгоды.

### Отвергнутая альтернатива

**Перестроить репозиторий под §44.** Отвергнуто: две-три недели работы на переезд
и перенастройку сборки, ноль функциональной пользы, и всё это до того, как написана
первая строка доменного кода. Ф11–Ф14 (перенос перевозчиков, booking, ticketing,
payment) от раскладки каталогов не зависят.

## Следствия

1. **Соответствие §44 читается по логическим границам.** Новый доменный сервис —
   это каталог в `backend/microservices/`, запись в `proxy.routes.ts`, part-файл в
   `prisma/schema-parts/` и запись в `model-ownership.yml`. Не отдельный npm-пакет.

2. **CRM живёт в том же Next.js-приложении**, в отдельной route-группе `(crm)`
   с собственным layout и RBAC-гейтом в `proxy.ts`. Отдельное приложение `apps/crm`
   заводится только если появится причина деплоить его независимо.

3. **`packages/contracts` из §44 отображается на два места:** серверные DTO — в
   `backend/microservices/shared`, клиентские zod-схемы — в
   `frontend/app/core/validators`. Дублирование схем между ними допускается;
   единый источник вводится, только если рассинхронизация станет реальной проблемой.

4. **Целевая архитектура остаётся источником истины по составу сервисов.** Список
   из §2.2 (auth, customer, transport, booking, ticketing, payment, provider,
   content, support, notification, analytics) не меняется — меняется только то,
   где физически лежат их каталоги.

5. **`example-service` подлежит удалению** в Ф5, когда появится первый доменный
   сервис DonBilet. До этого служит рабочим эталоном для `/feature-pattern`.

## Пересмотр

Этот ADR пересматривается, если:

- потребуется независимый деплой или версионность отдельных сервисов;
- CRM потребуется деплоить отдельно от публичного сайта;
- в проект придёт второй разработчик и общие `node_modules` начнут мешать.
