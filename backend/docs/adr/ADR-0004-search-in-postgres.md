# ADR-0004. Поиск на PostgreSQL вместо отдельного движка

**Статус:** принято
**Контекст:** базовое решение шаблона. Пересматривается при росте объёмов.

## Контекст

Почти в каждом проекте появляется поиск: по названию, по имени клиента, по
описанию. Рефлекс — поднять Elasticsearch/OpenSearch. Это добавляет к стеку
JVM-сервис, синхронизацию индексов, отдельный контур бэкапов и новый класс
багов «в БД есть, в индексе нет».

## Решение

**Поиск делается средствами PostgreSQL, пока объёмы это позволяют.**

### Что используется

| Задача | Инструмент | Индекс |
|---|---|---|
| Подстрока, опечатки, «похоже на» | `pg_trgm` | `GIN (col gin_trgm_ops)` |
| Полнотекстовый поиск по документу | `tsvector` + `to_tsquery` | `GIN (tsvector)` |
| Пересечение диапазонов, расписания | `btree_gist` | `GiST (workspace_id, range)` |

Оба расширения (`pg_trgm`, `btree_gist`) входят в стандартный contrib — образ
`postgres:*` подходит как есть, кастомная сборка не нужна.

### Почему индекс обязателен

Prisma-запрос вида

```ts
where: { name: { contains: query, mode: "insensitive" } }
```

компилируется в `ILIKE '%query%'`. Без GIN-индекса это seq scan, который
деградирует уже на десятках тысяч строк на тенанта — то есть не на нагрузочном
тесте, а на втором году эксплуатации.

Эталон — `projects_name_trgm_idx` и `tasks_title_trgm_idx` в миграции
`00000000000002_rls_and_search_indexes`. Добавили поле, по которому ищут, —
добавьте индекс той же миграцией.

### Когда этого перестаёт хватать

Признаки, что пора выносить поиск в отдельный движок:

- миллионы документов на тенанта;
- нужны релевантность с настраиваемым скорингом, фасеты, агрегации по тексту;
- запросы по нескольким сущностям в одном ранжированном списке;
- p95 поиска перестаёт укладываться в бюджет даже с индексами.

До этого момента внешний движок — чистый оверхед.

### Векторный поиск и гео

`pgvector` (эмбеддинги, RAG) и `PostGIS` (гео) в стандартный образ не входят.
Если проект их требует: соберите свой образ Postgres, укажите его в
compose-файлах и добавьте `CREATE EXTENSION` отдельной миграцией — по тем же
правилам, что и остальной ручной SQL (ADR-0003 §5).

## Последствия

- Один компонент в стеке вместо двух; бэкап БД = бэкап поиска.
- Нет рассинхрона между источником и индексом.
- Возможности ранжирования ограничены тем, что даёт Postgres.
- Индексы поиска нужно заводить осознанно: их отсутствие проявится не сразу.
