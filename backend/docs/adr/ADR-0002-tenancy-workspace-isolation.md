# ADR-0002. Мультитенантность: workspace, изоляция и RLS

**Статус:** принято
**Контекст:** базовое решение шаблона. Меняется только новым ADR.

## Контекст

Приложения на этой архитектуре — многотенантные: один стек обслуживает много
организаций. Нужно зафиксировать, как определяется тенант и что мешает данным
одного тенанта утечь другому.

## Решение

### 1. Тенант — `Workspace`, идентификатор в JWT

Тенант резолвится из claim `workspace_id` проверенного access-токена.

Отвергнутые альтернативы:

- **Поддомен на тенанта** (`acme.app.ru`) — требует wildcard-DNS и wildcard-TLS,
  ломает cookie между apex и поддоменом, усложняет локальную разработку (правка
  `hosts` под каждого тенанта). Выгода — только «красивый URL».
- **Тенант в теле/параметре запроса** — управляется клиентом, а значит
  подделывается. Использовать нельзя.

Следствие: заголовки вида `x-tenant-slug` не нужны. Фронт не знает и не должен
знать про тенанта на транспортном уровне.

### 2. Одна БД, одна схема, `workspace_id` в каждой бизнес-таблице

Отдельная БД или PG-схема на тенанта отвергнуты: миграции пришлось бы
прогонять N раз, а пул соединений — делить на N.

**Каждая бизнес-таблица несёт `workspace_id`** плюс составной индекс
`(workspace_id, status)` / `(workspace_id, created_at)` — под типовые выборки
«список сущностей тенанта».

Модель без `workspace_id` — осознанное исключение (глобальные справочники),
требует записи в `prisma/ownership/model-ownership.yml` в скоуп `global`.

### 3. Три рубежа изоляции

| Рубеж | Где | Что ловит |
|---|---|---|
| 1. Фильтр в коде | `where: { workspaceId }` в каждом запросе | 99% случаев |
| 2. Middleware + интерцептор | `WorkspaceContextMiddleware`, `WorkspaceTransactionInterceptor` | Отсутствие контекста вообще |
| 3. RLS | Политики в БД | Забытый фильтр, ручной SQL, доступ через psql |

**Первый рубеж — основной по частоте, третий — последний по надёжности.**

Механика третьего рубежа:

1. **Две роли БД.** `DATABASE_URL` — владелец таблиц: миграции, сид, служебные
   скрипты; политики к нему не применяются (RLS включён без `FORCE`), иначе
   миграции не смогли бы работать без workspace-контекста.
   `DATABASE_RUNTIME_URL` — роль приложения **без `BYPASSRLS`** и без владения
   таблицами; создаётся `npm run db:runtime-role` и входит в групповую роль
   `app_runtime`, которой миграция выдаёт права (включая DEFAULT PRIVILEGES на
   будущие таблицы).

2. **Контекст на транзакцию.** `WorkspaceTransactionInterceptor` оборачивает
   каждый tenant-запрос в транзакцию и выставляет в ней:

   ```sql
   SELECT set_config('app.current_workspace_id', '<uuid>', true);
   ```

   Третий аргумент `is_local = true` обязателен: без него значение переживёт
   запрос и утечёт в следующий через пул соединений — то есть один тенант увидит
   данные другого. Доменные сервисы ходят через `prisma.db`, который внутри
   контекста возвращает эту транзакцию, а вне его — обычный клиент.

3. **Политики fail-closed:**

   ```sql
   USING      (workspace_id = current_setting('app.current_workspace_id', true))
   WITH CHECK (workspace_id = current_setting('app.current_workspace_id', true))
   ```

   Контекста нет → `current_setting` вернёт NULL → сравнение даст NULL → ноль
   строк. `WITH CHECK` дополнительно запрещает записать строку в чужой workspace.

Если `DATABASE_RUNTIME_URL` не задан, приложение подключится владельцем, и
`PrismaService` при старте напишет предупреждение в лог: в этом режиме RLS не
защищает.

Проверяется тестом `npm run test:rls`: он ходит в БД напрямую, мимо Prisma и
приложения, и убеждается, что чужие строки недоступны на чтение, изменение,
удаление и вставку, а запрос без контекста не видит ничего.

### 3.1. Платформенные таблицы вне RLS

`workspaces`, `users`, `sessions` политикой по `workspace_id` не покрыты:
auth-service обязан читать их **до** того, как тенант определён — это и есть
процесс логина. Их изоляция обеспечивается кодом auth-service.

### 4. Проверка владения связями

Фильтр по `workspace_id` защищает от чтения чужого, но не от **привязки** к
чужому. Любой идентификатор, пришедший в теле запроса (`projectId`, `ownerId`,
`parentId`), проверяется на принадлежность тому же workspace до записи.

Эталон — `TasksService.assertProjectBelongsToWorkspace` в `example-service`.

### 5. Обновление и удаление — через `updateMany` / `deleteMany`

`prisma.update({ where: { id } })` не умеет фильтровать по `workspaceId`:
уникальный ключ обязателен. Пара «`findUnique` + проверка + `update`» — это гонка
и лишний запрос. Поэтому:

```ts
const { count } = await prisma.project.updateMany({
  where: { id, workspaceId },
  data,
});
if (count === 0) throw new NotFoundException();
```

Проверка владения становится частью самого запроса.

### 6. Префиксы во внешнем состоянии

ORM и RLS не покрывают Redis, очереди и поисковые индексы. Там изоляция —
префиксом ключа (см. ADR-0001 §8). Ключ без префикса тенанта — баг.

## Последствия

- Смена тенанта пользователем = новый токен, а не новый URL.
- Каждый новый доменный модуль обязан попасть в
  `WorkspaceContextMiddleware.forRoutes(...)`, а его контроллер — получить
  `@UseInterceptors(WorkspaceTransactionInterceptor)`. Без первого пуст
  `req.workspace`, без второго запросы уйдут вне транзакции и RLS вернёт ноль строк.
- Доменные запросы идут через `prisma.db`, а не `prisma` напрямую.
- Каждая новая tenant-таблица требует блока RLS в миграции — копируется из
  `00000000000002_rls_and_search_indexes`.
- Развёртывание требует двух шагов вместо одного: `db:migrate:deploy`, затем
  `db:runtime-role`, и `DATABASE_RUNTIME_URL` в окружении сервисов.
- Цена: одна транзакция на каждый tenant-запрос, включая GET. Транзакция на
  чтение дешёвая; альтернатива (`SET` без `LOCAL`) протекает через пул соединений.
