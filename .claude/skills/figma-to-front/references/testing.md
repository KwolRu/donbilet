# Тесты фронта

Два инструмента, разные задачи. Оба нужны.

| Инструмент | Что проверяет | Команда |
|---|---|---|
| `node --test` | чистая логика: сторы, утилиты, правила, парсинг | `npm test` |
| Playwright | путь пользователя целиком через реальный стек | `bun run e2e` |

## `node --test`

Файлы: `test/*.test.mjs` (+ точечные наборы: `test:filters`, `test:realtime`,
`test:table-settings`, `test:lead-communications`).

```bash
bun run test                    # = node --experimental-strip-types --test test/*.test.mjs
bun run test:legacy         # старый набор
```

Флаг `--experimental-strip-types` позволяет импортировать `.ts` напрямую — отдельного шага
сборки для тестов нет.

Что покрывать здесь:

- **Логика стора**: переходы состояний, вычисление `dirty`, слияние ответа с локальным
  черновиком, обработка ошибки.
- **Правила и фильтры**: то, что можно вызвать функцией и сравнить с ожиданием.
- **Парсинг схем**: что валидный ответ проходит, а невалидный — падает. Второе важнее.

```js
test("невалидный ответ отклоняется схемой", () => {
  assert.throws(() => knowledgeListSchema.parse({ sections: [{ section: "facts" }] }));
});
```

Не покрывать здесь: вёрстку, порядок DOM, стили — это либо Playwright, либо не тест.

## Playwright

```bash
bun run e2e            # headless
bun run e2e:headed     # видеть браузер
bun run e2e:ui         # интерактивный режим
bun run e2e:report     # отчёт последнего прогона
bun run e2e:codegen    # записать сценарий по клику
```

Конфигурация: `playwright.config.ts` (актуальный), `playwright.legacy.config.ts` (старый
контур S-CRM — не расширять).

Что проверять:

- Вход (dev-login) → попадание в рабочую зону → выход.
- Аноним на защищённом пути → редирект на `/login?next=…`.
- Основной путь раздела: открыть → увидеть данные → выполнить действие → увидеть результат.
- Роль `viewer`: необратимые действия недоступны, и при прямой попытке сервер отвечает 403.

Селекторы — по роли и тексту (`getByRole`, `getByText`) либо по `data-testid`. Селекторы по
классам Tailwind ломаются при любом изменении оформления.

## Правило пустых данных

Прогон, в котором нечего проверять, — не зелёный.

```js
assert.ok(rows.length > 0, "выборка пуста — прогон недействителен");
```

Сценарий Playwright, который «прошёл», потому что список пуст и ни один шаг не выполнился,
даёт ложную уверенность. Проверять наличие данных явно.

Обратная проверка: сломать вход намеренно и убедиться, что тест краснеет. Тест, который
никогда не падал, ничего не доказывает.

## Стабильность e2e

- Ждать **состояния**, а не времени: `await expect(locator).toBeVisible()`, не `waitForTimeout`.
- Данные для сценария готовить программно (сид/api), а не кликами по UI: иначе один
  сломанный экран роняет все тесты.
- Каждый сценарий независим: не полагаться на порядок и на состояние, оставленное соседом.
- Сеть к внешним провайдерам в e2e — мокать или отключать. Прогон, зависящий от чужого
  API, краснеет по чужим причинам.

## Перед коммитом

```bash
bun run typecheck        # tsc --noEmit
bun run lint
bun run test
bun run e2e              # если задет пользовательский путь
```

`typecheck` отдельно от сборки: Next может собрать проект, в котором типы расходятся с
контрактом, — и расхождение всплывёт в рантайме.
