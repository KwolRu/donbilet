# Сессия и авторизация на фронте

Канон: `backend/docs/adr/ADR-0002-tenancy-workspace-isolation.md`.

## Как устроено

```text
браузер
  │  cookie: access_token, refresh_token (httpOnly)
  ▼
nginx :8080            same-origin: / → фронт, /api → gateway
  ├─ /            →  Next.js :3000
  └─ /api/*       →  gateway :5000
                        │  верифицирует JWT, ставит x-workspace-id, x-actor-*
                        ├─ auth-service     :5007
                        └─ example-service  :5001
```

**Фронт не является BFF.** Он не подписывает токены, не хранит секрет JWT и не
знает содержимого сессии. Единственная точка проверки подписи — gateway.

## Три следствия, которые определяют код фронта

1. **Токены недоступны JS.** Обе cookie httpOnly, поэтому XSS не уводит сессию.
   Из этого же следует: нельзя прочитать `exp` и «узнать», жива ли сессия —
   про истечение узнаём по 401.

2. **Достаточно `withCredentials: true`.** Никаких заголовков `Authorization`
   вручную. Это уже настроено в `app/core/api/client.ts` — используйте `apiClient`,
   а не голый `fetch`.

3. **Тенант не передаётся с фронта.** `workspace_id` лежит в claim'е токена.
   Заголовков вида `x-workspace-id` фронт не ставит — gateway их затирает
   собственными значениями, иначе тенант подделывался бы клиентом.

## Обновление сессии

Реализовано в `app/core/api/client.ts`, трогать при добавлении фичи не нужно:

- **mutex** — параллельные 401 дают ровно один запрос на `/auth/refresh`;
- **cooldown 5 с** — после успешного refresh повторные 401 переиспользуют
  свежие cookies вместо нового сетевого вызова;
- **BroadcastChannel** — вкладки не съедают one-time refresh друг у друга;
- **проактивный refresh за ~80% TTL** — снимает 401 после долгого простоя,
  когда HTTP-запросов не было (открыт WS или вкладка висела в фоне).

Единственное, что требуется от фичи: после логина выставить маркер сессии в
`localStorage` (ключ `session`), чтобы проактивный refresh знал, что сессия есть.

## Гейт маршрутов

`frontend/proxy.ts` (в Next.js 16 это бывший `middleware.ts`) — **дешёвый**
edge-гейт: проверяет только наличие cookie `access_token`.

```ts
const hasSession = request.cookies.has("access_token");

if (isAppRoutePath(pathname) && !hasSession) → redirect /login
if (isAuthPublicPagePath(pathname) && hasSession) → redirect /app
```

Подпись здесь не проверяется намеренно: это потребовало бы секрета JWT на фронте,
а edge-middleware выполняется на каждый запрос — цена проверки высокая, польза
нулевая (реальную проверку всё равно делает gateway).

Список публичных путей — `lib/routing/auth-paths.ts`. Добавили страницу входа —
добавьте её туда, иначе она либо не откроется, либо будет ловить лишние refresh.

## Обработка кодов

| Код | Кто обрабатывает | Что делает фронт |
|---|---|---|
| 401 | интерцептор `apiClient` | Пытается refresh и повторяет запрос. Долетело до кода — сессия мертва, ведём на `/login` |
| 403 | стор | Показывает сообщение. Не ретраить |
| 404 | стор | Пустое состояние или сообщение. Для чужой сущности бэкенд отдаёт именно 404, а не 403 |
| 409 | стор | Конфликт версий — предложить перезагрузить данные |
| 429 | стор | Показать «слишком часто», не ретраить автоматически |
| 502/503 | `ServerErrorBoundary` | Событие `app:server-error` → страница-заглушка |

## Чего не делать

- Не читать и не хранить токены в `localStorage` — они httpOnly и не должны туда попадать.
- Не дублировать refresh в своём api-модуле: получите два параллельных обновления
  и «съеденный» one-time refresh-токен.
- Не проверять права на фронте как единственный рубеж: скрытая кнопка — это UX,
  а не защита. Решение принимает бэкенд.
- Не завязывать код на поддомен тенанта: их нет.
