# Инварианты платформы

Инвариант — правило, нарушение которого является **дефектом ревью**, а не предметом
обсуждения. Каждое правило ниже сопровождается ценой нарушения: если цену нельзя назвать,
это не инвариант, а предпочтение.

---

## I-1. Tenant из проверенного claim'а

Идентификатор тенанта берётся **только** из подписанного токена (проверка по JWKS/секрету).
Входящие заголовки `x-tenant-id`, `x-workspace-id`, `x-school-slug` — **затираются**
middleware до попадания в контроллер.

**Цена нарушения.** Любой клиент подставляет чужой идентификатор и читает чужие данные.
Дыра не видна на ревью: код выглядит обычным, тесты проходят.

**Исключение.** Service-to-service вызовы, где вызывающий уже проверил контекст. Тогда:
отдельный секрет, constant-time сравнение, и **владелец данных всё равно проверяет
принадлежность сущности тенанту**.

---

## I-2. Фильтр по tenant в каждом запросе

```ts
prisma.lead.findMany({ where: { workspaceId, status } })   // ✅
prisma.lead.findMany({ where: { status } })                // ❌ даже если сервис «тенантный»
```

**Цена.** Один пропущенный фильтр в редком эндпоинте = утечка между тенантами. Такие
находят по жалобе клиента, а не по тестам.

**Механизм защиты, а не дисциплина.** Middleware/расширение ORM, добавляющее фильтр
автоматически, + запрет глобальных запросов + проверка скриптом инвариантов.

---

## I-3. Внешние провайдеры — только через адаптер

Единый контракт на класс провайдеров (источник данных, канал связи, платёж). Бизнес-код
знает **возможность**, а не вендора.

```ts
send(channel: 'email' | 'telegram', payload)   // ✅ канал
sendViaSendgrid(payload)                       // ❌ вендор в коде
```

**Цена.** Смена провайдера = переписывание бизнес-логики; невозможность fallback;
невозможность посчитать экономику по провайдерам.

**Следствие.** Один адаптер = архитектура **не проверена**. Пока не подключён второй
провайдер того же класса, абстракция гипотетична.

---

## I-4. Политики как код, fail-closed

Жёсткие правила (кто что может, когда можно отправлять, что запрещено) — в движке политик,
а не в `if` по коду.

Нет явного `allow` → запрет. Движок недоступен → запрет.

**Цена fail-open.** В момент инфраструктурного сбоя система теряет ровно те ограничения,
ради которых governance строился: инцидент множится на инцидент.

**Граница.** Роли и права доступа к эндпоинту — это guard приложения. В политику выносится
**бизнес-политика** (окна отправки, лимиты, чёрные списки, право сервиса на инструмент).
Смешивать — значит тащить модель пользователей в Rego.

---

## I-5. Секреты — только из хранилища

Ни в репозитории, ни в конфиг-файлах под git, ни в образах. Пути изолированы по домену:
секреты каналов недоступны AI-сервису и наоборот.

**Цена.** Ротация ключа превращается в релиз; компрометация одного сервиса даёт доступ ко
всем ключам; ключ в истории git остаётся навсегда.

**Проверяемое следствие.** Приложение должно **падать при старте**, если обязательный
секрет не сконфигурирован, а не работать «как-нибудь».

---

## I-6. Шлюз только маршрутизирует

API-gateway/BFF: аутентификация, маршрутизация, агрегация ответов, терминация протоколов.
Бизнес-логика, доступ к доменным таблицам, доменные решения — в доменных сервисах.

**Цена.** Шлюз становится вторым монолитом, который меняется на каждый релиз каждого
домена и является единой точкой отказа с бизнес-багами.

---

## I-7. Контракты — в одном месте

`.proto`, общие DTO, коды ошибок, типы событий — в общем модуле/пакете. Копия контракта
рядом с сервисом запрещена.

**Цена.** Две копии расходятся молча. Ошибка проявляется в рантайме на границе, обычно в
проде и обычно в редком поле.

---

## I-8. Durable для длинных процессов

Процесс с > 1 шага, состоянием, паузами (часы/дни) или ожиданием внешнего события —
durable workflow. Activity **идемпотентна** и принимает идемпотентный ключ.

**Цена.** Цепочка cron + флаги в Redis теряется при рестарте; восстановление невозможно;
дубли отправок; «почему клиенту написали дважды» без ответа.

---

## I-9. Генерируемое — не редактируется руками

Если схема БД собирается из частей, клиент ORM генерируется, а конфиги рендерятся —
править результат руками запрещено; правится источник.

**Цена.** Изменение теряется при следующей генерации, обычно у другого разработчика и
обычно перед релизом.

---

## I-10. Статус определяется доказательствами

«Сделано» = есть evidence живого прогона с числами. Не «код написан», не «должно работать»,
не «тесты зелёные» (тест мог пройти на пустых данных).

**Цена.** Документация расходится с реальностью; планирование строится на ложном статусе;
на демонстрации выясняется, что половина не работала никогда.

---

## I-11. Отклонение фиксируется, а не замалчивается

Если реализация разошлась с принятым решением (нативная фича недоступна, вендор не
поддерживает, требование оказалось иным) — это записывается в ADR разделом «Актуализация
по факту» с причиной.

**Цена.** Через полгода никто не понимает, почему код не соответствует документу, и
«исправляет» его обратно в нерабочее состояние.

---

## I-12. Tenant-префиксы во всей инфраструктуре

```
Redis:      <tenant>:<service>:<key>
Очереди:    <tenant>__<service>__<queue>
Индексы:    tenant_<tenant>_<domain>_v1
Файлы S3:   <tenant>/<domain>/<id>
```

**Цена.** Кэш одного тенанта отдаётся другому; очередь одного клиента забивает обработку
остальных; поиск возвращает чужие документы.

---

## Как проверять

Инвариант, который нельзя проверить автоматически, будет нарушен. Минимум:

- `scripts/check-invariants.mjs` — статический скан (I-2, I-3, I-5, I-6, I-7, I-9).
- Тесты политик (`opa test`) — I-4.
- Тест изоляции: запрос под тенантом A к сущности тенанта B возвращает 404/403 — I-1, I-2.
- Тест старта без секрета: сервис падает — I-5.
- Приёмка по evidence — I-10, I-11.
