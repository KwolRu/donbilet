# Durable-оркестрация длинных процессов

Вопрос не «Temporal или BullMQ», а **какие гарантии нужны процессу**. Ответ на него
определяет инструмент, а не наоборот.

## Матрица выбора

| Гарантия | Очередь (BullMQ/SQS) | Durable workflow (Temporal/Inngest) |
|---|---|---|
| Ретрай задачи | ✅ | ✅ |
| Состояние между шагами | ручное (Redis/БД) | ✅ встроено |
| Пауза часы/дни | cron-костыль | ✅ `sleep('7 days')` |
| Ожидание внешнего сигнала | поллинг | ✅ сигнал |
| Восстановление после рестарта | с потерей позиции | ✅ с точностью до шага |
| Компенсация (saga) | вручную | ✅ обычный код |
| История выполнения | логи | ✅ полная, запрашиваемая |
| Human-in-the-loop | самодельно | ✅ сигнал + таймаут |
| Стоимость инфраструктуры | низкая | **сервер + своя БД** |
| Кривая обучения | ~нулевая | детерминизм workflow |

**Правило.** Durable workflow — если процесс имеет **> 1 шага с состоянием**, ретраи с
backoff между шагами, длинные паузы, ожидание внешнего события или требование «выполнить
ровно один раз». Очередь — быстрая одношаговая фоновая работа, rate-limited вызовы,
простые периодические джобы.

Держать оба нормально: `CollectionWorkflow` в Temporal, отправка одного письма — в очереди.

## Детерминизм workflow-кода

Код workflow воспроизводится из истории при каждом восстановлении, поэтому в нём **нельзя**:

```ts
Date.now()          Math.random()        crypto.randomUUID()
fetch()             fs.*                 прямые вызовы БД
process.env         сторонние синглтоны  импорт модулей с побочными эффектами
```

Всё это — в **activity**. В workflow — только оркестрация, `sleep`, сигналы, дочерние
workflow и детерминированные вычисления.

Типовая ловушка: workflow импортирует константу из модуля activities, а тот тянет ORM и
сеть — бандлер workflow падает или тащит в изолированный контекст то, чего там быть не
может. Решение: константы, нужные workflow, **дублируются явно** в workflow-модуле с
комментарием почему, либо выносятся в отдельный чистый модуль.

## Activity: правила

```ts
export async function runTask(input: TaskInput): Promise<TaskResult> {
  const attempt = Context.current().info.attempt;   // номер попытки доступен
  // Идемпотентный ключ приходит СНАРУЖИ (формирует workflow), а не генерируется здесь:
  // при повторе ключ обязан совпасть, иначе побочный эффект случится дважды.
  const res = await callService({ ...input, idempotencyKey: input.idempotencyKey });
  return res;
}
```

- **Идемпотентна.** Temporal гарантирует «хотя бы один раз» для activity; «ровно один раз»
  обеспечивает ваш идемпотентный ключ.
- Ключ формирует **workflow** (детерминированно, например из `workflowId` + шага), а не
  сама activity.
- Внешние вызовы (HTTP, LLM, провайдеры) — **только** в activity, и только через
  адаптер/шлюз.
- Ошибки классифицированы: неретраибельные (400, политика запретила) помечаются как
  non-retryable, иначе Temporal будет упорно повторять то, что не починится.

## Политики ретраев и таймауты

```ts
const { verifyCandidate, establishStatus } = proxyActivities<typeof activities>({
  startToCloseTimeout: '30 seconds',
  retry: {
    initialInterval: '2 seconds',
    backoffCoefficient: 2,
    maximumInterval: '30 seconds',
    maximumAttempts: 4,
    nonRetryableErrorTypes: ['BadRequestError', 'PolicyDeniedError'],
  },
});

// Долгая работа — своя политика, а не общая.
const { collectBatch } = proxyActivities<typeof collectionActivities>({
  startToCloseTimeout: '5 minutes',
  heartbeatTimeout: '30 seconds',      // длинная activity ОБЯЗАНА слать heartbeat
  retry: { maximumAttempts: 3 },
});
```

Правило вложенности таймаутов:
`activity timeout < workflow timeout`, `внешний вызов внутри activity < activity timeout`.

## Сигналы, запросы, human-in-the-loop

```ts
const stopSignal = defineSignal<[string]>('stop');
const replySignal = defineSignal<[LeadReply]>('leadReplied');
const statusQuery = defineQuery<WorkflowStatus>('status');

setHandler(stopSignal, (reason) => { stopped = true; stopReason = reason; });
setHandler(replySignal, (r) => { reply = r; });
setHandler(statusQuery, () => ({ step, stopped, waitingSince }));

// Ждём ответ лида до 7 дней ИЛИ немедленной остановки:
const answered = await condition(() => !!reply || stopped, '7 days');
```

Это заменяет поллинг: цепочка касаний останавливается **в момент** ответа, а не при
следующем проходе cron. Ради этого durable-оркестрация обычно и покупается.

Для approval-шага: сигнал + таймаут + ветка «никто не подтвердил» (эскалация или отмена).
Ветку «не подтвердили» пишут реже всего — и именно она случается.

## Дочерние workflow и параллелизм

- Дочерний workflow — когда у части процесса **свой жизненный цикл** (может пережить
  родителя или должен закрыться вместе с ним — `ParentClosePolicy`).
- Массовая обработка: не запускать 10 000 дочерних workflow разом — батчить, ограничивать
  конкуренцию, использовать continue-as-new при длинной истории.
- История workflow не бесконечна: длинные циклы требуют `continueAsNew`, иначе упрётесь в
  лимит размера истории.

## Компенсации (saga)

Распределённой транзакции нет; есть последовательность шагов с компенсацией на каждый:

```ts
const done: Array<() => Promise<void>> = [];
try {
  await reserveSlot(x);   done.push(() => releaseSlot(x));
  await charge(y);        done.push(() => refund(y));
  await notify(z);
} catch (e) {
  for (const undo of done.reverse()) await undo().catch(() => {});
  throw e;
}
```

Компенсация тоже идемпотентна: она может выполниться дважды.

## Идентификаторы workflow

`workflowId` — детерминированный и осмысленный:
`collect:<tenant>:<area>:<date>`, `touch:<tenant>:<leadId>`.

Это даёт дедупликацию бесплатно: повторный запуск с тем же id либо отклоняется, либо
присоединяется к существующему (в зависимости от политики повторного использования id).

## Namespacing и tenancy

- Платформенные процессы (сбор, верификация) — общий namespace.
- Тенантные процессы (касания, диалоги) — namespace или префикс `workflowId` по тенанту:
  это даёт изоляцию нагрузки и возможность остановить всё по одному клиенту.

## Эксплуатация

- Воркер — отдельный процесс со своим деплоем; порт и переменные окружения фиксированы
  (коллизия портов с легаси-стеком на dev-машине — типовая потеря часа).
- Standalone-процессы часто **не поднимают DI-контейнер приложения**: конфиг, логгер и
  ORM инициализируются вручную. Забытый `dotenv` в воркере — классическая причина «локально
  не работает, в докере работает».
- Мониторинг: число открытых workflow, возраст самого старого, доля упавших activity,
  очередь задач воркера.

## Антипаттерны

- **Cron + флаги в Redis вместо workflow.** Теряется при рестарте, дубли, нет истории.
- **Поллинг вместо сигнала.** Задержка реакции + нагрузка на БД.
- **Побочные эффекты в workflow.** Работает, пока не случится восстановление.
- **Activity без идемпотентности.** Ретрай = второе письмо клиенту.
- **Один общий retry-профиль на всё.** Тяжёлая activity падает по таймауту лёгкой.
- **Нет ветки «никто не подтвердил».** Процесс висит вечно.
- **Temporal ради одношаговой задачи.** Инфраструктура без выгоды.
