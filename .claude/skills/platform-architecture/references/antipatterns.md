# Архитектурные антипаттерны

Формат: **симптом → почему больно → как чинить**.

---

### 1. Тенант из заголовка

**Симптом.** `const tenant = req.headers['x-workspace-id']`.

**Почему больно.** Любой клиент подставляет чужой идентификатор и читает чужие данные.
На ревью не видно: код выглядит обычным, тесты проходят.

**Чинить.** Тенант — из проверенного claim'а токена; входящие tenant-заголовки затираются
в middleware. Тест: подстановка чужого заголовка не меняет результат.

---

### 2. Запрос без tenant-фильтра

**Симптом.** `findMany({ where: { status } })` в тенантном сервисе.

**Почему больно.** Утечка между тенантами. Находится по жалобе клиента.

**Чинить.** Фильтр в каждом запросе + механизм по умолчанию (расширение ORM) + тест
«пустой тенант видит пустые списки».

---

### 3. Сервис-обёртка над инфраструктурой

**Симптом.** `database-service`, `redis-service`, `cache-service`.

**Почему больно.** Сетевой хоп и точка отказа без единой выгоды; каждый доступ к данным
становится распределённым вызовом.

**Чинить.** Это shared infrastructure, а не микросервис. Общий клиент — в общей библиотеке.

---

### 4. Бизнес-логика в шлюзе

**Симптом.** Gateway обращается к доменным таблицам, считает бизнес-правила.

**Почему больно.** Второй монолит в единой точке отказа, релизится на каждое изменение
каждого домена.

**Чинить.** Шлюз: аутентификация, маршрутизация, агрегация. Домен — в доменном сервисе.

---

### 5. Общая БД как интеграция

**Симптом.** Два сервиса пишут в одну таблицу «чтобы не гонять по сети».

**Почему больно.** Схема становится публичным API, которое нельзя менять; транзакционные
гонки между сервисами; владение данными потеряно.

**Чинить.** Один писатель на таблицу. Остальным — API/события. Если разделить нельзя —
это один сервис, и граница проведена неверно.

---

### 6. Распределённый монолит

**Симптом.** Сервисы всегда релизятся вместе; изменение контракта требует синхронного
деплоя трёх репозиториев.

**Почему больно.** Все издержки микросервисов, ни одной выгоды.

**Чинить.** Либо склеить обратно, либо сделать контракты обратно совместимыми и разорвать
временную связанность (события вместо синхронных цепочек).

---

### 7. Синхронная цепочка из четырёх сервисов

**Симптом.** A → B → C → D в одном пользовательском запросе.

**Почему больно.** Доступность перемножается (4 × 99.9% = 99.6%), латентность
складывается, отказ любого звена роняет всё.

**Чинить.** Сократить цепочку, кэшировать, вынести часть в асинхронную обработку.

---

### 8. Cron + флаги в Redis вместо durable-процесса

**Симптом.** «Проверим через 3 дня» реализовано как периодическая джоба, читающая
статусы из Redis.

**Почему больно.** Состояние теряется при рестарте; дубли; нет истории; «почему клиенту
написали дважды» без ответа.

**Чинить.** Durable workflow с `sleep` и сигналами; activity идемпотентны.

---

### 9. Activity без идемпотентности

**Симптом.** Ретрай оркестратора отправляет второе письмо.

**Почему больно.** Гарантия доставки «хотя бы один раз» превращается в дубли для клиента.

**Чинить.** Идемпотентный ключ формирует **workflow** (детерминированно), исполнитель
проверяет его перед побочным эффектом.

---

### 10. Побочные эффекты в workflow

**Симптом.** `Date.now()`, `fetch`, ORM внутри workflow-кода.

**Почему больно.** Работает, пока не случится восстановление из истории — тогда поведение
расходится и процесс ломается непредсказуемо.

**Чинить.** В workflow — только оркестрация. Всё остальное — в activity.

---

### 11. Fail-open в governance

**Симптом.** Политика недоступна → продолжаем.

**Почему больно.** В момент инфраструктурного сбоя система теряет ровно те ограничения,
ради которых governance строился.

**Чинить.** Fail-closed по умолчанию, с внятной причиной в решении. Исключения — явные,
обоснованные и видимые в журнале.

---

### 12. Правило времени без учёта перехода через полночь

**Симптом.** `h >= start && h < end` для рабочего окна.

**Почему больно.** Настройка «пауза 00:00–06:00» даёт окно 6→0 (`start > end`) — условие
не выполняется никогда, и правдоподобная пользовательская настройка **молча блокирует всю
отправку**. Обнаруживается через дни тишины.

**Чинить.** Три случая: границы совпали (круглосуточно), окно внутри суток, окно через
полночь. Плюс тест на каждый.

---

### 13. Один адаптер как доказательство абстракции

**Симптом.** Интерфейс провайдера есть, реализация одна.

**Почему больно.** В абстракцию просачиваются особенности единственного вендора; при
подключении второго выясняется, что контракт не подходит, и переписывать надо всё.

**Чинить.** Проверять контракт вторым провайдером как часть приёмки, а не «когда
понадобится».

---

### 14. Слаг вендора в бизнес-коде

**Симптом.** `if (provider === 'sendgrid')`, `sendViaTelegram(...)` в доменном сервисе.

**Почему больно.** Смена провайдера = правка бизнес-логики; невозможен fallback; экономика
по провайдерам не считается.

**Чинить.** Бизнес-код знает **канал/способность**, а не вендора. Особенности —
в `capabilities()` адаптера.

---

### 15. Секрет в конфиге под git

**Симптом.** Ключ в `config.yaml`, «мы потом уберём».

**Почему больно.** В истории git он остаётся навсегда; ротация превращается в релиз;
компрометация одного репозитория даёт всё.

**Чинить.** Только `os.environ/…` / хранилище. Приложение падает при старте без секрета.
Проверять историю git на утечки при внедрении правила.

---

### 16. Ручная правка сгенерированного файла

**Симптом.** Прямая правка `schema.prisma`, собираемого из частей.

**Почему больно.** Изменение теряется при следующей генерации — обычно у другого
разработчика и обычно перед релизом.

**Чинить.** Править источник; в сгенерированный файл — заголовок «не редактировать»;
проверка в CI, что сгенерированное совпадает с источником.

---

### 17. Статус по документации

**Симптом.** Галочка «сделано» стоит, потому что задача описана и код есть.

**Почему больно.** Планирование строится на ложном статусе; на демонстрации выясняется,
что половина не работала никогда.

**Чинить.** Статус — по живому прогону с evidence. При ревизии перепроверять прогоном, а не
чтением.

---

### 18. Молчаливое отклонение от ADR

**Симптом.** Реализовано иначе, чем записано, и нигде это не отражено.

**Почему больно.** Через полгода никто не понимает, почему код не соответствует документу,
и «чинит» его обратно в нерабочее состояние.

**Чинить.** Раздел «Актуализация по факту» в том же ADR: что построено, где разошлось,
почему, какой инвариант сохранён.

---

### 19. Общая библиотека с бизнес-логикой

**Симптом.** В `shared` появился доменный сервис.

**Почему больно.** Все сервисы связаны релизами общей библиотеки — распределённый монолит
через зависимость.

**Чинить.** В `shared` — контракты, клиенты инфраструктуры, middleware безопасности.
Домен — только в своём сервисе.

---

### 20. Нет теста «пустой тенант»

**Симптом.** Тесты изоляции есть, но все — на данных существующего тенанта.

**Почему больно.** Самый дешёвый тест (завести пустого тенанта и пройти по всем спискам)
ловит больше всего пропущенных фильтров, и именно его не делают.

**Чинить.** Добавить пустого тенанта в набор e2e и проверять, что все списки пусты.
