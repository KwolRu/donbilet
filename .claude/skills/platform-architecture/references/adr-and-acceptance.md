# ADR и приёмка по доказательствам

Два механизма против одной проблемы: **система расходится со своим описанием, и никто не
знает, где правда.**

---

## ADR (Architecture Decision Record)

### Когда писать

- Выбор технологии или отказ от неё.
- Граница сервиса, модель tenancy, схема данных с долгими последствиями.
- Правило, которое станет инвариантом («все внешние вызовы — через адаптер»).
- Отклонение от ранее принятого решения.

Не писать: на выбор библиотеки для форматирования дат, на реализацию одной функции.
Признак «нужен ADR»: через полгода кто-то спросит «почему так?» — и без записи ответа не
будет.

### Структура

```markdown
# ADR-00NN: <решение одной фразой>

**Статус:** предложено | принято | заменено ADR-00MM | отклонено
**Дата:** YYYY-MM-DD
**Контекст:** что заставило принимать решение (проблема, ограничение, требование)

## Решение
Что решили. Императивно, без «возможно» и «в будущем».

## Следствия
Что становится возможным и что обязательным. Здесь же рождаются инварианты.

## Компромиссы
Чем платим. ADR без этого раздела — реклама, а не решение.

## Альтернативы
Что рассматривали и почему отклонили. Иначе через год это предложат снова.
```

### Раздел «Актуализация по факту» — ключевая практика

Через некоторое время после реализации в тот же ADR добавляется раздел:

```markdown
---
## Актуализация по факту (<веха>, YYYY-MM-DD)

**Что реально построено.** …

**Отклонение от ADR.** Формулировка «X делается средствами Y» не реализуема в текущем
развёртывании, потому что <причина>. Реализовано так: <как>. Инвариант <какой> сохранён.

**Находки, повлиявшие на решение.** …
```

Почему это критично: реализация **всегда** расходится с намерением — вендор не поддержал
фичу, требование оказалось иным, нативная возможность требует режима, который сняли. Без
записи через полгода никто не понимает, почему код не соответствует документу, и
«исправляет» его обратно в нерабочее состояние.

**Правило:** отклонение фиксируется, а не замалчивается. Осознанное отклонение с причиной —
нормальная инженерия. Молчаливое — технический долг с отложенным сроком взрыва.

Шаблон: `assets/adr-template.md`.

## Приёмка по доказательствам

### Принцип

**«Сделано» = есть evidence живого прогона с числами.** Не «код написан», не «должно
работать», не «тесты зелёные» — тест мог пройти на пустых данных.

### Уровни доказательства

| Уровень | Что доказывает | Достаточно для |
|---|---|---|
| Юнит-тест | логика функции | внутреннего рефакторинга |
| Интеграционный тест | связка модулей | ветки в PR |
| **Живой прогон с evidence** | система делает то, что обещано | закрытия задачи |
| Прогон в проде с метриками | работает на реальных данных | закрытия эпика |

### Формат evidence

JSON рядом с репозиторием (`audit/evidence/<task>.json`), содержащий:

```json
{
  "task": "Ф5.12 тест платформенности",
  "startedAt": "2026-08-22T14:00:00Z",
  "environment": "local",
  "steps": [
    { "name": "исходный upstream", "expected": "openai/gpt-5.6-luna", "actual": "openai/gpt-5.6-luna", "ok": true },
    { "name": "смена маршрута одной строкой", "actual": "UPDATE ai_routing_policies …", "ok": true },
    { "name": "upstream после смены", "expected": "deepseek/deepseek-v4-flash", "actual": "deepseek/deepseek-v4-flash", "ok": true },
    { "name": "код не менялся", "actual": "git diff --stat = 0 файлов в src/", "ok": true }
  ],
  "summary": { "total": 11, "passed": 11, "invalid": null }
}
```

Требования:

- **Числа, а не прилагательные.** «11/11», а не «работает хорошо».
- **Ожидание и факт рядом.** Только факт не доказывает ничего.
- **Прогон падает на пустых данных.** `total: 0` = провал, а не успех. Это правило
  спасает от самой частой иллюзии: зелёный прогон, в котором цикл не выполнился ни разу.
- Evidence воспроизводим одной командой, записанной в самом файле или рядом.

### Что считается достаточным доказательством по типам задач

| Тип | Доказательство |
|---|---|
| Абстракция (адаптер, шлюз) | работает на **двух** реализациях; смена — конфигом, `git diff` в бизнес-коде пуст |
| Tenant-изоляция | запрос под тенантом A к сущности B → 404/403; пустой тенант → пустые списки |
| Идемпотентность | повтор с тем же ключом → тот же результат, побочный эффект не повторился |
| Durable-процесс | убить воркер посередине → процесс продолжился с того же шага |
| Политика | `opa test` зелёный + живой отказ с внятной причиной |
| Бюджет/лимит | при исчерпании **новых выполнений не появляется** |
| AI-фича | golden-датасет + live-прогон (см. `ai-evals-ops`) |
| Секреты | сервис не стартует без обязательного секрета |

### Живой статус проекта

Один файл (`CURRENT.md` или аналог), который обновляется **по фактам**, а не по плану:

- что закрыто и чем доказано (ссылка на evidence);
- что помечено сделанным, но не проверено вживую — отдельным знаком;
- осознанные отклонения от плана/ADR с причиной;
- блокеры с указанием, что именно блокирует.

**Честность статуса важнее его красоты.** Ложный статус «готово» дороже открытого блокера:
на нём строится планирование, и цена ошибки растёт с каждым днём.

Опасный частный случай: галочка проставлена по документации, а не по прогону. При ревизии
статуса проверять **живым прогоном**, а не чтением задачи.

Шаблон приёмки: `assets/acceptance-template.md`.
