# Границы сервисов

Микросервис — это **граница деплоя и отказа**, а не способ разложить папки. Неверная
нарезка дороже монолита: распределённые транзакции, сетевые отказы и версионирование
контрактов появляются сразу, а выгода — никогда.

## Критерии: сервис или модуль

Отдельный сервис оправдан, если выполняется **хотя бы одно**:

| Критерий | Пример |
|---|---|
| Независимый цикл деплоя | биллинг релизится отдельно от CRM |
| Другой профиль нагрузки | сбор данных масштабируется ×10, остальное нет |
| Изоляция сбоя обязательна | падение отправки не должно ронять веб-интерфейс |
| Другая команда-владелец | Conway работает независимо от вашего мнения |
| Другой рантайм/зависимости | воркер с тяжёлыми ML-библиотеками |
| Требование изоляции доступа | сервис с доступом к платёжным данным |

Если ни один не выполняется — **модуль внутри существующего сервиса**. Разделить потом
дешевле, чем склеивать обратно.

## Что НЕ является сервисом

- `database-service`, `redis-service`, `cache-service`, `elasticsearch-service` — это
  **shared infrastructure**, а не микросервисы. Обёртка вокруг СУБД добавляет сетевой хоп
  и точку отказа, не давая ничего.
- `common-service`, `utils-service` — это библиотека.
- Сервис без собственных данных, который только читает чужие таблицы — это модуль,
  оформленный как сервис, с сетью посередине.

## Владение данными

**Одна таблица — один сервис-писатель.** Читать могут другие (через API/gRPC/реплику),
писать — только владелец.

Ownership фиксируется явно: файл `model-ownership.md` или аннотация в схеме. Без
зафиксированного владения через год в таблицу пишут трое, и никто не знает, кто последний.

Если два сервиса пишут в одну таблицу — они на самом деле один сервис, и граница проведена
неверно.

## Типовая нарезка продуктовой платформы

```
gateway / BFF        — вход, аутентификация, маршрутизация, агрегация. БЕЗ бизнес-логики
auth                 — вход/регистрация/токены/сессии всех ролей
core (домен)         — основные бизнес-сущности и операции
collector / ingest   — сбор и обогащение из внешних источников (другой профиль нагрузки)
channels             — исходящие/входящие коммуникации (изоляция сбоя, свои лимиты)
ai                   — AI-задачи (см. ai-layer-architecture)
notification         — уведомления внутри продукта
billing              — тарифы, платежи, лимиты (изоляция доступа)
analytics            — агрегаты и отчёты (другой профиль запросов)
shared               — контракты, общие DTO, утилиты. НЕ сервис
```

Начинать не со всех сразу: `gateway + core + auth` покрывают старт, остальное выделяется
по критериям выше, когда критерий реально появился.

## Общий модуль (shared)

Что кладётся:

- контракты (`.proto`, DTO, типы событий, коды ошибок);
- клиенты кросс-сервисных механизмов (политики, секреты, хранилище файлов);
- middleware безопасности (валидация токена, tenant-контекст);
- константы прав/ролей.

Что **не** кладётся: бизнес-логика домена. Как только в shared появляется доменный сервис,
все сервисы становятся связаны его релизами — это распределённый монолит.

## Внутрисервисная структура (NestJS-профиль)

```
src/
  main.ts
  app.module.ts
  core/                 # конфиг, инфраструктурные сервисы (ORM, S3, кэш)
  shared/               # middleware, декораторы, guards этого сервиса
  modules/
    <feature>/
      <feature>.module.ts
      <feature>.controller.ts     # валидация входа → сервис → формат ответа
      <feature>.service.ts        # бизнес-логика, без HTTP
      dto/
```

Единые правила на все сервисы: глобальный `ValidationPipe({ whitelist,
forbidNonWhitelisted, transform })`, единый фильтр исключений, единый префикс маршрутов,
health-эндпоинт, метрики.

## Межсервисное взаимодействие

| Способ | Когда | Осторожно |
|---|---|---|
| HTTP (внутренний) | простые запросы, разные языки | нужен таймаут, ретрай, классификация ошибок |
| gRPC | частые вызовы, строгий контракт | контракт только в shared |
| События (шина/очередь) | уведомление о факте, слабая связность | доставка ≥1 раз ⇒ обработчик идемпотентен |
| Общая БД | **никогда между сервисами** | это не интеграция, а связанность |

**Правило:** синхронный вызов = временная связанность. Если сервис A не может работать
при падении B — либо это один сервис, либо вызов должен стать асинхронным.

## Service-to-service аутентификация

Внутренние эндпоинты (например, вызов из воркера оркестратора) не используют
пользовательский токен:

```ts
const expected = process.env.INTERNAL_RPC_SECRET;
if (!expected) throw new ServiceUnavailableException('secret не сконфигурирован'); // fail-closed
const a = createHash('sha256').update(received).digest();
const b = createHash('sha256').update(expected).digest();
if (!timingSafeEqual(a, b)) throw new UnauthorizedException();
```

Хэширование перед сравнением — чтобы `timingSafeEqual` получал буферы одинаковой длины.
Отсутствие секрета = отказ, а не «пропустим».

## Конфигурация и окружение

- Один источник переменных на сервис, валидируемый при старте (обязательные — падение).
- Порты фиксированы и задокументированы: коллизии с легаси-стеком на dev-машине —
  типовая потеря часа.
- Локальный запуск: одна команда поднимает инфраструктуру + все сервисы.

## Антипаттерны нарезки

- **Распределённый монолит** — сервисы, которые всегда релизятся вместе.
- **Наносервисы** — сервис на сущность; накладные расходы превышают домен.
- **Сервис-обёртка над БД** — сетевой хоп без ценности.
- **Общая БД как интеграция** — схема становится публичным API, который нельзя менять.
- **Логика в gateway** — второй монолит в единой точке отказа.
- **Синхронная цепочка из 4 сервисов** — доступность перемножается: 4 × 99.9% = 99.6%.
