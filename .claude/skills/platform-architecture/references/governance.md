# Governance: политики, секреты, адаптеры, аудит

Governance — это ответ на вопрос «кто, что, кому и при каких условиях имеет право
сделать», вынесенный из бизнес-кода в проверяемые артефакты.

---

## 1. Политики как код

### Что выносится в политику

- Право сервиса вызвать инструмент/внешний источник.
- Условия исходящего действия: чёрный список, отписка, дневной лимит, защита от дублей,
  рабочее окно, глобальный стоп-флаг.
- Жёсткие запреты контента.

### Что НЕ выносится

- Роли и права доступа к эндпоинту (`owner`/`operator`/`viewer`) — это guard приложения.
  Вынос в политику тащит туда модель пользователей и делает Rego зависимым от схемы БД.
- Валидация формата — это схема.
- Бизнес-вычисления — это код.

Граница проста: **политика отвечает «можно ли», код отвечает «как»**.

### Контракт PEP (точки применения)

```ts
const decision = await pep.authorize({
  actor: { service: 'ai-service', tenant: workspaceId },
  tool: 'search_organizations',
  source: 'geoapify',
  purpose: 'collection',
  context: { allow_paid: false, requests_today: 412 },
});
if (!decision.allow) throw new ForbiddenException(decision.reason);
```

Требования:

- **Fail-closed.** Любой сбой связи, парсинга или пустой ответ → `allow: false` с
  указанием правила (`pep_unavailable`, `pep_no_decision`). Причина обязательна: без неё
  разбор «почему не отправилось» невозможен.
- **Все факты подставляет сервер** из БД/кэша. Клиент не сообщает, сколько он уже отправил
  сегодня, — иначе политика проверяет то, что ей сказали.
- Таймаут запроса политики короткий (2–3 с) — он на горячем пути.
- Решения логируются: вход (без PII) + результат + правило.

### Тестирование политик

Политики тестируются **как код**: набор входов → ожидаемые решения (`opa test`).
Обязательные кейсы: пустой вход, отсутствующие поля, граничные значения.

**Реальный дефект, который ловится только тестом границ.** Правило рабочего окна
`h >= start && h < end` верно только для окна внутри суток. Настройка «ночная пауза
00:00–06:00» даёт рабочее окно 6→0 (`start > end`) — условие не выполняется никогда, и
правдоподобная пользовательская настройка **молча блокирует всю отправку**. Правило
обязано разбирать три случая: границы совпали (пауза не настроена ⇒ круглосуточно), окно
внутри суток, окно через полночь. См. `assets/current-stack/policies/outbound_send.rego`.

## 2. Секреты

### Правила

- Источник — хранилище (Vault/облачный менеджер) с fallback на env **только в dev**.
- Изоляция путей по домену: `secret/channels/*`, `secret/ai/*`, `secret/billing/*` —
  политика каждого сервиса даёт доступ только к своему префиксу.
- В репозитории и в образах секретов нет. Конфиги ссылаются на переменные окружения
  (`os.environ/KEY`), а не содержат значения.
- Приложение **падает при старте**, если обязательный секрет отсутствует. «Работает
  как-нибудь без секрета» — источник самых дорогих инцидентов.
- Единый загрузчик с кэшем: `loadSecrets()` — одна точка, где известно, откуда берутся
  ключи.

### Реестр известных секретов

Загрузчик обязан отдавать список **значений** известных секретов для output-фильтра утечек.
Если фильтр читает `process.env`, а ключи переехали в хранилище и удалены из `.env`, он
молча перестаёт что-либо покрывать — см. `ai-evals-ops/references/guardrails.md`.

### Ротация

Ротация должна быть операцией конфигурации, а не релиза. Проверять периодически: «сможем ли
мы сменить ключ провайдера за 5 минут без деплоя». Если нет — секреты живут неправильно.

## 3. Адаптеры внешних провайдеров

**Инвариант.** Любой внешний сервис (источник данных, канал связи, платёж, обогащение) —
за адаптером с единым контрактом на класс. Слаг вендора в бизнес-логике — ошибка ревью.

Три слоя, которые часто путают:

| Слой | Ответственность |
|---|---|
| **Реестр источников** | экономика: приоритет, лимиты, бюджет, health, платность |
| **Шлюз инструментов** | транспорт + authz + аудит + маршрутизация |
| **Адаптер/сервер** | вызов конкретного внешнего API за контрактом |

Смешение слоёв — типичная причина того, что «добавить провайдера» превращается в неделю:
экономика зашита в адаптер, аудит — в бизнес-код, а маршрутизация — в `if`.

### Правило двух реализаций

**Один адаптер = архитектура не проверена.** Абстракция, у которой одна реализация,
почти всегда протекает: в неё просачиваются особенности единственного вендора. Проверять
контракт вторым провайдером — обязательный приёмочный шаг, а не «когда понадобится».

### Классификация ошибок провайдера

```ts
type ProviderErrorClass = 'rate_limit' | 'quota_or_auth' | 'provider_failure' | 'timeout' | 'unknown';
```

Разные классы → разные операционные реакции: притормозить / сменить ключ / ретраить /
переключить провайдера. Без классификации в мониторинге видно только «ошибки», и решение
принимается вручную каждый раз.

## 4. Аудит

Что логируется обязательно:

- каждый вызов внешнего API: кто, какой инструмент, **хэш** аргументов, статус, длительность;
- каждое решение политики: вход (без PII), решение, правило;
- каждое необратимое действие: кто инициировал, какой актор, идемпотентный ключ, результат;
- изменения конфигурации: маршруты, лимиты, версии промптов, права.

Аудит **не** содержит: значений секретов, персональных данных, полных текстов сообщений
(только идентификаторы и хэши, если не принято отдельное решение о хранении).

Практическое требование: по одному `correlationId` должна собираться вся цепочка —
запрос пользователя → workflow → activity → внешний вызов → решение политики → результат.

## 5. Необратимые действия и стоп

Для действий, которые нельзя отменить (отправка, списание, публикация):

- **Гейт роли** на эндпоинте (guard), **плюс** политика на само действие.
- **Идемпотентный ключ** обязателен.
- **Глобальный стоп-флаг тенанта** — мгновенно останавливает все исходящие, независимо от
  бюджета, расписания и очередей. Проверяется в политике, а не в клиенте.
- Признак «кто исполнитель»: система или человек — это разные истории аудита.

Стоп-флаг проверяется **на сервере в момент действия**, а не при постановке в очередь:
между постановкой и исполнением проходит время, ради которого он и нужен.
