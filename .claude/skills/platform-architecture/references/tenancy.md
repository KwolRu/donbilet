# Мультитенантность

Модель tenancy выбирается **до первой таблицы**. Смена модели позже — это миграция всех
данных, всех запросов и всей инфраструктуры одновременно.

## Три модели

| Модель | Изоляция | Стоимость | Когда |
|---|---|---|---|
| **Общая БД + `tenant_id`** | на уровне приложения | низкая | SaaS, много мелких тенантов, единый релиз |
| **Схема на тенанта** | на уровне СУБД | средняя | десятки–сотни тенантов, требование раздельных данных |
| **БД/стек на тенанта** | полная | высокая | enterprise, регуляторика, изоляция производительности |

Дефолт для продуктового SaaS — **общая БД + `tenant_id`**. Остальные модели покупаются за
операционную сложность и берутся только под конкретное требование (комплаенс, шумный
сосед, географическое размещение).

Решение фиксируется в ADR вместе с ценой: «схема на тенанта отклонена, потому что
миграции ×N и провижининг усложняют релиз».

## Резолв тенанта

```
Токен (подписанный)  ──> claim workspace_id  ──> WorkspaceContext  ──> запросы
Заголовки x-tenant-* ──> ЗАТИРАЮТСЯ middleware
Поддомен / slug      ──> только для выбора темы/логина, НЕ для авторизации данных
```

```ts
// middleware
const token = fromAuthHeader(req) ?? fromCookie(req);
const claims = await validator.verify(token);          // JWKS/секрет, с кэшем ключей
req.workspace = { workspaceId: claims.workspace_id, actorUserId: claims.sub };
delete req.headers['x-workspace-id'];                  // затирание входящего
delete req.headers['x-actor-user-id'];
```

**Почему затирать, а не игнорировать.** Игнорирование опирается на дисциплину каждого
контроллера. Затирание делает подмену невозможной физически — и это проверяемо.

Поддомен/slug — удобство маршрутизации и брендинга. Авторизация данных на них не строится
никогда: slug виден в адресной строке и подставляется руками.

## Фильтрация данных

Три уровня защиты, нужны все три:

1. **Явный фильтр в запросе** — база.
2. **Механизм по умолчанию** — расширение ORM/репозиторий, добавляющий `tenant_id`
   автоматически; ручной запрос без фильтра запрещён линтером/скриптом инвариантов.
3. **RLS в СУБД** (если поддерживается) — последний рубеж, ловит то, что пропустило
   приложение.

```sql
ALTER TABLE leads ENABLE ROW LEVEL SECURITY;
CREATE POLICY tenant_isolation ON leads
  USING (workspace_id = current_setting('app.workspace_id')::uuid);
```

RLS требует, чтобы соединение выставляло `app.workspace_id` — это нетривиально при пуле
соединений. Если не готовы платить эту цену, честно записать в ADR, что защита — два
уровня, а не три.

## Схема таблиц

Каждая бизнес-таблица несёт:

```sql
workspace_id  uuid NOT NULL REFERENCES workspaces(id),
created_at    timestamptz NOT NULL DEFAULT now(),
updated_at    timestamptz,
-- составной индекс ПЕРВЫМ полем tenant:
CREATE INDEX ON leads (workspace_id, status, created_at DESC);
```

`workspace_id` **первым** в составном индексе: иначе планировщик сканирует все тенанты и
фильтрует после — на больших объёмах это разница в порядки.

Уникальность — всегда в связке с тенантом:
`UNIQUE (workspace_id, email)`, а не `UNIQUE (email)`.

## Инфраструктурные префиксы

```
Redis      <tenant>:<service>:<key>
Очереди    <tenant>__<service>__<queue>
Индексы    tenant_<tenant>_<domain>_v1
Файлы      <tenant>/<domain>/<id>
Метрики    tenant как label ТОЛЬКО при ограниченном числе тенантов (кардинальность!)
```

Очереди с префиксом тенанта дают ещё и справедливость: один клиент с 100k задач не
блокирует остальных.

## Платформенные vs тенантные настройки

Типовой паттерн для любой конфигурации (маршруты, промпты, лимиты, шаблоны):

```
tenant-override (workspace_id = X) → платформенный дефолт (workspace_id = NULL) → ошибка
```

Правила:
- `NULL` в `tenant_id` означает «платформенное» — и это единственное допустимое место,
  где tenant может быть пустым.
- Цепочка резолва одинакова для всех видов конфигурации: разная логика fallback даёт
  комбинации, которые никто не тестировал.
- Финальный шаг — **явная ошибка**, а не молчаливый дефолт.

## Провижининг тенанта

Создание тенанта — транзакционная операция с идемпотентностью: повтор не создаёт второй
воркспейс. Что входит: запись тенанта, владелец, дефолтные настройки, посев справочников,
создание бакетов/индексов/очередей.

Зарезервированные slug'и (`www`, `api`, `app`, `admin`, `static`) — в константах и
проверяются при создании.

## Удаление тенанта

Продумывается заранее, иначе окажется невозможным:
- мягкое удаление + срок хранения;
- список всех мест с данными тенанта (БД, файлы, кэш, индексы, очереди, внешние системы);
- экспорт данных перед удалением (требование GDPR-подобных режимов).

## Тестирование изоляции

Обязательные тесты, без них tenancy не считается реализованной:

1. Запрос под тенантом A к сущности тенанта B → **404/403**, не 200 и не пустой список.
2. Подстановка `x-workspace-id` чужого тенанта не меняет результат.
3. Токен с `workspace_id` A и путь с slug'ом B → отказ.
4. Ключи кэша/очередей содержат префикс (проверять по факту, не по коду).
5. Список сущностей под новым пустым тенантом → пусто (ловит запросы без фильтра —
   они вернут чужие данные).

Тест №5 — самый дешёвый и ловит больше всего: заведите тенанта без данных и пройдите по
всем спискам приложения.
