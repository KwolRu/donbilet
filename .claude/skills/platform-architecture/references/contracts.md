# Контракты между сервисами

Контракт — это то, что нельзя изменить в одностороннем порядке. Всё остальное —
реализация. Граница проходит там, где ошибка проявится у потребителя, а не у автора.

## Где живут контракты

Единственное место — общий модуль/пакет:

```
shared/src/
  proto/          # gRPC-контракты
  dto/            # межсервисные DTO (по доменам)
  events/         # типы событий шины
  constants/      # коды ошибок, права, справочники
  interfaces/     # общие интерфейсы (адаптеры провайдеров)
```

Копия контракта рядом с сервисом запрещена: копии расходятся молча, и ошибка всплывает в
рантайме, в редком поле, обычно в проде.

## Версионирование

| Изменение | Совместимость | Что делать |
|---|---|---|
| Добавить необязательное поле | обратно совместимо | просто добавить |
| Добавить обязательное поле | ломает | новая версия контракта |
| Удалить/переименовать поле | ломает | deprecate → две версии → удаление |
| Сузить тип/enum | ломает | новая версия |
| Расширить enum | ломает потребителя со строгим switch | потребитель обязан иметь ветку `default` |

**Версия — в самом запросе**, а не только в URL: `taskVersion`, `schemaVersion`,
`eventVersion`. Неподдержанная версия — **явный отказ**, а не молчаливое исполнение по
другой версии контракта. Молчаливое исполнение даёт результат, который выглядит правильным.

## Schema pinning для внешних контрактов

Контракты внешних API (провайдеры, инструменты) фиксируются хэшем схемы. При расхождении —
остановить вызовы этого инструмента и поднять ошибку, а не «продолжить как получится».

Это единственный способ поймать несовместимое изменение внешнего API **на границе**, а не
через неделю в виде странных данных.

## Ошибки как часть контракта

Потребитель принимает решения по коду ошибки, значит код — контракт:

| Класс | Код | Реакция потребителя |
|---|---|---|
| Невалидный запрос | 400 | чинить запрос, не ретраить |
| Не аутентифицирован | 401 | обновить токен |
| Запрещено политикой | 403 | не ретраить, чинить права |
| Не найдено | 404 | ветка отсутствия |
| Конфликт состояния | 409 | перечитать и повторить |
| Лимит/бюджет исчерпан | **402 / 429** | не ретраить сразу; пополнить/подождать |
| Ошибка апстрима | 502 | ретрай с backoff |
| Недоступен | 503 + `Retry-After` | ретрай по заголовку |

Всё в 500 = потребитель не может отличить «почини запрос» от «повтори позже» и ретраит
бесконечно то, что не починится.

Тело ошибки — единого формата на всю платформу, без стектрейсов и внутренних деталей:

```json
{ "statusCode": 402, "error": "AiBudgetExceeded", "message": "…", "spentUsd": 12.3, "limitUsd": 12 }
```

## Идемпотентность как контракт

Любая операция с побочным эффектом принимает `idempotencyKey`:

- ключ формирует **вызывающий**, детерминированно по бизнес-смыслу;
- повтор с тем же ключом возвращает **тот же результат**, не выполняя действие второй раз;
- ответ содержит признак повтора (`reused: true`) — потребителю это нужно для метрик и UI;
- ключ хранится вместе с результатом; TTL — не меньше максимального окна ретраев
  оркестратора.

Без идемпотентности любая доставка «хотя бы один раз» превращается в дубли: два письма,
два списания, два лида.

## События

Формат события — тоже контракт:

```ts
interface DomainEvent<T> {
  id: string;            // uuid события (дедупликация у потребителя)
  type: string;          // 'lead.status_changed'
  version: number;
  occurredAt: string;    // ISO
  tenantId: string;
  correlationId?: string;
  payload: T;
}
```

Правила:

- **Доставка ≥ 1 раза** ⇒ обработчик идемпотентен по `id`. Всегда. Не «наша шина
  гарантирует ровно один раз».
- Событие описывает **факт**, а не команду: `lead.status_changed`, не `update_lead`.
- Payload содержит то, что нужно потребителю, а не всю сущность: иначе схема сущности
  становится публичным контрактом.
- Порядок между событиями **не гарантирован**, если не заданы партиции по ключу.
- Потребитель не падает на неизвестных полях и неизвестных `type`.

## Контракты адаптеров

Для класса внешних провайдеров — один интерфейс:

```ts
interface OutboundChannelAdapter {
  readonly channel: ChannelType;
  capabilities(): { supportsAttachments: boolean; maxLength: number; requiresOptIn: boolean };
  send(msg: OutboundMessage, ctx: SendContext): Promise<SendResult>;
  health(): Promise<HealthStatus>;
}
```

`capabilities()` обязателен: без него бизнес-код начинает знать про особенности вендоров
(«у телеграма нельзя писать первым»), и абстракция протекает обратно.

`SendResult` содержит классификацию ошибки (`rate_limit`, `quota_or_auth`,
`provider_failure`, `timeout`), потому что операционная реакция на них разная: притормозить
/ сменить ключ / ретраить.

## Совместимость и тесты

- **Contract tests**: потребитель фиксирует ожидания, поставщик прогоняет их в CI.
- **Golden-примеры** запросов/ответов в репозитории — они же документация.
- Правило раскатки: сначала поставщик поддерживает обе версии, потом мигрируют
  потребители, потом старая версия удаляется. Никогда не наоборот.
