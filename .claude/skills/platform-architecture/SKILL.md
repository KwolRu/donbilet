# Архитектура платформы

Правило принятия решений: **сначала инварианты, потом контракты, потом технологии.**
Технология — реализация требования, а не его источник. Если проект уже на конкретном
стеке — продолжать с ним; если стек не определён — предлагать профиль по умолчанию
(см. `references/stack-selection.md`), явно называя компромиссы.

## Когда применять

- Новая система или новый сервис: где границы, что общее.
- «Нужен ли отдельный микросервис под X».
- Мультитенантность: изоляция, ключи, префиксы, тестирование.
- Длинные процессы: очередь, cron или durable workflow.
- Подключение внешнего провайдера (данные, каналы связи, платежи).
- Секреты, политики, аудит, права сервисов.
- Оформление решения (ADR) и приёмка фичи.

## Когда НЕ применять

- Вопрос внутри AI-слоя (шлюз, промпты, tools, RAG) → `ai-layer-architecture`.
- Качество AI, метрики, guardrails, инциденты → `ai-evals-ops`.
- Прикладная фича внутри существующего сервиса без архитектурного выбора — просто делать.

## Инварианты (нарушение = ошибка ревью)

1. **Tenant-идентификатор берётся из проверенного claim'а токена**, входящие
   `x-tenant-*`/`x-workspace-*` заголовки затираются. Клиент никогда не определяет,
   в чьих данных он работает.
2. **Каждый запрос к tenant-данным несёт явный фильтр по tenant.** Не «сервис же
   тенантный» — фильтр в самом запросе.
3. **Все внешние провайдеры — только через адаптер за единым контрактом.** Слаг вендора
   в бизнес-логике запрещён; добавление провайдера = новый адаптер + запись в реестре.
4. **Политики и запреты — как код (policy-as-code), fail-CLOSED.** Нет явного `allow` →
   запрет. Недоступность движка политик = запрет, а не «продолжим».
5. **Секреты — только из хранилища/окружения**, никогда в репозитории и в конфиг-файлах
   под git. Изоляция путей по домену (каналы ≠ AI ≠ платежи).
6. **Шлюз только маршрутизирует.** Бизнес-логика в нём — ошибка.
7. **Межсервисные контракты — в одном общем месте**, дублировать `.proto`/DTO по сервисам
   запрещено.
8. **Длинный процесс с состоянием — durable workflow, а не цепочка cron+Redis.**
   Activity идемпотентна и несёт идемпотентный ключ.
9. **Схема БД генерируется из версионируемых частей** (если проект так устроен) —
   ручная правка сгенерированного файла запрещена.
10. **Статус работы определяется доказательствами, а не документацией.** «Сделано» = есть
    evidence живого прогона.

## Порядок анализа/проектирования

1. **Определить домены и владельцев данных.** Кто единственный пишет в эту таблицу —
   тот и владеет. Сервис без собственных данных — почти всегда не сервис, а модуль.
2. **Проверить необходимость сервиса** по критериям `references/microservices.md`
   (независимый деплой / масштабирование / изоляция сбоя / отдельная команда).
   Не прошёл — модуль внутри существующего.
3. **Зафиксировать модель tenancy** до первой таблицы: `references/tenancy.md`.
4. **Описать контракты**: HTTP/gRPC/события, версии, ошибки, идемпотентность —
   `references/contracts.md`.
5. **Классифицировать процессы**: одношаговые фоновые → очередь; многошаговые с
   состоянием/паузами/ожиданием → durable workflow — `references/durable-orchestration.md`.
6. **Спроектировать governance**: политики, секреты, аудит, адаптеры —
   `references/governance.md`.
7. **Выбрать стек** по способностям, а не по названиям — `references/stack-selection.md`.
8. **Оформить решение ADR** и определить критерии приёмки —
   `references/adr-and-acceptance.md`.

## Правила assets

- `assets/current-stack/` — реализации для профиля по умолчанию: `policies/*.rego`,
  `prisma/ai-layer.prisma`, `temporal/*.ts`, `vault/*.hcl`. Копировать только тот
  компонент, который реально используется в проекте.
- `assets/adr-template.md`, `assets/acceptance-template.md` — оформление решений и приёмки.
- `scripts/check-invariants.mjs` — запускаемая проверка инвариантов этого скилла **и**
  AI-слоя (I-1, I-2, I-5, I-6, I-7, I-9 + AI-1…AI-7). Зависимостей нет, Node 18+.

```bash
node scripts/check-invariants.mjs --root ./backend/microservices   # текстовый отчёт
node scripts/check-invariants.mjs --root . --json                  # для CI
node scripts/check-invariants.mjs --only I-1,AI-2 --strict         # точечно, warning тоже роняет
```

Настройка под проект — `.invariants.json` в корне: `tenantField`, `gatewayDirs`,
`aiFacadeFiles`, `contractsDir`, `generatedFiles`, **`platformModels`** (список
не-тенантных таблиц — без него правило I-2 шумит на справочниках). Ложное срабатывание
подавляется комментарием `invariant-ok: <причина>` в строке; причина обязательна.

Скрипт — эвристика: он ловит массовые механические нарушения и не заменяет ревью.

## Чеклист архитектурного ревью

- [ ] У каждого сервиса есть собственные данные и причина быть отдельным процессом.
- [ ] Tenant берётся из проверенного claim'а; входящие tenant-заголовки затираются.
- [ ] Каждый запрос к tenant-данным фильтрован; ключи кэша/очередей/индексов имеют префикс.
- [ ] Контракты лежат в общем месте, версионированы, ошибки классифицированы.
- [ ] Внешние вызовы идут через адаптер + политику + аудит; слагов вендоров в коде нет.
- [ ] Длинные процессы durable; activity идемпотентны.
- [ ] Секретов в репозитории нет; политики fail-closed и покрыты тестами.
- [ ] Решения зафиксированы в ADR; отклонения от ADR записаны, а не замолчаны.
- [ ] Приёмка опирается на evidence, а не на «должно работать».
- [ ] `node scripts/check-invariants.mjs` — зелёный.
