# Реестр источников и адаптеры

## Три слоя, которые нельзя смешивать

| Слой | Отвечает за | Не отвечает за |
|---|---|---|
| **Реестр источников** | приоритет, возможности, платность, дневной бюджет, health, статистика | транспорт, авторизацию вызова |
| **Шлюз инструментов** | authz (fail-closed), аудит, маршрутизация к нужному серверу | выбор источника, экономику |
| **Адаптер / сервер источника** | вызов конкретного внешнего API за контрактом | всё вышеперечисленное |

Смешение — типовая причина того, что «добавить источник» превращается в неделю: экономика
зашита в адаптер, аудит — в бизнес-код, маршрутизация — в `if`.

## Контракт адаптера

```ts
interface SourceAdapter {
  readonly slug: string;

  /** Что источник умеет. Без этого бизнес-код начинает знать про вендоров. */
  capabilities(): {
    search: boolean;
    details: boolean;
    contacts: boolean;
    reviews: boolean;
    maxRadiusM?: number;
    supportsPagination: boolean;
    paid: boolean;
  };

  search(input: SearchInput): Promise<{ records: RawRecord[]; cursor?: string; schemaHash: string }>;
  details?(id: string): Promise<RawRecord>;
  health(): Promise<{ ok: boolean; latencyMs?: number; reason?: string }>;
}
```

`capabilities()` обязателен. Без него в конвейере заводится `if (source === 'overpass')`, и
абстракция протекает обратно.

`schemaHash` фиксирует форму ответа источника: несовместимое изменение внешнего API ловится
**на границе**, а не через неделю в виде странных данных. При расхождении — остановить
источник, а не «продолжить как получится».

## Правило двух реализаций

**Один адаптер = архитектура не проверена.** В абстракцию с единственной реализацией всегда
просачиваются особенности вендора: формат координат, семантика радиуса, поведение пагинации.
Подключение второго источника — часть приёмки, а не «когда понадобится».

## Реестр: что хранить

```
slug, label, enabled
priority              — порядок выбора при равных возможностях
paid                  — требует ли явного разрешения на трату
daily_limit           — потолок вызовов в сутки
cost_per_call         — для отчётности
health_status         — ok | degraded | down (обновляет проверка)
last_error_class      — rate_limit | quota_or_auth | provider_failure | timeout
requests_today        — счётчик, источник правды для лимита
coverage              — регионы/категории, где источник полезен
```

Выбор источника: **фильтр по возможностям → фильтр по health → фильтр по бюджету →
сортировка по приоритету и стоимости**. Не «первый в списке».

## Бюджет и rate-limit

Проверяются **до** вызова, а не после. Постфактум-контроль — отчёт, а не лимит.

```ts
if (source.paid && !ctx.allowPaid) return deny('paid_source_not_allowed');
if (source.dailyLimit && source.requestsToday >= source.dailyLimit) return deny('daily_limit_exceeded');
```

Факты подставляет **сервер** из своей статистики. Клиент, сообщающий «я сегодня сделал 5
запросов», проверяет сам себя.

Rate-limit — отдельно от бюджета: бюджет про деньги за сутки, лимитер про частоту в секунду.
Лимитер должен уметь возвращать `retryAfterMs`, иначе вызывающий будет молотить в стену.

## Классификация ошибок провайдера

```ts
type ProviderErrorClass =
  | 'rate_limit'      // 429 → притормозить (backoff)
  | 'quota_or_auth'   // 401/403 → сменить ключ / проверить квоту
  | 'provider_failure'// 5xx → ретраить, при устойчивости — деградировать на другой источник
  | 'timeout'         // сеть → ретрай
  | 'unknown';
```

Разные классы требуют разных операционных реакций. Без классификации в мониторинге видно
только «ошибки», и решение принимается вручную каждый раз.

`quota_or_auth` дополнительно должен помечать источник в реестре как `degraded`: продолжать
дёргать источник с исчерпанной квотой — трата времени на каждом лиде.

## Секреты источников

Ключи — из хранилища, с изоляцией по домену. Приложение падает при старте, если ключ
обязательного источника не сконфигурирован, а не работает «как-нибудь» и не выясняет это на
первом же лиде.

## Health-проверка

Периодическая, дешёвая (не полноценный поиск), с записью результата в реестр. Источник,
трижды подряд ответивший ошибкой, помечается `down` и исключается из выбора до
восстановления — иначе конвейер тратит попытки на заведомо мёртвый источник.

## Профиль LeadMap

Источники обёрнуты в MCP-серверы; вызов идёт `SourceManager → MCP Gateway → MCP-сервер`.
Gateway централизованно делает authz (OPA, fail-closed), аудит и маршрутизацию. Конверт
вызова и классификация ошибок — в `microservices/shared/src/mcp/`. Адаптеры конкретных
источников — `collector-service/src/modules/sources/adapters/`.
