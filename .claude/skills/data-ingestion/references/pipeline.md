# Этапы конвейера

```
   поиск/обход        сырьё            нормализация      идентичность
  ┌──────────┐    ┌───────────┐      ┌───────────┐    ┌──────────┐
  │ search   │───▶│ raw_record│─────▶│ normalized│───▶│  dedup   │
  └──────────┘    └───────────┘      └───────────┘    └────┬─────┘
                   сохраняем ВСЕГДА                        │
                                                    ┌──────▼──────┐
   скоринг          верификация        обогащение   │  persist    │
  ┌────────┐      ┌────────────┐     ┌───────────┐  │ (upsert по  │
  │ score  │◀─────│  verify    │◀────│  enrich   │◀─│  ключу)     │
  └────────┘      └────────────┘     └───────────┘  └─────────────┘
```

Каждый этап — отдельная единица работы со **своей** идемпотентностью. Слепленные в одну
функцию этапы невозможно перезапустить по отдельности, а перезапускать приходится всегда.

## 1. Поиск / обход

- Вход: область (город, район, радиус, полигон) + категория. Область — типизированная
  структура, а не строка: `radius` и `polygon` ведут себя по-разному у разных источников.
- Пагинация — **курсором источника**, не смещением. Курсор сохраняется вместе с прогоном,
  чтобы продолжить после сбоя.
- Батч фиксированного размера; после каждого батча — сохранение и heartbeat.
- Идемпотентность: ключ прогона `${source}:${area}:${category}:${date}`. Повторный запуск с
  тем же ключом присоединяется к существующему прогону или отклоняется.

## 2. Сырьё

**Сохранять сырой ответ отдельно от разобранного.** Без сырья невозможно переразобрать
данные после исправления парсера — придётся снова платить источнику.

Хранить: `source`, `external_id`, `raw` (JSON), `schema_hash`, `fetched_at`, `run_id`.

Ретенция сырья ограничена (30–90 дней) — иначе таблица становится крупнейшей в базе.

## 3. Нормализация

Чистые функции, тестируемые без БД. Приводят к общей форме:

| Поле | Правило |
|---|---|
| Название | trim, схлопывание пробелов, снятие кавычек и правовых форм (`ООО`, `ИП`) в отдельное поле |
| Телефон | E.164, с указанием страны по региону источника; хранить и оригинал |
| Домен | нижний регистр, без `www`, без схемы, без завершающего слэша; хранить и полный URL |
| Адрес | нормализованная строка + компоненты; координаты отдельно |
| Категория | маппинг таксономии источника в свою; неизвестное → `unknown`, а не молча в «прочее» |

Правило: нормализация **не выбрасывает** оригинал. Она добавляет нормализованные поля рядом.

Неизвестная категория/значение — это сигнал, а не мусор: копить их и периодически
пересматривать маппинг. Молчаливое приведение к дефолту скрывает пробелы в таксономии.

## 4. Дедуп

См. `dedup-and-identity.md`. Здесь важно только место в конвейере: **до** записи, а не
после. Дедуп после вставки означает, что в базе постоянно есть дубли, а склейка — отдельная
миграция.

## 5. Persist

`upsert` по стабильному ключу `(source, external_id)` + связь с канонической сущностью после
склейки. Никаких `create` без проверки: повторный прогон обязан быть безопасным.

Что обновлять при повторной встрече: только поля, которые источник действительно
предоставил, и только если они «свежее». Затирание проверенного факта неподтверждённым
значением из нового прогона — самая обидная потеря данных.

## 6. Обогащение

Отдельный этап, часто с другими источниками и другой экономикой (дороже, медленнее).
Правила:

- Обогащать **не всех подряд**, а по критерию (скор, приоритет, отсутствие ключевого поля).
  Иначе бюджет уходит на записи, которые никогда не понадобятся.
- Каждое добавленное поле несёт свидетельство: откуда, когда, каким способом.
- Обогащение идемпотентно по `(entity_id, enrichment_type)` — повтор не платит второй раз.

## 7. Верификация

См. `verification-and-confidence.md`. Ключевое: это **не** этап «проверить формат», а
установление фактов с уверенностью и серией наблюдений во времени.

## 8. Скоринг

- Считается из **зафиксированных признаков**, а не из «ощущения модели».
- Объяснимый: рядом со скором хранится разбивка по осям, иначе на вопрос «почему 42»
  ответа нет.
- Пересчитывается при изменении входящих фактов — событием, а не ночным полным пересчётом
  (полный пересчёт нужен только при смене формулы).
- Версия формулы хранится вместе со скором: иначе сравнение вчерашних и сегодняшних чисел
  бессмысленно.

## Оркестрация

Цепочка «обход → верификация ×N с интервалом → установление статуса → скоринг» — это
многошаговый durable-процесс с паузами, а не цепочка cron-задач:

- шаги переживают рестарт воркера;
- пауза между попытками верификации — часть процесса, а не отдельная джоба;
- отмена/остановка приходит сигналом, а не поллингом флага.

Одношаговые задачи (отправить один запрос, пересчитать один скор) остаются в обычной
очереди. Критерии выбора — `platform-architecture/references/durable-orchestration.md`.

## Наблюдаемость прогона

Минимум, без которого сбор нельзя эксплуатировать:

```
run_id, source, area, category, started_at, finished_at, status
requested, received, new, updated, duplicates, rejected
errors_by_class (rate_limit / quota_or_auth / provider_failure / timeout)
cost, cursor
```

`rejected` без разбивки по причинам бесполезен: половина отладки сбора — это вопрос
«почему из 200 записей сохранились 40».
