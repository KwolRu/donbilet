# Верификация фактов и уверенность

Верификация — не «проверить формат». Это установление факта о внешнем мире, который может
меняться, наблюдаться с ошибкой и противоречить сам себе.

## Свидетельство как единица

Ничего не записывается как факт напрямую. Записывается **свидетельство**:

```ts
interface Evidence {
  entityId: string;
  claim: string;          // 'website_belongs' | 'phone_reachable' | 'company_active'
  value: string;
  source: string;         // откуда: провайдер, страница, DNS, ручной ввод
  method: string;         // как: http_probe | dns | page_parse | llm_judgement | manual
  observedAt: string;
  confidence?: number;    // вклад ЭТОГО свидетельства
  raw?: unknown;          // на чём основано
}
```

Итоговый факт — **производная** от набора свидетельств, вычисляемая детерминированным
резолвером. Преимущества: новое свидетельство не затирает старое; можно пересчитать после
исправления правил; на вопрос «почему так решили» есть машинный ответ.

## Порядок принятия решения

```
1. детерминированные правила по имеющимся свидетельствам
2. хватило?  → статус, готово (модель не вызывается — экономия и предсказуемость)
3. не хватило → собрать ещё свидетельства (доп. проверки, страницы, источники)
4. всё ещё не хватило → ИИ добирает: суждение + reasons[] + confidence
5. итог считает КОД, подмешивая вклад модели отдельной осью с потолком
```

**Модель не выставляет статус.** Она отвечает на узкий вопрос («принадлежит ли этот сайт
этой организации?») и возвращает суждение с причинами. Решение о статусе принимает
детерминированный код — иначе галлюцинация становится состоянием системы, а аудит
показывает «так решил ИИ».

Подробности вызова — `ai-layer-architecture`.

## Сложение уверенности

```ts
const AXES = {
  phoneMatch:      { weight: 40, cap: 40 },
  domainInProfile: { weight: 35, cap: 35 },
  nameOnPage:      { weight: 20, cap: 20 },
  addressOnPage:   { weight: 15, cap: 15 },
  llmJudgement:    { weight: 25, cap: 25 },   // отдельная ось с ПОТОЛКОМ
};
const THRESHOLD = 60;
```

Правила:

- **Потолок на ось.** Иначе одна ось с несколькими свидетельствами перевешивает все
  остальные.
- **Потолок на вклад модели.** Модель не должна в одиночку переводить факт через порог.
- **Асимметрия допустима и часто нужна.** «Принадлежит» повышает уверенность; «не
  принадлежит» — не понижает автоматически, потому что отрицательное суждение модели о
  редком случае менее надёжно, чем положительное. Асимметрию фиксировать явно в коде и в
  ADR, иначе её сочтут багом.
- **Порог — не 50 по умолчанию.** Подбирается на размеченной выборке, где известен верный
  ответ.

Рядом со статусом хранится разбивка: какие оси сработали и на сколько. Без неё разбор
жалобы превращается в гадание.

## Серии наблюдений

**Единичный отрицательный результат не даёт вывода.** Сайт может лежать пять минут,
DNS — резолвиться с задержкой, провайдер — отдать 503.

```
attempts_required: 3
interval: 30 минут … несколько часов
статус = f(серия), а не f(последняя попытка)
```

Серия реализуется durable-шагами с паузой, а не `setTimeout` и не тремя быстрыми повторами
подряд (три подряд ловят один и тот же сбой).

Промежуточное состояние тоже статус: `unknown_pending` честнее, чем преждевременное
`dead`. Отдельно различать «не проверяли» и «проверяли, не установили» — это разные
операционные ситуации.

## Устаревание фактов

У каждого факта есть срок годности, зависящий от природы:

| Факт | Проверять заново |
|---|---|
| Сайт доступен | недели |
| Телефон принадлежит компании | месяцы |
| Компания существует | месяцы |
| Профиль в соцсети активен | недели |

Факт без даты наблюдения бесполезен: через год он либо верен, либо нет, и отличить нельзя.

## Reachability ≠ verified

Два независимых свойства контакта, которые постоянно путают:

- **verified** — подтверждено, что контакт принадлежит этой сущности;
- **reachable** — по нему технически можно достучаться.

Подтверждённый email из закрытого домена — verified, но не reachable. Найденный на сайте
телефон может быть reachable без подтверждения владельца. Хранить отдельными полями и не
выводить одно из другого.

## Приёмка верификации

- Прогон на реальных данных с числами **до и после**: сколько записей сменило статус.
- Набор контрольных случаев с известным ответом: свой сайт, маркетплейс, соцсеть, чужой
  домен, агрегатор. Маркетплейс и соцсеть **не** должны признаваться собственным сайтом.
- Проверка, что при пустой выборке прогон падает, а не рапортует успех.
- Проверка асимметрии: отрицательное суждение модели не роняет уверенность ниже порога само
  по себе.
