# Guardrails: слои, запреты, режимы отказа

Guardrails — не один фильтр, а четыре слоя с разной ответственностью. Слои **не
дублируются**: дубль означает два места, где чинить, и одно, где забудут.

```
INPUT   границы, санитизация, обрамление недоверенного текста      → 400
AGENT   лимит шагов, таймаут, потолок токенов                      → 502
TOOL    authz (fail-closed) + аудит + safe-проекция  ← в инструменте, не здесь
OUTPUT  утечки секретов, жёсткие запреты, нормализация             → needs_review
```

## INPUT

```ts
export const AGENT_LIMITS = {
  maxContextHintChars: 1000,   // недоверенный фрагмент
  maxInputChars: 4000,         // весь собранный вход
  maxOutputTokens: 1024,
  maxToolSteps: 3,
  timeoutMs: 45_000,
};
```

- Границы проверяются **в дополнение** к DTO-валидации: DTO знает про поля, guardrail —
  про собранный вход целиком.
- Превышение — ошибка, **не** тихое усечение: усечение теряет запреты и делает результат
  невоспроизводимым.
- Управляющие символы вырезаются (кроме `\n`) — ими маскируют инъекции.
- Всё внешнее обрамляется как данные (`frameUntrustedContext`, см.
  `ai-layer-architecture/references/memory-and-context.md`).

**Про prompt injection честно.** Обрамление — митигация, снижающая вероятность, а не
защита. Единственная настоящая защита: у модели нет инструментов необратимого действия,
её выход проходит детерминированную проверку, а решения принимает код. Проектировать надо
так, чтобы **успешная инъекция не давала атакующему ничего ценного**.

## AGENT

- `maxToolSteps` — защита от tool-loop, не оптимизация. Reasoning-модели зацикливаются на
  строгом structured output систематически.
- `timeoutMs` — на всю задачу; таймаут инструмента строго меньше, таймаут шлюза — между.
- `maxOutputTokens` — с запасом для reasoning-моделей: часть бюджета уходит на рассуждение,
  и обрыв на середине JSON выглядит как «модель сломалась».

## TOOL

Этот слой живёт **в инструменте**, а не в guardrails-модуле: authz (fail-closed), аудит,
safe-проекция, валидация схем с обеих сторон. См.
`ai-layer-architecture/references/tool-contracts.md`.

Дублировать его проверками «а можно ли этому агенту этот инструмент» в runner'е — значит
завести второй источник правды об авторизации.

## OUTPUT

### Утечка секретов

```ts
const SECRET_PATTERNS = [
  /sk-[a-z0-9]{16,}/i,
  /\bBearer\s+[a-z0-9._-]{16,}/i,
  /eyJ[a-zA-Z0-9_-]{10,}\.[a-zA-Z0-9_-]{10,}\.[a-zA-Z0-9_-]{6,}/,  // JWT
  /\b[a-f0-9]{40,}\b/i,
  /(api[_-]?key|master[_-]?key)\s*[:=]\s*\S+/i,
];

export function assertNoSecretLeak(text: string): void {
  for (const secret of knownSecretValues()) {          // ← реестр, НЕ process.env
    if (text.includes(secret)) throw new GuardrailOutputError('output содержит секрет');
  }
  for (const re of SECRET_PATTERNS) {
    if (re.test(text)) throw new GuardrailOutputError('output совпал с secret-паттерном');
  }
}
```

**Критичная деталь.** Источник дословных значений — **реестр секретов приложения**, а не
`process.env`. После переезда ключей в хранилище (и удаления из `.env`) чтение одного лишь
env молча перестаёт покрывать реальные ключи. Паттерны ловят не любой формат (например,
`sk-or-v1-…` с дефисами), поэтому дословная проверка остаётся основной защитой — и она
обязана смотреть туда, где ключи реально лежат.

Сканировать нужно **финальные строки**, которые уйдут наружу (сообщение, тема, обоснования),
а не сырой объект модели.

### Жёсткие запреты — политикой, не промптом

Запрет в промпте — вероятностная просьба. Запрет в политике — проверяемое правило:

```rego
package ai.content.safety

violations contains "price_disclosed" if regex.match(`(?i)(\d[\d\s]{2,})\s*(руб|₽|тыс)`, input.text)
violations contains "guarantee_claim"  if regex.match(`(?i)гарантиру|100%\s*результат`, input.text)
violations contains "external_link"    if regex.match(`(?i)https?://`, input.text)

decision := { "safe": count(violations) == 0, "violations": violations }
```

Преимущества: правило меняется без релиза, одинаково применяется ко всем задачам,
тестируется отдельно (`opa test`), и на вопрос «почему сообщение не ушло» есть машинный
ответ вместо россыпи `if` в коде.

Модель поверх политики проверяет **нюансы**, которые нельзя выразить регуляркой:
вводящие в заблуждение обещания, неуместный тон, скрытая агрессия. Итог:
`safe = opaViolations.empty && modelViolations.empty`.

### Safe failure

Сомнительный выход **отклоняется**, а не «подчищается»:

```
GuardrailOutputError → статус needs_review → 502 наружу → запись в журнал
```

- Не пытаться вырезать нарушение из текста: получится полуфабрикат, который выглядит
  нормально и потому опаснее.
- `needs_review` — отдельный статус, а не `failed`: это разные операционные ситуации
  (сбой vs требует человека) и разные метрики.
- Пользователю — нейтральное сообщение без деталей проверки: детали помогают обходить.

## Fail-closed и когда fail-open допустим

**По умолчанию fail-closed.** Политика недоступна → запрет. Это инвариант governance:
нет явного `allow` → нет действия.

Fail-open допустим только когда одновременно:

1. Проверка **дополнительная**, а более жёсткий слой остался активен;
2. Отказ полностью блокировал бы продукт, а риск пропуска ограничен;
3. Деградация **явно помечена** в результате и попадает в журнал и метрику.

Пример корректного компромисса: контент-safety, где детерминированные запреты (политика)
отработали, а нюансная модель недоступна — вердикт выносится по политике, факт
недоступности фиксируется как `opa_unavailable` / `model_unavailable` и уводит кейс в
ревью. Ключевое: **деградация видима**, а не молчалива.

Некорректный fail-open: недоступна политика отправки → «отправим, потом разберёмся».

## Порядок применения в runner'е

```
enforceInputBounds          → до трат
frameUntrustedContext       → при сборке входа
assertInputSize             → после сборки
[LLM]
postProcess + нормализация  → сначала привести к домену
assertNoSecretLeak(...)     → потом сканировать финальные строки
[политика запретов]         → для исходящего контента
```

Скан до нормализации проверяет не то, что уйдёт наружу. Политика до нормализации
проверяет сырой текст модели, а не финальный.

## Что НЕ является guardrail'ом

- Просьба в промпте («никогда не …») — это инструкция, её нельзя предъявить как гарантию.
- `try/catch` вокруг вызова — это обработка ошибок.
- Валидация схемы — необходимое, но не достаточное: схема не знает про смысл.
- Ретрай с другой моделью — это деградация, а не проверка.

## Чеклист

- [ ] Четыре слоя присутствуют, ответственность не дублируется.
- [ ] Реестр секретов — источник для output-фильтра (не `process.env`).
- [ ] Жёсткие запреты вынесены в политику и покрыты тестами политики.
- [ ] `needs_review` — отдельный статус с собственной метрикой.
- [ ] Все точки fail-open перечислены явно, каждая помечена в журнале.
- [ ] Сообщения об отказе не раскрывают деталей проверки.
- [ ] Adversarial-кейсы в golden-датасете проверяют каждый OUTPUT-guardrail.
