# Проектирование evals

Eval — не «тест на LLM». Это способ ответить на вопрос **«стало ли хуже»** после смены
модели, промпта, схемы контекста или данных. Всё остальное — следствие.

## Три слоя проверок

| Слой | Что | Стоимость | Когда запускать |
|---|---|---|---|
| **Детерминированные evaluators** | чистые функции над выходом | ~0 | всегда, в CI |
| **Фикстурный прогон** | evaluators на зафиксированных выходах | ~0 | всегда, в CI |
| **Live-прогон** | реальный агент → evaluators | деньги + время | перед релизом, по расписанию |

Первые два запускаются на каждый коммит. Live — по кнопке и по расписанию, с сохранением
evidence.

## Детерминированные evaluators

Чистые функции без LLM: быстро, воспроизводимо, бесплатно, объяснимо.

```ts
export interface EvalResult {
  name: string;
  pass: boolean;
  critical: boolean;   // критичные фейлы РОНЯЮТ кейс
  detail: string;      // почему — для разбора, а не только true/false
}
```

**Критичные vs некритичные.** Разделение обязательно:

- *Критичные* — нарушение контракта или безопасности: невалидная схема, выдуманные
  контакты, запрещённый контент, утечка секрета, недопустимое значение enum.
- *Некритичные* — качество и стиль: язык, длина, заканчивается ли вопросом, упомянут ли
  контекст. Их падение снижает score, но не роняет кейс.

Без этого разделения либо всё красное из-за стилистики, либо ничего не красное вообще.

**Типовой набор для генеративной задачи:**

| Evaluator | Крит. | Проверяет |
|---|---|---|
| `schema_valid` | да | тип, непустота, границы длины |
| `enum_valid` | да | значение из словаря (после нормализации) |
| `no_fabricated_contacts` | да | нет телефонов/email/URL, которых не было во входе |
| `no_forbidden_content` | да | нет цен/обещаний/запрещённых тем |
| `no_secret_leak` | да | не совпало с реестром секретов и паттернами |
| `factual_grounding` | нет | упомянуты факты из контекста, а не выдуманные |
| `language` | нет | язык ответа |
| `style_*` | нет | длина, тон, завершение |

**Grounding без LLM.** Простейшая версия: проверить, что ключевые факты входа (название,
город) встречаются в ответе, а сущности, которых во входе не было (числа, домены, имена),
— отсутствуют. Это ловит большую часть галлюцинаций дешевле любого judge.

## Golden-датасет

Три вида кейсов, все обязательны:

```ts
{
  id: 'fabricated_contact',
  kind: 'adversarial',
  cand: { message: 'Звоните +7 900 123-45-67 или пишите на test@example.ru', channel: 'email' },
  ctx:  { orgName: 'ВАО Дент' },
  expectPass: false,
  expectFail: 'no_fabricated_contacts',   // КАКОЙ ИМЕННО evaluator должен упасть
}
```

- **positive** — корректные ответы, должны проходить.
- **adversarial** — намеренно плохие: выдуманные контакты, раскрытая цена, утечка ключа,
  инъекция инструкций, недопустимый enum. Для каждого зафиксировано, **какой evaluator**
  обязан сработать.
- **edge** — пустой контекст, отсутствующие данные, другой язык, предельная длина.

**`expectFail` — ключевая деталь.** Кейс, который «просто не прошёл», не доказывает
ничего: он мог упасть по другой причине. Проверять надо совпадение имени сработавшего
evaluator'а.

Размер: 6–10 кейсов на задачу для старта. Качество важнее количества — 8 продуманных
кейсов ловят больше, чем 200 сгенерированных.

Датасет живёт в репозитории рядом с кодом и растёт **из инцидентов**: каждый реальный
плохой ответ превращается в новый adversarial-кейс. Это единственный источник роста,
который окупается.

## Live-прогон

```ts
export const LIVE_EVAL_INPUTS = [
  { id: 'live_tool_grounded', useTool: true,  channel: 'email' },
  { id: 'live_no_tool',       useTool: false, channel: 'email', contextHint: '…' },
];
```

Живой прогон обязан покрывать оба пути (с governed-инструментами и без), потому что это
два разных режима сборки контекста с разными отказами.

Результат сохраняется как **evidence-JSON** (см. `assets/eval-suite/run-eval.ts`):

```json
{
  "task": "FIRST_MESSAGE_GENERATION",
  "mode": "live",
  "startedAt": "2026-08-23T10:11:12Z",
  "modelAlias": "app-fast",
  "physicalModels": ["openrouter/openai/gpt-5.6-luna"],
  "promptVersion": 3,
  "cases": [{ "id": "...", "passed": true, "score": 0.87, "evaluators": [...] }],
  "summary": { "total": 8, "passed": 8, "avgScore": 0.91, "costUsd": 0.0042 }
}
```

## Правило пустых данных

**Прогон обязан падать, если входных данных нет.** Самая частая иллюзия: harness зелёный,
потому что список кейсов пуст, сущности не найдены, а цикл не выполнился ни разу.

```ts
if (cases.length === 0) throw new Error('eval: пустой набор кейсов — прогон недействителен');
if (liveInputs.length && resolvedEntities.length === 0)
  throw new Error('eval: не найдено ни одной сущности для live-прогона');
```

То же относится к приёмке фич: «14/14 пройдено» на пустой выборке — это 0/0.

## LLM-as-judge

Применять, когда критерий нельзя выразить функцией: тон, уместность, связность,
соответствие сложной инструкции.

Правила:

- Judge — **дополнение**, а не замена детерминированных проверок. Критичные проверки
  никогда не отдаются judge.
- Судить **другой** моделью, не той, что генерировала. Иначе оценивается собственный стиль.
- Judge возвращает **структурированный** вердикт со шкалой и обоснованием, а не «хорошо/плохо».
- Judge — обычная AI-задача: свой `taskType`, промпт с версией, журнал, стоимость.
  Она тоже стоит денег и тоже деградирует.
- Judge нужно **калибровать**: 20–30 примеров с ручной разметкой, замерить согласие
  (доля совпадений с человеком). Судья, согласующийся с человеком в 60% случаев,
  не измеряет качество — он добавляет шум.

## Регресс-гейты

Что запускать и когда:

| Событие | Фикстуры | Live | Порог |
|---|---|---|---|
| Коммит | ✅ | — | 100% критичных |
| Новая версия промпта | ✅ | ✅ | не хуже baseline по avgScore и 100% критичных |
| Смена алиаса/модели | ✅ | ✅ | то же + сравнение стоимости и p95 |
| Релиз | ✅ | ✅ | то же |
| Ночью по расписанию | ✅ | ✅ | тренд, алерт на падение |

Baseline фиксируется в evidence и обновляется **осознанно**, с указанием причины. Молча
переписанный baseline — способ не заметить деградацию.

## Что мерить помимо качества

- Доля `needs_review` (сработавших output-guardrails) — рост означает деградацию модели
  или атаку.
- Доля невалидного structured output — маркер неподходящей модели для задачи.
- Доля нормализованных enum'ов — систематическая нормализация означает, что маршрут или
  промпт выбраны неверно.
- Стоимость и латентность на кейс — они меняются при смене модели сильнее качества.
