# Архитектор портфеля скиллов

Скилл — не документация и не учебник. Это **исполняемая инструкция для повторяемого
сценария с неочевидными решениями**. Портфель скиллов проектируется как продукт: у каждого
элемента есть свой вопрос, своя граница и своя причина существовать.

Цель — **минимальный полезный портфель**, а не скилл под каждую библиотеку и папку.

## Когда применять

- «Какие скиллы нужны этому проекту», «собери набор скиллов под ТЗ».
- Аудит существующих скиллов: дубли, устаревшее, конфликты, пробелы.
- Спор «нужен ли отдельный скилл под X» или «глобально это или в репозиторий».
- Стек/архитектура изменились, инструкции отстали от кода.
- Онбординг нового репозитория в агентский рабочий процесс.

## Когда НЕ применять

- Обычная разработка: поле в форме, эндпоинт, страница, миграция, багфикс. Для этого
  существуют доменные скиллы — их и вызывать.
- Написание одного конкретного скилла, когда решение уже принято, — достаточно
  `references/skill-blueprint.md`.
- Аудит кода, безопасности, зависимостей: это другие инструменты.

## Три режима

| Режим | Что делает | Что меняет |
|---|---|---|
| **Audit** | анализ проекта + инвентаризация скиллов + отчёт | ничего |
| **Plan** | рекомендуемый портфель, волны, blueprint каждого скилла | ничего |
| **Build** | создаёт/обновляет **утверждённые** скиллы | только файлы скиллов |

Режим по умолчанию — **Audit**. Plan запускается по запросу «предложи портфель / что
добавить». Build — только когда пользователь явно написал «создай», «собери», «реализуй»
и портфель согласован.

**Build никогда не удаляет, не перемещает и не архивирует существующие скиллы.** Cleanup —
отдельное действие с отдельным явным разрешением.

## Принципы

1. **Код важнее документации.** ТЗ описывает намерение; код описывает реальность. При
   расхождении источником истины считается код, а расхождение выносится в отчёт как
   находка, а не сглаживается.
2. **Факты отделены от выводов.** В отчёте три категории: подтверждённые факты (с командой
   или файлом), выводы, неразрешённые противоречия. Смешивать нельзя.
3. **Никаких чисел без evidence.** «12 дублей», «покрытие 80%» заявляются только со ссылкой
   на воспроизводимую команду.
4. **Наличие технологии ≠ потребность в скилле.** Скилл оправдан повторяемостью и риском,
   а не тем, что в проекте есть Redis.
5. **Обновить лучше, чем создать почти такой же.** Новый скилл, на 70% повторяющий
   существующий, — это будущий конфликт инструкций.
6. **Одно каноническое место.** Один скилл живёт либо глобально, либо в репозитории.
   Копия в обоих местах — гарантированное расхождение при первой правке.
7. **Один вопрос на скилл.** Если описание границы требует союза «и» между разными
   доменами — это два скилла или ни одного.

## Процедура

Фазы 0–3 выполняются всегда, 4–6 — по режиму.

0. **Определить корни.** Проектный корень, каталог проектных скиллов, каталог глобальных
   скиллов. Проверить `.gitignore`: версионируются ли проектные скиллы.
1. **Найти главное ТЗ** и вспомогательные документы. → `references/project-discovery.md`
2. **Сверить документацию с кодом** по контрольным точкам (сервисы, схема, маршруты,
   аутентификация, внешние провайдеры). Расхождения зафиксировать.
3. **Инвентаризировать скиллы** — запустить скрипт (см. ниже) и прочитать frontmatter.
   → `references/portfolio-rubric.md`, раздел «Инвентаризация».
4. **Оценить покрытие** по областям и вынести вердикт keep/update/add/replace/archive.
   → `references/portfolio-rubric.md`
5. **Спроектировать недостающие скиллы** по шаблону blueprint.
   → `references/skill-blueprint.md`
6. **Собрать отчёт** по обязательной структуре. → `references/report-template.md`

В Build дополнительно: создать файлы, прогнать валидацию и проверить сценарии активации.

## Размещение

| Признак | Куда |
|---|---|
| Принципы, инварианты, контракты, переносимо в другой проект | глобально |
| Имена сервисов, пути, схемы БД, продуктовые термины, конкретные команды | в репозиторий |
| Дизайн-система конкретного продукта | в репозиторий |
| Практики фреймворка/языка | глобально (или существующий внешний скилл) |

Проверить `.gitignore` **до** утверждения, что проектный скилл версионируется: каталог
`.claude/` часто игнорируется целиком, и тогда «проектный скилл» существует только на одной
машине. `.gitignore` не изменять без явного разрешения — сообщить и предложить.

Если репозиторий обслуживается несколькими агентскими системами, выбрать **один**
канонический источник и предложить механизм синхронизации. Ручные расходящиеся копии не
создавать.

## Инвентаризация: скрипт

```bash
node scripts/inventory-skills.mjs --project <путь-к-репозиторию>            # текст
node scripts/inventory-skills.mjs --project <путь> --json                   # для отчёта
node scripts/inventory-skills.mjs --project <путь> --global <путь>          # свои корни
node scripts/inventory-skills.mjs --self-test                               # проверка логики
```

Даёт воспроизводимое evidence: список скиллов с обеих сторон, качество frontmatter,
побайтовые дубли, одноимённые скиллы с разным содержимым, каталоги без `SKILL.md`,
битые ссылки на references, пустые каталоги. Ничего не изменяет; содержимое файлов не
печатает.

Если Node недоступен — алгоритм и эквивалентные команды оболочки приведены в
`references/project-discovery.md`, раздел «Инвентаризация без скрипта».

## Валидация созданного (обязательна в Build)

- [ ] Frontmatter: `name` совпадает с именем каталога; `description` содержит и триггеры,
      и явное «не использовать для…».
- [ ] Ни одного `TODO`, `[…]`-заглушки, пустого раздела и пустого каталога.
- [ ] Все ссылки на `references/*` существуют; на несуществующие файлы ссылок нет.
- [ ] `SKILL.md` ≤ ~200 строк; детали вынесены в `references/`.
- [ ] Проверены два сценария: запрос, который **должен** активировать скилл, и близкий
      запрос, который **не должен**.
- [ ] Границы с соседними скиллами названы в тексте обоих.
