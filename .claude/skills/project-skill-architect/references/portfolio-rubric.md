# Рубрика портфеля

## Инвентаризация: что собрать по каждому скиллу

| Поле | Откуда | Зачем |
|---|---|---|
| имя, размещение | каталог | канонизация места |
| `description` | frontmatter | триггеры и границы |
| размер `SKILL.md`, число файлов | ФС | признак мега-скилла или заглушки |
| дата последнего изменения | ФС/git | признак заброшенности |
| ссылки на код и пути | содержимое | проверить, что они ещё существуют |
| соответствие коду | проверка выборочно | устаревший скилл хуже отсутствующего |

Обязательная выборочная проверка: взять из скилла 3–5 конкретных утверждений (путь, имя
таблицы, команда, имя сервиса) и проверить их в репозитории. Один провал — скилл под
подозрением, три — он устарел.

## Области проверки

Проходить весь список; по каждой области — «покрыто / частично / пробел» с доказательством.

| # | Область | Признак, что нужен скилл |
|---|---|---|
| 1 | Сквозная доставка фичи | изменение проходит 3+ слоя, есть регулярно забываемые шаги |
| 2 | Frontend и BFF | свой дата-слой, сессии, граница server/client |
| 3 | UI/UX и дизайн-система | собственная идентичность, токены, набор экранов |
| 4 | Backend и API | конвенции модулей, контракты, коды ошибок |
| 5 | БД и миграции | генерация схемы, порядок изменений, обратная совместимость |
| 6 | Auth/authz и tenancy | изоляция данных, источник идентификатора, роли |
| 7 | Security и secrets | хранилище, ротация, запреты на утечки |
| 8 | AI-архитектура | шлюз моделей, промпты, инструменты, runner |
| 9 | AI evals и эксплуатация | качество, guardrails, бюджеты, инциденты |
| 10 | Сбор и обогащение данных | внешние источники, дедуп, нормализация |
| 11 | Evidence и confidence | факты со свидетельствами, уверенность, скоринг |
| 12 | Исходящие коммуникации | необратимые действия, согласие, лимиты |
| 13 | Billing, планы, лимиты | тарифы, счётчики, квоты |
| 14 | Тестирование и приёмка | что считается доказательством готовности |
| 15 | Локальная инфраструктура и деплой | воспроизводимый запуск, порты, окружения |
| 16 | Эксплуатация и инциденты | плейбуки, алерты, деградация |
| 17 | Продуктовые спецификации и ADR | как оформляются решения и требования |
| 18 | Миграция легаси | системный перенос сервисов/схем/данных |

**Наличие технологии в области ≠ потребность в скилле.** Redis в проекте не делает нужным
скилл про Redis.

## Критерии нового скилла

Новый скилл предлагается, только если выполняется **большинство** условий:

| # | Условие | Проверка |
|---|---|---|
| 1 | Сценарий повторяется или дорог при ошибке | найден в истории коммитов / в разборах инцидентов |
| 2 | Содержит неочевидные решения и инварианты | можно назвать цену нарушения |
| 3 | Формулируется точный автотриггер | можно написать `description`, по которому он сработает |
| 4 | Понятная граница ответственности | описывается без союза «и» между доменами |
| 5 | Не покрыт существующими скиллами | проверено чтением их `description` и содержимого |
| 6 | Подтверждается ТЗ или кодом | есть ссылка на файл/раздел |
| 7 | Есть источник истины для сопровождения | понятно, что читать при обновлении |

Меньше четырёх выполненных условий — предложение отклоняется. Ровно четыре-пять —
предлагается как кандидат следующей волны, а не первой.

## Стоп-лист

Не создавать:

- под разовую задачу («перенести один сервис»);
- общий учебник по фреймворку — для этого есть внешние скиллы и документация;
- пересказ официальной документации;
- спекулятивный скилл «пригодится, когда будем делать X»;
- catch-all мега-скилл «всё про бэкенд»;
- копию существующего глобального скилла;
- локальную копию глобального скилла с тем же именем.

Отдельно: **не создавать скилл вместо исправления кода.** Если сценарий сложен из-за
дефекта архитектуры, скилл законсервирует дефект. Такое выносится в отчёт как техдолг.

## Вердикты

| Вердикт | Когда | Что делать |
|---|---|---|
| **keep** | актуален, границы чистые, применяется | ничего |
| **update** | суть верна, детали устарели или размыты | точечная правка + сверка утверждений |
| **replace** | описывает несуществующую архитектуру | новый скилл + архивация старого (с разрешения) |
| **add** | пробел, прошедший критерии | blueprint + Build по согласованию |
| **archive** | не применяется, дублирует, вводит в заблуждение | вывести из автодискавери **только с разрешения** |
| **relocate** | лежит не в своём каноническом месте | перенести с разрешения |

Разница между **update** и **replace**: если после правок от скилла останется меньше
половины — это replace. Косметический ремонт устаревшей архитектуры дороже переписывания.

Вывод из автодискавери — не всегда удаление: достаточно убрать каталог из каталога скиллов
(перенести в архив). Предлагать именно это, а не `rm`.

## Разрешение конфликтов

Два скилла конфликтуют, если по одному запросу оба претендуют на ответ и дают разные
инструкции.

Порядок разрешения:

1. **Разделить границу** — уточнить `description` обоих, добавив «НЕ использовать для…»
   со ссылкой на соседа. Дешевле всего, работает в большинстве случаев.
2. **Поглотить** — если один покрывает второй целиком, второй архивируется.
3. **Расщепить** — если оба покрывают часть и пересекаются, вынести общее в третий, а в
   исходных оставить специфику. Дорого; применять, когда первые два не подходят.

Проектный скилл имеет приоритет над глобальным по продуктовым деталям; глобальный — по
принципам. Это должно быть написано в тексте обоих, иначе агент выберет случайно.

## Проверка дизайн-направления

Выполняется всегда, отдельно от области 3, потому что дизайн чаще всего покрывается
внешними скиллами и потому обрастает дублями.

Собрать факты:

- есть ли макеты/скриншоты/Figma и как они попадают в код;
- есть ли дизайн-система: токены, палитра, типографика, набор компонентов;
- где живут переиспользуемые компоненты и как они компонуются;
- accessibility: фокус, контраст, семантика, клавиатура;
- responsive: какие брейкпоинты реально используются;
- визуальная идентичность: есть ли собственный язык или это дефолт библиотеки;
- server/client boundaries: что рендерится где и почему.

Затем — **проверить существующие дизайн-скиллы перед созданием нового**: продуктовый
дизайн-скилл проекта, универсальные UI/UX-скиллы, гайдлайны веб-интерфейса, скиллы по
композиции и практикам React. Решение:

| Ситуация | Решение |
|---|---|
| Существующий покрывает | переиспользовать, ничего не создавать |
| Не хватает только продуктовых правил | узкий проектный скилл или обновление существующего |
| Нет ни идентичности, ни системы | сначала дизайн-решения, потом скилл |
| Есть общий и продуктовый, они спорят | развести границу: общий — данные и практики, продуктовый — идентичность |

Общий дубликат поверх существующего универсального скилла не создавать никогда.

## Волны

Портфель внедряется волнами, а не целиком.

- **Волна 1** — то, что используется ежедневно и уже болит: сквозная доставка фичи, самый
  нагруженный слой, критичные инварианты.
- **Волна 2** — области с подтверждённой, но менее частой болью.
- **Backlog** — прошедшие критерии, но без текущего повторяющегося сценария. Для каждого
  записывается **условие запуска** («когда появится X»), иначе backlog превращается в
  свалку намерений.

## Метрика достаточности

Портфель достаточен, когда:

- каждый повторяющийся workflow из фазы разведки имеет ровно один адрес;
- ни один скилл не претендует на два разных домена;
- по каждому вопросу разработчика понятно, что вызвать, без чтения всех описаний;
- нет двух скиллов, отвечающих на один вопрос по-разному.

Дальнейшее наращивание портфеля без нового повторяющегося сценария снижает пользу: чем
больше скиллов, тем хуже автовыбор.
