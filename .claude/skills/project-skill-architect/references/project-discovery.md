# Разведка проекта

Цель фазы — получить **проверенную** карту репозитория и понять, какие рабочие сценарии в
нём повторяются. Не пересказ документации, а сверка документации с кодом.

## 1. Найти главное ТЗ

Приоритет источников:

1. **Путь, указанный пользователем.** Если он назван — это главное ТЗ, спорить не с чем.
2. **Явные кандидаты** в порядке убывания вероятности:
   `plan/`, `docs/`, `specs/`, `requirements/`, `rfc/`, `product/`, корневые `*.md`.
3. **Инструкции для агентов**: `CLAUDE.md`, `AGENTS.md`, `.cursorrules`, вложенные
   `*/CLAUDE.md`. Это не ТЗ, но это действующие правила, и они часто устаревают первыми.
4. **ADR** (`docs/adr/`, `doc/adr/`, `architecture/decisions/`) — решения и их отмены.
5. **Живой статус**: `CURRENT.md`, `STATUS.md`, `ROADMAP.md`, `CHANGELOG.md`, доска задач.

```bash
find . -maxdepth 3 -iname "*.md" -not -path "*/node_modules/*" -not -path "*/.git/*" \
  | head -50
ls -1 docs plan specs requirements 2>/dev/null
```

### Как отличить главное ТЗ от соседей

| Признак | Значение |
|---|---|
| Объём кратно больше соседей | обычно это оно |
| Есть «Версия», «Базис», «Основание» и ссылки на другие документы | это вершина иерархии |
| Нумерованные требования, на которые ссылается роадмап и код | это оно |
| Описывает бизнес и рынок, а не систему | это продуктовый документ, не ТЗ |
| Описывает порядок работ и фазы | это план исполнения, не ТЗ |

Если конкурирующих кандидатов несколько и определить главный **по фактам** невозможно —
задать пользователю **один** короткий вопрос со списком кандидатов. Во всех остальных
случаях решать самостоятельно и написать в отчёте, на каком основании.

### Что извлечь из ТЗ

- Границы системы: что входит, что явно не входит.
- Ключевые процессы и их шаги.
- Инварианты и запреты («ни при каких условиях…», «только через…»).
- Нефункциональные требования: изоляция, лимиты, приватность, доступность.
- Точки, где ТЗ уже отменено более поздним решением (ADR).

## 2. Сверить документацию с кодом

**Документация не является источником истины, если противоречит коду.** Проверять по
контрольным точкам — быстро и предметно.

| Контрольная точка | Как проверить |
|---|---|
| Состав сервисов/пакетов | каталоги + manifests (`package.json`, `pyproject.toml`, `go.mod`, `Cargo.toml`, `*.csproj`) |
| Порты и запуск | `docker-compose*.y*ml`, скрипты запуска, `main.*` |
| Модель данных | миграции и схема, а не раздел ТЗ «структура БД» |
| Аутентификация | код middleware/guard, а не описание |
| Мультитенантность | реальный фильтр в запросах и источник идентификатора тенанта |
| Внешние интеграции | клиенты/адаптеры в коде, а не список в ТЗ |
| Маршруты API | роутер/контроллеры |
| Тесты и приёмка | конфиги тестов, CI, скрипты `*e2e*`, каталог evidence |

```bash
git log --oneline -30                      # что делали последним
git log --since="3 months ago" --name-only --pretty=format: \
  | grep -v '^$' | sort | uniq -c | sort -rn | head -30   # где кипит работа
```

Каталоги, в которые чаще всего коммитят, — это и есть места, где повторяются сценарии.
Скиллы нужны там, а не там, где красивая архитектура.

### Классы расхождений

- **Устаревшее**: ТЗ описывает решение, отменённое более поздним ADR или кодом.
- **Опережающее**: ТЗ описывает то, чего ещё нет. Не ошибка — но скилл под это делать рано.
- **Противоречие**: два действующих документа требуют разного. Требует решения человека.
- **Легаси**: код есть, но помечен как не развиваемый. Скиллы под него не создаются.

Каждое расхождение попадает в отчёт с указанием, где документ и где код.

## 3. Карта проекта

Собрать компактно и **только из проверенного**:

```
границы:        сервисы/пакеты, их роли, кто владеет какими данными
данные:         где схема, как мигрируется, есть ли генерация из частей
контракты:      где межсервисные типы, где API-описание, версионирование
вход:           как приходит запрос: шлюз, BFF, прямые вызовы
аутентификация: где выдаётся, где проверяется, откуда берётся тенант
внешний мир:    провайдеры, адаптеры, шлюзы, секреты
процессы:       очереди, воркеры, workflow, cron
проверка:       тесты, e2e, evidence, CI
эксплуатация:   локальный запуск, деплой, наблюдаемость
фронт:          фреймворк, роутинг, дата-слой, дизайн-система
```

Каждая строка — с файлом-подтверждением. Строка без подтверждения переносится в «выводы».

## 4. Выделить повторяющиеся workflows

Скилл окупается там, где сценарий **повторяется** и содержит **неочевидные решения**.
Признаки:

- Один и тот же путь изменения проходит через 3+ слоя (схема → сервис → контракт → фронт).
- В истории коммитов сценарий встречается многократно.
- Есть шаг, который регулярно забывают (регистрация модуля, маршрут, индекс, фильтр).
- Есть решение, ошибка в котором дорога и незаметна (изоляция тенанта, идемпотентность,
  необратимая отправка, деньги).
- Есть проверка, без которой «зелёный» результат ничего не значит.

Источники таких признаков: разборы инцидентов, комментарии в коде вида «ВАЖНО/ВНИМАНИЕ»,
разделы ADR «Актуализация по факту», пометки `TODO` с объяснением причины.

```bash
grep -rn "ВАЖНО\|ВНИМАНИЕ\|ИНВАРИАНТ\|ошибка ревью\|НИКОГДА\|fail-closed" \
  --include=*.ts --include=*.py --include=*.go . | head -40
```

## 5. Выделить инварианты

Инвариант — правило, нарушение которого является дефектом, а не предметом обсуждения. У
него можно назвать **цену нарушения**. Если цену назвать нельзя — это предпочтение, и в
скилл оно идёт как рекомендация, а не как инвариант.

Собирать из: ADR (раздел «Следствия»), комментариев в критичных местах, guard'ов и
middleware, политик, тестов, которые проверяют запреты.

## 6. Инвентаризация без скрипта

Если Node недоступен:

```bash
# перечислить скиллы обеих сторон
for d in "$HOME/.claude/skills"/*/ ./.claude/skills/*/; do
  [ -f "$d/SKILL.md" ] && echo "SKILL  $d" || echo "no-md  $d"
done

# frontmatter: имя и первая строка описания
for f in "$HOME/.claude/skills"/*/SKILL.md ./.claude/skills/*/SKILL.md; do
  echo "== $f"; sed -n '1,12p' "$f" | grep -E '^(name|description):'
done

# побайтовые дубли по одноимённым скиллам
for d in ./.claude/skills/*/; do
  n=$(basename "$d"); g="$HOME/.claude/skills/$n/SKILL.md"
  [ -f "$g" ] && [ -f "$d/SKILL.md" ] && \
    { cmp -s "$g" "$d/SKILL.md" && echo "ДУБЛЬ идентичный: $n" || echo "РАСХОЖДЕНИЕ: $n"; }
done

# заглушки
grep -rl "TODO\|\[TODO" "$HOME/.claude/skills" ./.claude/skills 2>/dev/null | head
```

Проверить `.gitignore`:

```bash
git check-ignore -v .claude/skills 2>/dev/null || echo "не игнорируется — версионируется"
```

## 7. Что записать в отчёт из этой фазы

- Главное ТЗ и на каком основании оно выбрано.
- Карта проекта со ссылками на файлы.
- Список расхождений «документация ↔ код» с классификацией.
- Список повторяющихся workflows и инвариантов — это вход для следующей фазы.
- Всё, что не удалось подтвердить, — отдельным списком «требует уточнения».
