# Blueprint скилла

## Карточка (заполняется в режиме Plan до написания файлов)

```
имя:              kebab-case, совпадает с именем каталога
главный вопрос:   на какой один вопрос отвечает скилл
триггеры:         формулировки пользователя, по которым он должен сработать
антитриггеры:     близкие формулировки, по которым он НЕ должен срабатывать
размещение:       глобально | репозиторий  + обоснование
источник истины:  что читать при обновлении (файлы, ADR, конфиги)
инварианты:       3–10 правил с ценой нарушения
references:       список файлов и вопрос, на который отвечает каждый
assets:           только реально копируемые заготовки (или «нет»)
scripts:          только детерминированные повторяемые проверки (или «нет»)
границы:          с какими скиллами соседствует и где проходит линия
проверка:         2+ сценария активации и 1+ сценарий неактивации
```

Карточка без заполненных «антитриггеров» и «границ» неполна: именно они определяют, будет
ли скилл мешать соседям.

## Frontmatter

```yaml
---
name: <kebab-case, как каталог>
description: >-
  Что делает и для каких задач. Далее — типовые формулировки запросов через
  «Использовать при/по запросам …». В конце — «НЕ использовать для …» со ссылкой
  на соседний скилл.
argument-hint: "[что передать]"   # опционально
---
```

`description` — **единственное**, по чему принимается решение о вызове. Требования:

- различающее: по нему понятно, чем скилл отличается от соседей;
- содержит слова, которыми пользователь реально формулирует задачу, а не термины из кода;
- содержит явное отрицание — без него скилл начинает срабатывать на всё подряд;
- не длиннее нескольких предложений: раздутое описание размывает триггер.

Плохо: «Помогает с бэкендом». Хорошо: «Сквозной паттерн добавления функциональности: схема
→ модуль → маршрут → фронт → приёмка. Использовать при добавлении фичи, эндпоинта, таблицы.
НЕ использовать для устройства AI-слоя — там `<сосед>`.»

## Структура

```
<skill>/
├── SKILL.md              точка входа, ≤ ~200 строк
├── references/           детали по вопросам, грузятся по необходимости
├── assets/               копируемые заготовки (только если реально копируются)
└── scripts/              детерминированные проверки (только если оправданы)
```

Progressive disclosure: `SKILL.md` отвечает «что делать и в каком порядке», `references/` —
«как именно». Всё, что нужно не в каждом вызове, выносится.

Каталог создаётся только под содержимое. Пустые `assets/`, `agents/`, `references/` —
мусор, который выглядит как незавершённая работа.

## Содержание `SKILL.md`

Порядок разделов, проверенный на практике:

1. **Когда применять** — 3–6 пунктов формулировками пользователя.
2. **Когда НЕ применять** — со ссылками на соседей. Обязательный раздел.
3. **Инварианты** — нумерованные, с ценой нарушения. Это ядро скилла.
4. **Порядок действий** — шаги, каждый со ссылкой на reference за деталями.
5. **Маршрутизация по references** — таблица «вопрос → файл».
6. **Правила assets/scripts** — если они есть.
7. **Чеклист** — то, что проверяется перед «готово».

Чего в `SKILL.md` быть не должно: длинных листингов кода, пересказа документации
фреймворка, теории. Код — в `assets/`, детали — в `references/`.

## Инварианты

Инвариант формулируется как правило + цена нарушения:

> **Tenant берётся из проверенного claim'а, а не из заголовка.**
> Цена: любой клиент подставляет чужой идентификатор и читает чужие данные; на ревью это
> не видно — код выглядит обычным.

Если цену назвать нельзя — это рекомендация, и она идёт в reference, а не в список
инвариантов. Размытые инварианты обесценивают список целиком.

3–10 штук. Больше — их перестают читать.

## References

Один файл — один вопрос. Имя файла отвечает на вопрос, а не называет тему:
`runner-and-routing.md` лучше, чем `details.md`.

Внутри: примеры из реального кода, объяснение «почему так», типовые ошибки. Хорошая
проверка качества — раздел «почему именно такой порядок»: если порядок шагов произволен,
скорее всего, он ещё не продуман.

Отдельный `antipatterns.md` оправдан, когда набор ошибок велик и повторяем. Формат:
**симптом → почему больно → как чинить**. Симптом должен быть узнаваем в коде.

## Assets

Добавлять только то, что **реально копируется** в проект: скелеты модулей, шаблоны
конфигураций, заготовки политик, шаблоны документов.

- Комментарии в заготовке объясняют инварианты, а не синтаксис.
- Плейсхолдеры именуются так, чтобы их нельзя было забыть заменить.
- Заготовка «на всякий случай» устареет раньше, чем понадобится.

## Scripts

Добавлять только когда проверка **детерминированная и повторяемая**: инварианты, структура,
инвентаризация, генерация отчёта.

Требования: без внешних зависимостей; read-only, если это проверка; понятный код выхода;
подавление ложных срабатываний с обязательной причиной; самопроверка на маленьком наборе.

Если надёжный переносимый скрипт не получается — оставить алгоритм и команды в reference.
Слабый скрипт хуже его отсутствия: ему верят.

## Антипаттерны скиллов

| Симптом | Почему больно | Как чинить |
|---|---|---|
| `description` без отрицания | срабатывает на всё, конкурирует с соседями | добавить «НЕ использовать для…» |
| Мега-скилл на домен | грузится целиком, автовыбор деградирует | разделить по вопросам |
| Скилл-учебник | дублирует документацию, устаревает | оставить только проектные решения |
| Пути и имена, которых нет | агент делает неверные правки уверенно | сверять утверждения при каждой правке |
| Дубль глобального в репозитории | версии расходятся молча | одно каноническое место |
| Пустые каталоги и `TODO` | выглядит как готовое, работает как нет | не коммитить незавершённый каркас |
| Нет границ с соседями | агент выбирает случайно | назвать границу в тексте обоих |
| Инварианты без цены | их не соблюдают | либо цена, либо в рекомендации |

## Проверка сценариями

Минимум три:

1. **Должен активироваться** — запрос словами пользователя, не терминами скилла.
2. **Не должен активироваться** — близкий по теме запрос, относящийся к соседу или к
   обычной разработке.
3. **Полезность** — пройти по инструкции на реальном участке репозитория и убедиться, что
   шаги выполнимы, пути существуют, команды работают.

Проверка №2 важнее №1: ложное срабатывание вредит сильнее, чем несрабатывание, — оно
подменяет правильный скилл неправильным.

## Чеклист готовности

- [ ] `name` совпадает с именем каталога; `description` различающее и с отрицанием.
- [ ] Есть разделы «когда применять» и «когда НЕ применять».
- [ ] Инварианты с ценой нарушения, 3–10 штук.
- [ ] Каждый шаг процедуры ведёт в reference за деталями.
- [ ] Все ссылки на `references/*` существуют.
- [ ] Нет `TODO`, заглушек, пустых разделов и пустых каталогов.
- [ ] `assets/` содержат только копируемое; `scripts/` — только оправданное и проверенное.
- [ ] Утверждения о путях, именах и командах сверены с репозиторием.
- [ ] Пройдены три сценария проверки.
- [ ] Границы с соседями названы в тексте обоих скиллов.
