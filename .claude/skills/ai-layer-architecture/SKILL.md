# Архитектура AI-слоя

Цель слоя: **модель, провайдер, фреймворк и промпт меняются без правки бизнес-кода**.
Всё остальное — следствия. Если смена провайдера требует правки кода в бизнес-модуле —
слой спроектирован неверно, независимо от того, насколько красив код.

## Когда применять

- Появляется первая или очередная AI-функция в продукте.
- Нужно решить: «звать SDK напрямую или строить слой».
- Ревью AI-кода: «почему это не масштабируется».
- Перевод прототипа (прямые вызовы SDK) в продуктовый контур.

## Когда НЕ применять

- Разовый скрипт/эксперимент без продакшена — слой не нужен, нужен один файл.
- Вопрос про качество ответов, метрики, лимиты, алерты → `ai-evals-ops`.
- Вопрос про границы микросервисов, tenant-изоляцию, Temporal → `platform-architecture`.

## Инварианты (нарушение = ошибка ревью)

1. **Бизнес-код знает только логический алиас модели** (`task-default`, `task-fast`).
   Физический ID (`openrouter/google/gemini-3.7-flash`) и слаг провайдера в бизнес-коде,
   в реестре моделей и в БД — запрещены. Физический ID появляется только в конфиге шлюза
   и постфактум в журнале как наблюдаемость.
2. **Ни один вызов LLM не идёт мимо шлюза** — включая эмбеддинги, реранкеры и «быстрый
   вызов для одной проверки». Прямой импорт provider-SDK вне модуля шлюза запрещён.
3. **Фреймворк агента не виден доменному коду.** Домен работает с фасадом рантайма
   (`ToolDescriptor`, `runStructuredAgent`); импорт `@mastra/*`, `langchain`, `openai`
   вне фасада запрещён.
4. **Агент не читает бизнес-БД напрямую.** Любые данные — через governed-инструмент
   с authz и аудитом.
5. **Промпт — версионированная запись, а не строка в коде.** Ровно одна активная версия
   на (tenant, key), версии иммутабельны, обновление = новая версия.
6. **У каждой AI-задачи есть idempotencyKey и запись в журнале** — создаётся ДО вызова
   модели (`running`) и закрывается после (`completed`/`failed`/`needs_review`).
7. **Выход всегда структурирован схемой + нормализован.** Свободный текст модели не
   попадает в бизнес-путь; enum'ы нормализуются в коде — schema не гарантирует словарь.
8. **Модель не принимает необратимых решений.** Она отдаёт суждение + `reasons[]`; итог
   (статус, отправка, списание) считает детерминированный код.
9. **Недоверенный текст обрамляется как данные**, не как инструкции.
10. **Стоимость и физическая модель фиксируются из ответа шлюза**, а не угадываются по
    алиасу и не считаются самостоятельно по токенам.

## Порядок реализации

Строго по шагам; каждый следующий опирается на предыдущий.

1. **Определить задачу как контракт**: `taskType`, вход, схема выхода, что считается
   успехом. Без схемы выхода не начинать — она определяет всё остальное.
2. **Решить, нужна ли модель вообще.** Детерминированное правило дешевле, стабильнее и
   объяснимее. Модель — там, где правил не хватило, и она *добирает*, а не решает первой.
3. **Поднять шлюз** и завести логические алиасы по ролям: `default`, `fast`, `fallback`
   (другая provider-семья!), `batch`. → `assets/litellm-config.yaml`.
4. **Завести реестр в БД**: модели-алиасы, маршруты `useCase → alias` (tenant → platform →
   ошибка), промпты с версиями, журнал выполнений. → `references/runner-and-routing.md`.
5. **Написать фасад рантайма** — единственное место, где живёт фреймворк агента.
   → `assets/tool-facade/runtime-facade.ts`.
6. **Описать инструменты** как governed-контракты. → `references/tool-contracts.md`,
   `assets/tool-facade/governed-tool.ts`.
7. **Спроектировать сборку контекста**: что берём детерминированно, что отдаём агенту,
   нужен ли retrieval вообще. → `references/memory-and-context.md`, `references/rag.md`.
8. **Написать ОДИН общий runner** для всех задач. → `assets/runner/agent-task-runner.ts`.
   Порядок шагов внутри runner'а не произволен — см. `references/runner-and-routing.md`.
9. **Поставить фасад задач** `ExecuteTask(taskType, taskVersion, idempotencyKey, input,
   executionPolicy)` — один вход вместо N эндпоинтов.
10. **Подключить guardrails и журнал** → `ai-evals-ops`.
11. **Проверить платформенность вживую**: сменить маршрут одной строкой в БД/конфиге и
    убедиться, что физический upstream сменился, генерация продолжилась, код не менялся.
    Пока этот тест не пройден — абстракция не доказана.

## Правила assets

Файлы в `assets/` — **заготовки для копирования и адаптации**, не библиотека.

- Копировать в проект и править под его инфраструктуру (ORM, DI, логгер, названия
  таблиц). Не импортировать «как есть» и не тащить целиком, если нужна половина.
- Имена tenant-поля (`workspaceId`), таблиц (`ai_task_executions`) и алиасов —
  плейсхолдеры: переименовать под проект в момент копирования.
- `assets/runner/` — скелет общего runner'а и логики конфигурации.
- `assets/tool-facade/` — фасад рантайма и governed-инструмент.
- `assets/litellm-config.yaml` — конфиг шлюза с ролями алиасов и каскадом fallback.

Проверка инвариантов слоя — `platform-architecture/scripts/check-invariants.mjs`.

## Чеклист (перед «готово»)

- [ ] `grep` по бизнес-коду не находит физических model ID и слагов провайдеров.
- [ ] Импорт provider-SDK и фреймворка агента есть только в фасаде/шлюзе.
- [ ] Смена маршрута одной строкой доказана живым прогоном (физический upstream сменился).
- [ ] У задачи есть схема выхода, нормализация enum'ов и `reasons[]` там, где решает код.
- [ ] Повтор с тем же `idempotencyKey` не вызывает модель второй раз.
- [ ] Журнал содержит: alias, физическую модель, provider, токены, стоимость, латентность,
      версию промпта, версии контекста, статус.
- [ ] Агент не имеет пути к бизнес-БД в обход governed-инструмента.
- [ ] Fallback настроен на **другую** provider-семью, а не на соседнюю модель того же вендора.
