# Общий runner, маршрутизация и идемпотентность

Один runner на все AI-задачи. Каждая задача — набор параметров к нему, а не собственный
поток исполнения. Как только появляется вторая реализация «того же, но чуть иначе»,
расходятся идемпотентность, журнал, обработка ошибок и бюджет.

## Порядок шагов внутри runner'а

Порядок **не произволен**. Каждая перестановка ниже уже приводила к реальному дефекту.

```
1  валидация границ входа           → 400, до любых трат
2  idempotency lookup                → completed? вернуть сохранённый результат, БЕЗ вызова
3  budget gate                       → 402, ПОСЛЕ идемпотентности
4  resolve alias + active prompt     → ошибка, если use case не зарегистрирован
5  journal: create/upsert status=running
6  gather context (governed tools)   → детерминированно, до LLM
7  build input: base + context + knowledge + framed untrusted
8  assert input size
9  LLM call (timeout, maxSteps, maxOutputTokens)
10 postProcess + нормализация enum'ов
11 output guardrails (secret scan, запреты)
12 journal: status=completed + вся телеметрия
13 внешняя трассировка (best-effort, ошибки не роняют задачу)
```

**Почему 2 перед 3.** Повтор с тем же ключом денег не тратит. Если бюджет проверить
раньше, исчерпанный лимит начнёт отклонять уже оплаченные и завершённые задачи — клиент
не сможет забрать свой же результат.

**Почему 3 перед 5.** Отказ по бюджету — не выполнение. Создавать `running`-запись под
задачу, которая не начнётся, значит засорять журнал и ломать метрику success rate.

**Почему 6 перед 9.** См. «Детерминированный сбор vs tool-loop» ниже.

**Почему 11 после 10.** Скан утечек идёт по **финальным** строкам, которые уйдут наружу,
а не по сырому объекту модели.

**Почему 12 в обеих ветках.** В `catch` тоже пишем журнал (`failed` / `needs_review`),
иначе провалы невидимы, и success rate считается по выжившим.

## Идемпотентность

Ключ формирует **вызывающий** (оркестратор/UI), не runner. Runner подставляет случайный
UUID только если ключ не пришёл — и это осознанная деградация, а не норма.

```ts
const existing = await journal.findUnique({ where: { idempotencyKey } });
if (existing?.status === 'completed' && existing.storedResult) {
  return toResponse(existing, existing.storedResult, /* reused */ true);
}
```

Правила:

- Ключ детерминирован по бизнес-смыслу: `${taskType}:${entityId}:${attemptScope}` —
  чтобы повтор одного и того же намерения совпал, а новое намерение — нет.
- `reused: true` возвращается наружу: вызывающий должен отличать свежий результат от
  повтора (это влияет на метрики и на UI «сгенерировать заново»).
- Незавершённые (`running`) записи **не** считаются попаданием: параллельный дубль лучше
  один раз пересчитать, чем вернуть пустоту. Если параллелизм критичен — брать advisory
  lock по ключу, а не полагаться на статус.
- Сохранённый результат хранится рядом с записью выполнения (JSON-колонка). Без него
  идемпотентность вырождается в «мы помним, что это было» без возможности отдать ответ.

## Резолв конфигурации

```
resolveModelAlias(useCase, workspaceId)
  → tenant policy (workspaceId, useCase, isActive) 
  → platform policy (workspaceId=null, useCase, isActive)
  → UnknownUseCaseError

resolveActivePrompt(key, workspaceId)  // симметрично
  → tenant active → platform active → PromptNotFoundError
```

Обе цепочки **симметричны** намеренно: разная логика fallback для модели и промпта даёт
комбинации, которые никто не тестировал (тенантный промпт + платформенная модель).

Алиас дополнительно проверяется на существование и `isEnabled` **до** вызова — иначе
ошибка всплывёт как невнятный 400 от шлюза.

## Телеметрия вызова (перехват заголовков)

Шлюз возвращает в теле **алиас**. Физическая модель, стоимость и call-id — в заголовках.
Перехватывать их надо в кастомном `fetch` провайдера, а результат класть в
**AsyncLocalStorage**, а не в переменную модуля:

```ts
const callTelemetry = new AsyncLocalStorage<CallTelemetry>();

fetch: async (input, init) => {
  const res = await fetch(input, init);
  const slot = callTelemetry.getStore();
  if (slot) {
    slot.physicalModel = res.headers.get('x-litellm-model-name') ?? undefined;
    slot.costUsd = Number(res.headers.get('x-litellm-response-cost')) || undefined;
    slot.callId = res.headers.get('x-litellm-call-id') ?? undefined;
  }
  return res;
}
```

**Почему не переменная модуля.** Вызовы идут параллельно; глобальная переменная припишет
модель и стоимость одного запроса другому. Это не гипотетический риск — под нагрузкой
это происходит на первой же паре одновременных задач, и журнал начинает врать тихо.

Стоимость от шлюза **приоритетнее** разбора `usage`: она авторитетна, учитывает fallback
и не зависит от формы ответа конкретного провайдера.

## Детерминированный сбор контекста vs agent tool-loop

Два режима, выбор осознанный:

| | Детерминированный сбор | Agent tool-loop |
|---|---|---|
| Когда | данные нужны **всегда** и известно какие | набор данных зависит от рассуждения |
| Надёжность | высокая: вызов гарантирован | модель может не позвать инструмент или зациклиться |
| Стоимость | 1 LLM-вызов | N вызовов (шаги) |
| Governance | сохранён: тот же governed-путь | сохранён |
| Реализация | `gatherContext()` до LLM, агент **без** tools | `tools` передаются агенту |

Правило: если `gatherContext` задан — вызывать агента **без** tools. Смешение даёт
худшее из обоих: модель повторно зовёт инструмент, данные которого уже в контексте.

Reasoning-модели особенно склонны зацикливать tool-loop при строгом structured output —
для таких задач детерминированный сбор надёжнее по факту, а не по вкусу.

## Нормализация выхода

Схема (`json_object` / structured output) **не гарантирует попадание в словарь**: модель
вернёт `"e-mail"` вместо `"email"`, `"WhatsApp"` вместо `"whatsapp"`, придумает
отсутствующее значение enum.

```ts
function normalizeChannel(raw: string | undefined, preferred?: string): Channel {
  const v = (raw ?? '').toLowerCase().replace(/[^a-z]/g, '');
  const hit = CHANNELS.find((c) => c === v || ALIASES[c]?.includes(v));
  return hit ?? preferred ?? 'email';   // детерминированный дефолт, не бросок
}
```

Правила: нормализовать в коде, а не «уточнять промптом»; иметь детерминированный дефолт;
факт нормализации логировать — систематическое расхождение означает, что промпт или
маршрут выбраны неверно.

## Схема выхода: две схемы, не одна

- `LlmXSchema` — **толерантная** схема того, что реально присылает модель (опциональные
  поля, свободные строки вместо enum).
- `XOutput` — **строгий** доменный тип после `normalizeX()`.

Если склеить их в одну строгую схему, любая мелкая вольность модели превращается в
`no object generated` и полный провал задачи вместо нормализации одного поля.

## Обработка ошибок как контракт

Наружу — контролируемые ошибки без стектрейсов и секретов. Классификация по причине,
потому что реакция клиента разная:

| Причина | Код | Что делает клиент |
|---|---|---|
| Бюджет исчерпан | **402** + `spentUsd/limitUsd/period` | пополнить лимит, не ретраить |
| Guardrail входа | 400 | починить запрос |
| Guardrail выхода | 502 + статус `needs_review` | ручная проверка, не показывать пользователю |
| Таймаут агента | 502 | ретрай уместен |
| Невалидный structured output | 502 | ретрай/смена маршрута |
| Tool denied политикой | 400 | не ретраить, чинить права |
| Шлюз недоступен | 502 | ретрай с backoff |

Сваливать всё в 500 — значит лишить оркестратор возможности принимать решение о повторе.
Именно поэтому доменные ошибки бюджета/guardrail'ов **обязаны** проходить через маппер;
брошенные напрямую, они превращаются в 500 и неотличимы от сбоя.

## Фасад задач

```ts
interface ExecuteTaskRequest {
  taskType: AiTaskType;
  taskVersion?: number;          // отсутствует = 1; чужая версия → явный отказ
  idempotencyKey?: string;
  correlationId?: string;
  input: Record<string, unknown>;
  executionPolicy?: { maxCostUsd?: number; maxLatencyMs?: number };
}
```

- Неизвестный `taskType` и неподдержанная `taskVersion` — **явный отказ**, не молчаливое
  исполнение по другой версии контракта.
- `executionPolicy.maxCostUsd` проверяется **постфактум** (до вызова стоимость неизвестна):
  не откатываем — деньги потрачены, — но громко логируем. Дорогая задача не должна
  раствориться в общей сумме и всплыть только в счёте.
- Фасад не имеет своего состояния и своих ретраев.

## Проверка платформенности (обязательный приёмочный тест)

1. Зафиксировать физический upstream текущего маршрута (из журнала).
2. Изменить **одну строку** в маршрутной политике (`useCase → другой alias`).
3. Повторить ту же задачу.
4. Убедиться: физический upstream в журнале сменился, результат валиден, **код не менялся**.

Пока этот тест не пройден вживую, слой абстракции существует только в намерениях.
