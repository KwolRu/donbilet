# Контракты инструментов агента

Инструмент агента — это **не** удобная обёртка над репозиторием. Это внешняя граница
доверия: за ней LLM, поведение которой определяется в том числе текстом, пришедшим извне.

## Обязательный путь вызова

```
Агент → фасад рантайма (ToolDescriptor.execute)
      → tool-эндпоинт (MCP/HTTP, service-to-service аутентификация)
      → policy decision point (allow/deny + reason, fail-CLOSED)
      → владелец данных (сервис домена, свой ORM, tenant-фильтр)
      → safe-проекция → валидация схемой → агент
```

Ни один шаг не пропускается «потому что это read-only». Read-only утечка персональных
данных — такой же инцидент, как запись.

## Анатомия инструмента

```ts
export function buildOrganizationTool(ctx: ToolCtx): ToolDescriptor {
  return {
    id: 'get_organization',
    description: 'Безопасная карточка организации по id (название, город, категория, ' +
                 'статус сайта, типы доступных каналов). Контактные значения НЕ возвращаются.',
    inputSchema: GetOrganizationInputSchema,          // zod, строгий (uuid и т.п.)
    execute: async (args) => {
      const parsed = inputSchema.safeParse(args);      // 1) валидация ВХОДА
      if (!parsed.success) throw new ToolAccessError('malformed tool args');
      const raw = await invokeGovernedTool('get_organization', parsed.data, ctx);
      const out = OutputSchema.safeParse(raw);         // 2) валидация ВЫХОДА
      if (!out.success) throw new ToolAccessError('tool вернул некорректный результат');
      return out.data;
    },
  };
}
```

**Валидация с обеих сторон обязательна.** Вход — потому что аргументы придумала модель.
Выход — потому что контракт удалённого сервиса мог измениться, и лучше узнать об этом
здесь, чем увидеть галлюцинацию, построенную на мусоре.

## Правила описания (`description`)

`description` — часть промпта, а не документация. Оно определяет, позовёт ли модель
инструмент и с какими аргументами.

- Написать, что инструмент возвращает **и чего не возвращает** («контактные значения не
  возвращаются» — снимает попытки достать их через инструмент).
- Не описывать реализацию («идёт в таблицу organizations») — только смысл.
- Один инструмент — одно намерение. `get_data(type, filters)` с 8 режимами модель будет
  вызывать неправильно; три узких инструмента работают лучше.
- Имя — глагол + сущность: `get_organization`, `search_reviews`, `send_email`.

## Safe-проекция

Инструмент возвращает **проекцию**, а не сущность:

| Отдавать | Не отдавать никогда |
|---|---|
| факт наличия канала, его тип и достижимость | сам номер/адрес/логин |
| агрегаты отзывов, тексты без авторов | ФИО, id пользователей, персональные данные |
| статусы, категории, флаги | внутренние ключи, токены, служебные поля |
| «есть N документов» | сами документы, если задача их не требует |

Правило: **модель получает ровно то, что нужно для формулировки суждения**. Отправку по
каналу выполняет детерминированный код, у которого есть настоящий адрес.

## Разделение read / write

- **Read-инструменты** — норма для агента.
- **Write / необратимые действия** (отправка, списание, изменение статуса) — по умолчанию
  **не даются агенту**. Агент готовит *предложение*, а исполняет детерминированный код
  после проверки политикой и (при необходимости) подтверждения человеком.
- Если write-инструмент всё же нужен: обязателен идемпотентный ключ в аргументах, запись в
  аудит до и после, отдельное правило политики и лимит частоты.

## Ошибки инструмента

Классифицировать, а не сваливать в одну:

| Класс | Что означает | Реакция агента/runner'а |
|---|---|---|
| `denied` | политика запретила | не ретраить, наружу 400 «отклонено политикой» |
| `not_found` | сущности нет | вернуть модели факт отсутствия, не падать |
| `bad_args` | модель придумала аргументы | не ретраить бесконечно, считать шагом |
| `unavailable` | сервис/сеть | ретрай с backoff, затем деградация |
| `schema_mismatch` | контракт разошёлся | падать громко — это дефект, а не ситуация |

Текст ошибки, который видит модель, не должен содержать внутренних деталей (имена таблиц,
хосты, стектрейсы) — модель может процитировать его в ответе пользователю.

## Schema pinning

Схема инструмента фиксируется хэшем (`schemaHash`), который проверяется при вызове.
Несовместимое изменение внешнего API или соседнего сервиса ловится **на границе**, а не
через неделю в виде странных результатов.

При расхождении: остановить вызовы этого инструмента, а не «продолжить как получится».

## Таймауты и лимиты

```ts
maxToolSteps: 3        // шагов агента: хватает на вызов + финализацию
toolTimeoutMs: 8_000   // на один вызов инструмента
```

- Лимит шагов — защита от tool-loop, а не оптимизация. Reasoning-модели зацикливаются при
  строгом structured output систематически.
- Таймаут инструмента строго меньше таймаута задачи, иначе задача умрёт раньше, чем
  инструмент вернёт понятную ошибку.

## Service-to-service аутентификация

Tool-эндпоинт вызывается сервисом, а не пользователем: отдельный секрет, сравнение
constant-time, fail-closed при отсутствии конфигурации.

```ts
const a = createHash('sha256').update(received).digest();
const b = createHash('sha256').update(expected).digest();
if (!timingSafeEqual(a, b)) throw new UnauthorizedException();
```

Tenant передаётся **в теле от доверенного вызывающего** (сервис уже проверил контекст) —
но сам tool-эндпоинт обязан проверить, что запрошенная сущность принадлежит этому tenant'у.
Доверие вызывающему сервису не отменяет проверку владения данными.

## Чеклист инструмента

- [ ] Схемы входа и выхода валидируются обе.
- [ ] `description` объясняет смысл и явно называет, чего инструмент не отдаёт.
- [ ] Возвращается проекция без персональных данных и внутренних ключей.
- [ ] Решение политики запрашивается на каждый вызов, fail-closed.
- [ ] Каждый вызов попадает в аудит (кто, что, хэш аргументов, статус).
- [ ] Ошибки классифицированы; тексты безопасны для показа.
- [ ] Есть таймаут и лимит шагов.
- [ ] Write-инструменты либо отсутствуют, либо идемпотентны и подтверждаемы.
