# Модель слоёв AI-контура (L0–L9)

Слой определяется не файлом и не сервисом, а **ответственностью и границей**. Признак
корректной границы: соседний слой можно заменить, не трогая этот.

```
        ┌─────────────────────────────────────────────────────────┐
  L8    │  Оркестрация (workflow/activity, очереди, cron)         │
        └───────────────────────┬─────────────────────────────────┘
                                │ ExecuteTask(taskType, idempotencyKey, …)
        ┌───────────────────────▼─────────────────────────────────┐
  L7    │  Фасад задач  →  ОБЩИЙ RUNNER (idempotency, бюджет,     │
        │  resolve, журнал, guardrails, нормализация)             │
        └───┬──────────────┬──────────────┬───────────────┬───────┘
            │              │              │               │
    ┌───────▼──────┐ ┌─────▼──────┐ ┌─────▼───────┐ ┌─────▼──────┐
 L2 │ Маршрутизация│ │ L3 Промпты │ │ L6 Контекст │ │ L4 Runtime │
    │ useCase→alias│ │  (версии)  │ │  + знания   │ │  (фасад)   │
    └───────┬──────┘ └────────────┘ └─────┬───────┘ └─────┬──────┘
            │                             │               │
            │                    ┌────────▼────────┐ ┌────▼─────────┐
            │                 L5 │ Governed tools  │ │ L1 Шлюз      │
            │                    │ (MCP + authz)   │ │ моделей      │
            │                    └────────┬────────┘ └────┬─────────┘
            │                             │               │
  L0 ───────┴─────────────────────────────┴───────────────┴──────────  секреты/конфиг
  L9 ─────────────── наблюдаемость и экономика (сквозной) ────────────
```

---

## L0. Секреты и конфигурация (сквозной)

**Ответственность.** Единая точка получения ключей: секрет-хранилище с fallback на env в
dev. Реестр известных секретных значений — он же используется output-фильтром утечек.

**Не делает.** Не решает, какой провайдер выбран, и не знает про модели.

**Контракт.** `loadAiSecrets(): { gatewayBaseUrl, gatewayKey, … }` — async, кэширующая.

**Признак нарушения.** `process.env.OPENAI_API_KEY` в бизнес-модуле; ключ, попавший в
конфиг-файл под git; output-фильтр, читающий только `process.env` (после переезда ключей
в хранилище он молча перестаёт что-либо покрывать).

---

## L1. Шлюз моделей

**Ответственность.** Единый OpenAI-совместимый эндпоинт. Маршрутизация алиас → физическая
модель, retries на транзиентных ошибках, каскад fallback, cost tracking, ключи провайдеров.

**Не делает.** Не валидирует бизнес-ответы, не применяет запреты, не знает о tenant'ах.

**Контракт наружу.** Только логические алиасы + роли:

| Роль | Назначение | Требования |
|---|---|---|
| `default` | интерактивные агентные задачи | tools + structured output, стабильность важнее пиковой силы |
| `fast` | высокочастотные лёгкие задачи, строгий JSON | дешёвая, предсказуемая на schema |
| `fallback`, `-2`, `-3` | деградация | **другие provider-семьи**, иначе общий сбой вендора кладёт всё |
| `batch` | асинхронные массовые прогоны, eval, обогащение | дешевле, латентность не важна |

**Признак нарушения.** Физический model ID в коде или в БД; вызов провайдера в обход
шлюза «только для эмбеддингов»; fallback внутри одной семьи моделей.

**Важно.** Тело ответа шлюза обычно содержит **алиас**, а не физическую модель. Физическая
модель и авторитетная стоимость приходят в **заголовках** — их надо перехватывать
(см. `runner-and-routing.md` → «Телеметрия вызова»). Без этого невозможно ни доказать смену
провайдера, ни отнести стоимость к конкретному upstream после fallback.

---

## L2. Реестр моделей и маршрутизация

**Ответственность.** Таблицы: `ai_providers` (проекция для UI), `ai_models` (алиас, роль,
`supportsTools`, `supportsStructuredOutput`, `isEnabled`), `ai_routing_policies`
(`workspaceId?`, `useCase`, `alias`, `isActive`).

Резолв строго: **tenant-override → платформенный дефолт → явная ошибка**. Молчаливый
дефолт «взять первую попавшуюся модель» запрещён — он маскирует незарегистрированный
use case.

**Не делает.** Не хранит физические ID (иначе смена модели = миграция БД), не хранит ключи.

**Контракт.** `resolveModelAlias(useCase, workspaceId?) → alias`, с проверкой, что алиас
существует и включён (сервисная проверка + FK в БД — обе, они ловят разные ошибки).

**Признак нарушения.** `if (useCase === 'x') model = 'gpt-…'` в коде; алиас, которого нет
в реестре, но который «работает», потому что шлюз его знает.

---

## L3. Реестр промптов

**Ответственность.** `prompt_templates(workspaceId?, key, version, status, content,
variablesSchema)`. Версии **иммутабельны**: правка = новая версия. Активация — транзакция
«снять текущую active → archived, поставить целевую → active».

Детерминированность гарантируется на уровне БД: частичный UNIQUE `(workspace_id, key)
WHERE status='active'`. Не полагаться на «мы всегда аккуратно активируем».

**Не делает.** Не рендерит бизнес-данные в промпт (это L6), не решает, какой моделью его
исполнять (это L2).

**Контракт.** `resolveActivePrompt(key, workspaceId?) → { key, version, content }` с той же
цепочкой tenant → platform → ошибка.

**Признак нарушения.** Промпт в TS-константе; правка `content` существующей версии;
отсутствие `promptVersion` в журнале (тогда регресс качества невозможно связать с релизом).

---

## L4. Runtime агента (за фасадом)

**Ответственность.** Единственное место, где живёт фреймворк агента: agent loop, tool
calling, structured output, парсинг результата, перехват телеметрии шлюза.

**Не делает.** Не знает бизнес-домена, не ходит в БД, не решает про промпты и маршруты.

**Контракт наружу** — два типа и одна функция:

```ts
interface ToolDescriptor { id; description; inputSchema; execute(args): Promise<unknown> }
interface StructuredAgentRun<T> { modelAlias; agentId; instructions; input; schema;
                                  tools?; maxSteps?; maxOutputTokens? }
runStructuredAgent<T>(run): Promise<{ object: T; usage; physicalModel; gatewayCallId;
                                      finishReason; toolCalls }>
```

Домен передаёт `ToolDescriptor` — обычные функции и zod-схемы. Всё, что специфично для
фреймворка (`createTool`, `new Agent`, ESM/CJS-мосты, форма результата), остаётся внутри.

**Почему это критично.** Фреймворки агентов — самый быстро устаревающий компонент стека.
Через фасад замена фреймворка = переписать один файл. Без фасада — переписать домен.

**Признак нарушения.** `import { Agent } from '@mastra/core'` в доменном сервисе;
доменный код, знающий про форму `res.steps[].toolCalls`.

---

## L5. Governed-инструменты

**Ответственность.** Доступ агента к данным и действиям — через контракт с authz, аудитом
и безопасной проекцией. См. `tool-contracts.md`.

**Не делает.** Не является «удобной обёрткой над репозиторием» — если инструмент просто
проксирует Prisma без политики и аудита, слой отсутствует.

**Признак нарушения.** Агент с прямым доступом к ORM; инструмент, возвращающий сырую
сущность со всеми полями (телефоны, email, персональные данные).

---

## L6. Контекст и знания

**Ответственность.** Собрать вход: данные предметной области (детерминированно или через
tool-loop), знания тенанта, недоверенный пользовательский текст в обрамлении, история
диалога. Зафиксировать версии всего, что попало в контекст.

**Не делает.** Не решает про модель и не пишет журнал.

См. `memory-and-context.md` и `rag.md`.

---

## L7. Фасад задач и общий runner

**Ответственность.** Один вход `ExecuteTask` + один runner, через который проходят ВСЕ
задачи. Именно здесь идемпотентность, бюджет, журнал, guardrails, нормализация.

**Ключевое правило.** Фасад — тонкий диспетчер: валидация типа, разбор `input`, вызов
существующего use case. Он **не дублирует** бизнес-логику и **не обходит** гейты. Как
только у фасада появляется своя ветка логики — появляется второй путь исполнения и второй
набор багов.

Второй вход (service-to-service для оркестратора) — это **другой транспорт к той же
задаче**, а не вторая реализация.

См. `runner-and-routing.md`.

---

## L8. Оркестрация (граница со `platform-architecture`)

**Ответственность.** Durable-выполнение многошаговых процессов; вызывает AI-задачу как
activity через служебный эндпоинт. Идемпотентный ключ формирует **вызывающий** — так
replay после падения воркера не порождает второй LLM-вызов.

**Не делает.** Не содержит промптов, не знает про модели.

Подробности — `platform-architecture/references/durable-orchestration.md`.

---

## L9. Наблюдаемость и экономика (сквозной)

**Ответственность.** Журнал выполнений (`ai_task_executions`) как источник правды по
стоимости и качеству; спаны трассировки; корреляция `correlationId` ↔ trace ↔ execution.

Минимальный набор полей журнала:

```
workspaceId, taskType, idempotencyKey, correlationId, status,
modelAlias, model (физическая!), provider,
promptKey, promptVersion, knowledgeVersions,
promptTokens, completionTokens, costUsd, latencyMs, attempts,
guardrailsPassed, result
```

**Признак нарушения.** В поле `model` пишется алиас (тогда после fallback невозможно
понять, кто ответил); стоимость считается по своей таблице цен вместо данных шлюза;
prompt/PII в атрибутах спанов.

Детали — `ai-evals-ops/references/observability.md`.

---

## Матрица «слой ↔ что ломается, если его нет»

| Нет слоя | Что произойдёт |
|---|---|
| L1 шлюз | смена провайдера = правка N модулей + релиз |
| L2 реестр | нельзя дать тенанту свою модель; маршрут захардкожен |
| L3 промпты | регресс качества невозможно связать с изменением; правка промпта = деплой |
| L4 фасад | обновление фреймворка агента ломает домен |
| L5 tools | агент — дыра в авторизации и приватности |
| L6 контекст | недетерминированность, prompt injection, «модель забыла запреты» |
| L7 runner | дубли вызовов, потерянные деньги, N разных обработок ошибок |
| L9 журнал | счёт в конце месяца без объяснения; невозможно доказать регресс |
