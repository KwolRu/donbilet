# Исходящие коммуникации

Отправка — **необратимое действие с внешними последствиями**: испорченная репутация домена,
жалоба на спам, заблокированный аккаунт, потерянный клиент. Проектировать её надо от
запретов, а не от «как отправить».

## Когда применять

- Подключение канала связи или провайдера.
- Первое касание, цепочка касаний, ответ на входящее.
- Разбор «почему сообщение не ушло» или «почему ушло дважды».
- Отписки, чёрные списки, жалобы.
- Лимиты, окна отправки, аварийная остановка.

## Когда НЕ применять

- Генерация текста сообщения → `ai-layer-architecture` (+ `ai-evals-ops` про запреты).
- Сбор контактов и их верификация → `data-ingestion`.
- Durable-цепочки как механизм → `platform-architecture`.

## Инварианты

1. **Единая точка отправки (choke point).** Все исходящие идут через один сервис-метод.
   Второй путь отправки = второй набор пропущенных проверок.
2. **Порядок гейтов фиксирован**: провайдер → секрет → согласие и подавление → политика
   (стоп/окно/лимит/дубль) → rate-limit → отправка → аудит. Перестановка ломает гарантии.
3. **Fail-closed.** Нет явного разрешения — не отправляем. Политика недоступна — не
   отправляем.
4. **Факты для политики подставляет сервер**, не вызывающий. Клиент, сообщающий «я сегодня
   отправил 3 письма», проверяет сам себя.
5. **Идемпотентность обязательна.** Ключ формирует вызывающий, детерминированно.
   Доставка «хотя бы один раз» без ключа = два письма клиенту.
6. **Отписка и чёрный список — навсегда.** Не «на 30 дней», не «до смены кампании».
7. **Канал выбирает сервер.** Клиент может предпочесть, но выбор проверяется по
   достижимости и согласию.
8. **Глобальный стоп проверяется в момент отправки**, а не при постановке в очередь —
   между ними проходит время, ради которого стоп и нужен.
9. **Каждая попытка попадает в аудит**, включая отклонённые: «почему не ушло» должно иметь
   машинный ответ.

## Порядок построения

1. **Определить, что считается согласием** в вашей модели и юрисдикции. Это решение
   продуктовое и юридическое, не техническое — но всё остальное зависит от него.
   → `references/consent-and-suppression.md`
2. **Контракт адаптера канала** с `capabilities()`. → `references/channel-adapters.md`
3. **Единая точка отправки** с фиксированным порядком гейтов. → `references/send-gate.md`
4. **Политика отправки** как код: стоп, окно, лимит, дубль, чёрный список.
5. **Приём ответов**: входящие, атрибуция к диалогу, остановка цепочки сигналом.
   → `references/inbound-and-replies.md`
6. **Наблюдаемость**: отправлено/отклонено/доставлено/ответы/жалобы с разбивкой причин.
7. **Приёмка**: живая отправка в каждый канал + доказанный отказ по каждому гейту.

## Правила assets

- `assets/channel-provider.ts` — контракт провайдера канала с `capabilities()`,
  классификацией ошибок и идемпотентностью. Копировать при подключении первого канала.
- `assets/outbound-delivery.ts` — единая точка отправки с порядком гейтов. Это тот файл,
  который определяет, будут ли гарантии соблюдены.

## Профиль текущего стека (LeadMap)

`channels-service` — владелец каналов: `outbound/providers/` (email, telegram, vk, fake),
`outbound/rate-limit/`, `outbound/secrets/` (Vault), `blacklist/`, `limits/`, `accounts/`,
`proxy/`. Единая точка — `OutboundDeliveryService`. Политика отправки — OPA
(`ai.outbound.send`), стоп-флаг — ключ в Redis. Отправку инициирует **только** activity
Temporal-воркера; AI-слой сюда не ходит — он лишь готовит текст.

Замены компонентов — `platform-architecture/references/stack-selection.md`.

## Чеклист

- [ ] Второй провайдер того же канала подключается без правок бизнес-логики.
- [ ] Все отправки физически проходят через один метод (проверено поиском по коду).
- [ ] Повтор с тем же `idempotencyKey` не создаёт второго сообщения.
- [ ] Отписка и чёрный список действуют мгновенно и навсегда.
- [ ] Глобальный стоп останавливает всё, включая уже поставленное в очередь.
- [ ] Рабочее окно корректно работает при переходе через полночь (типовой дефект).
- [ ] Причина отказа сохраняется и доступна в интерфейсе.
- [ ] Живая отправка проверена в каждом канале, а не только в `fake`.
