# Единая точка отправки и порядок гейтов

## Choke point

**Все** исходящие проходят через один метод одного сервиса. Не «по договорённости», а
физически: провайдеры не экспортируются наружу, инициировать отправку может только этот
сервис.

Второй путь отправки — это второй набор проверок, который однажды забудут обновить. Именно
так уходят сообщения в чёрный список: не потому, что список не работал, а потому, что мимо
него был проложен обход.

Проверяется поиском по коду: обращения к `provider.send` вне точки отправки — ноль.

## Порядок гейтов

```
1  провайдер известен            → нет реализации канала = отказ, не «попробуем как-нибудь»
2  секрет доступен               → fail-closed для реальных провайдеров
3  идемпотентность               → уже отправляли с этим ключом? вернуть прошлый результат
4  согласие и подавление         → чёрный список, отписка, жалоба, невалидный адрес
5  политика                      → стоп-флаг, рабочее окно, дневной лимит, защита от дублей
6  rate-limit                    → acquire → … → release в finally
7  отправка                      → provider.send
8  аудит                         → результат, класс ошибки, providerMessageId
```

Почему именно так:

- **3 перед 4 и 5.** Повтор уже отправленного не должен упираться в лимит: сообщение
  физически не отправляется, а вызывающий имеет право получить прежний результат.
- **4 перед 5.** Отписка — абсолютный запрет, он не зависит от расписания и лимитов.
  Проверять его после лимитов означает тратить квоту на заведомо запрещённое.
- **6 после 5.** Занимать слот лимитера ради сообщения, которое отклонит политика, — прямая
  потеря пропускной способности.
- **8 всегда**, включая отказы. «Почему не ушло» обязано иметь машинный ответ.

## Политика как код

Проверяемые правила выносятся в движок политик, а не в `if` по коду:

```
approved                — черновик не отправляется
blacklisted             — навсегда
unsubscribed            — навсегда
suppressed              — bounce, жалоба, блокировка
daily_limit_exceeded    — счётчик воркспейса/аккаунта
duplicate_recent        — то же содержимое тому же получателю недавно
workspace_stopped       — глобальный стоп
outside_working_hours   — рабочее окно в часовом поясе ПОЛУЧАТЕЛЯ
```

Все факты подставляет **сервер** из БД/кэша. Клиент их не сообщает — иначе политика
проверяет то, что ей сказали.

Решение содержит **причину** (`reason`, `rule`): без неё разбор «почему тишина» сводится к
чтению логов вручную.

Fail-closed: движок недоступен → отказ. Готовый шаблон политики с тестами —
`platform-architecture/assets/current-stack/policies/outbound_send.rego`.

### Рабочее окно — типовой дефект

Условие `hour >= start && hour < end` верно **только** для окна внутри суток. Настройка
«ночная пауза 00:00–06:00» даёт окно 6→0 (`start > end`), условие не выполняется никогда,
и правдоподобная пользовательская настройка **молча блокирует всю отправку**. Обнаруживается
через дни тишины.

Разбирать три случая: границы совпали (круглосуточно), окно внутри суток, окно через
полночь. И написать тест на каждый.

Час считается в часовом поясе **получателя**, иначе «не писать ночью» соблюдается по
времени дата-центра.

## Идемпотентность

```
idempotencyKey = `${workspaceId}:${leadId}:${touchNumber}`     // детерминированно
```

- Формирует **вызывающий** (workflow/оркестратор), а не сервис отправки: при повторе
  ключ обязан совпасть.
- Хранится вместе с результатом; TTL — не меньше максимального окна ретраев.
- Ответ содержит `reused: true`, чтобы вызывающий отличал повтор.
- Дедупликация на стороне провайдера (если он умеет) — дополнение, а не замена: не все
  умеют, и полагаться на это нельзя.

Случайный ключ на каждую попытку означает, что ретрай доставки = второе сообщение клиенту.

## Ретраи

| Класс ошибки | Ретрай |
|---|---|
| `rate_limit` | да, по `retryAfterMs` |
| `provider_failure`, `timeout` | да, экспоненциально, ограниченное число раз |
| `quota_or_auth` | нет — сменить аккаунт/ключ |
| `invalid_recipient`, `blocked_by_user` | **никогда** — в подавление |
| `content_rejected` | нет — в ревью |

Ретраи выполняет оркестратор (durable), а не цикл внутри метода отправки: цикл не переживёт
рестарт и не даст паузы в часы.

## Глобальный стоп

Аварийный рубильник воркспейса — отдельно от бюджетов и расписаний.

- Хранится там, где читается быстро (кэш) с зеркалом в БД.
- Проверяется **в момент отправки**, а не при постановке в очередь: между постановкой и
  исполнением проходит время, ради которого стоп и нужен.
- Останавливает **всё**, включая уже запланированное и находящееся в очереди.
- Включение и выключение — в аудит, с указанием актора.

## Лимиты

Три уровня, все нужны:

| Уровень | Защищает от |
|---|---|
| На аккаунт (в минуту) | блокировки провайдером |
| На воркспейс (в сутки) | репутационного ущерба и перерасхода |
| На получателя (частота касаний) | ощущения преследования |

Лимитер должен возвращать `retryAfterMs`, иначе вызывающий будет молотить в стену.
`acquire` и `release` — с `finally`: незакрытый слот при исключении навсегда съедает
пропускную способность.

## Наблюдаемость

```
attempted, sent, rejected(by_rule), failed(by_error_class), delivered, replied, complained
```

`rejected` без разбивки по правилам бесполезен: половина эксплуатации — это ответ на
вопрос «почему из 500 касаний ушло 40».

Алерты: доля отказов по одному правилу выше нормы; ноль отправок при непустой очереди
(тишина — тоже инцидент); рост `complained` и `blocked_by_user`.
