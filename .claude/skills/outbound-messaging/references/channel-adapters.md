# Адаптеры каналов

## Контракт

```ts
interface ChannelProvider {
  readonly channel: ChannelType;          // 'email' | 'telegram' | 'vk' | 'whatsapp' | 'sms'
  readonly provider: string;              // конкретная реализация: 'smtp' | 'sendgrid' | …

  capabilities(): ChannelCapabilities;
  send(cmd: SendCommand): Promise<SendResult>;
  health(): Promise<{ ok: boolean; reason?: string }>;
}
```

Бизнес-код знает **канал**, а не вендора. `sendViaSendgrid(...)` в доменном сервисе —
ошибка ревью: смена провайдера превращается в правку бизнес-логики, fallback невозможен,
экономика по провайдерам не считается.

## `capabilities()` — почему обязателен

Каналы различаются не количеством, а **правилами**:

```ts
interface ChannelCapabilities {
  maxLength: number;              // 4096 у telegram, ~100k у email
  supportsSubject: boolean;       // только email
  supportsAttachments: boolean;
  supportsHtml: boolean;
  /** Можно ли писать первым, или нужно, чтобы собеседник начал. */
  requiresInitiationByRecipient: boolean;
  /** Требуется ли явное согласие до первого касания. */
  requiresOptIn: boolean;
  /** Окно, в течение которого можно отвечать свободно (24 часа у ряда мессенджеров). */
  replyWindowHours?: number;
  ratePerMinute: number;
}
```

Без этого в бизнес-код просачивается «у телеграма нельзя писать первым», и абстракция
протекает обратно. С этим — правило проверяется единообразно для всех каналов.

Типовые различия, которые кусаются:

| Канал | Особенность |
|---|---|
| Email | репутация домена, SPF/DKIM/DMARC, жалобы на спам, bounce-обработка |
| Telegram | нельзя писать первым — нужен `/start` от пользователя; лимит длины |
| VK | ограничения на первое сообщение от сообщества, окно ответа |
| WhatsApp | шаблоны, одобряемые заранее; окно 24 часа для свободного текста |
| SMS | стоимость за сообщение, транслитерация, ограничение символов |

## Команда отправки и результат

```ts
interface SendCommand {
  channel: ChannelType;
  to: string;                    // адрес/идентификатор получателя
  body: string;
  subject?: string;
  /** Формирует ВЫЗЫВАЮЩИЙ, детерминированно. Провайдер дедуплицирует по нему. */
  idempotencyKey: string;
  workspaceId: string;
  correlationId?: string;
  /** Идентификатор аккаунта отправителя, если их несколько. */
  accountId?: string;
}

interface SendResult {
  status: 'sent' | 'rejected' | 'failed';
  providerMessageId?: string;
  errorClass?: ProviderErrorClass;
  retryAfterMs?: number;
  /** true = сообщение с этим ключом уже отправлялось, повтора не было. */
  reused?: boolean;
}
```

`providerMessageId` обязателен при успехе: без него невозможно связать доставку, ответ,
жалобу и отписку с исходным сообщением.

## Классификация ошибок

```ts
type ProviderErrorClass =
  | 'rate_limit'        // притормозить, вернуть retryAfterMs
  | 'quota_or_auth'     // ключ/аккаунт — пометить аккаунт degraded, не долбить
  | 'invalid_recipient' // адрес не существует → в suppression, НЕ ретраить
  | 'blocked_by_user'   // получатель заблокировал → в suppression НАВСЕГДА
  | 'content_rejected'  // провайдер счёл спамом → в ревью, не ретраить
  | 'provider_failure'  // 5xx → ретрай
  | 'timeout';
```

Разница между `invalid_recipient` и `provider_failure` принципиальна: первое нельзя
ретраить никогда (адрес не появится), второе нужно ретраить. Смешение даёт либо вечные
повторы в пустоту, либо потерю доставимых сообщений.

`blocked_by_user` и `invalid_recipient` **автоматически** пополняют список подавления —
это не «когда-нибудь почистим базу», а немедленное действие.

## Аккаунты отправителей

Один канал — несколько аккаунтов (несколько ящиков, ботов, сообществ):

- у каждого свои лимиты, свой health и своя репутация;
- выбор аккаунта — server-side, по загрузке и здоровью, не по желанию клиента;
- аккаунт с `quota_or_auth` выводится из ротации до вмешательства;
- «прогрев» нового аккаунта — постепенное повышение дневного лимита, а не сразу максимум.

## Секреты

Токены каналов — из хранилища, изолированно по домену: сервис каналов не должен видеть
ключи AI и наоборот. Для реальных провайдеров — **fail-closed**: нет секрета → отправка не
происходит. Для `fake`-провайдера секрет не нужен, и именно поэтому его нельзя случайно
получить вместо реального: выбор провайдера явный, а не «что сконфигурировано, то и
используем».

## Fake-провайдер

Отдельная реализация того же контракта для тестов и e2e. Правила:

- пишет «отправленное» в журнал/файл, чтобы прогон можно было проверить;
- включается **явным** конфигом окружения, никогда не по умолчанию в проде;
- e2e, прошедший только на `fake`, **не доказывает** работу канала. Живая отправка в
  каждый реальный канал — часть приёмки.

## Прокси и сеть

Часть каналов требует исходящих запросов с определённых адресов (гео-ограничения,
репутация IP). Диспетчер прокси — внутри слоя провайдеров, бизнес-код о нём не знает.
Отказ прокси классифицируется как `provider_failure`, а не как отказ получателя.
