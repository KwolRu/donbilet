# Схема БД и миграции

## Правило номер один

`backend/prisma/schema.prisma` **генерируется**. Правки в нём теряются при следующей
сборке — обычно у другого разработчика и обычно перед релизом. Менять только
`backend/prisma/schema-parts/*.prisma`.

## Куда класть модель

| Part | Домен |
|---|---|
| `00-base` | базовые сущности платформы, воркспейсы, пользователи |
| `05-platform` | платформенные справочники и настройки (не тенантные) |
| `10-catalog` | категории, ниши, справочники поиска |
| `20-organizations` | организации, контакты, сайты, отзывы |
| `30-collection` | источники, задания сбора, прогоны, статистика, evidence |
| `40-leads` | лиды, состояния, скоринг, очереди, касания |
| `50-inbox` | входящие, диалоги, сообщения |
| `60-channels` | аккаунты каналов, лимиты, чёрные списки, отписки |
| `70-ai` | модели, маршруты, промпты, журнал выполнений, знания |
| `90-billing` | планы, подписки, счётчики |

Крупный новый домен → отдельный part `NN-<domain>.prisma` с шагом нумерации, оставляющим
место (`80-…`). Нумерация задаёт порядок склейки: enum и модели, на которые ссылаются
другие, должны идти раньше.

## Обязательное для тенантной таблицы

```prisma
model LeadTask {
  id          String   @id @default(uuid())
  workspaceId String   @map("workspace_id")
  status      String
  createdAt   DateTime @default(now()) @map("created_at")
  updatedAt   DateTime @updatedAt @map("updated_at")

  @@index([workspaceId, status, createdAt(sort: Desc)])
  @@map("lead_tasks")
}
```

- `workspace_id` — **первым** полем составного индекса. Иначе планировщик читает все
  тенанты и фильтрует после; на объёме это разница в порядки.
- Уникальность — всегда в связке с тенантом: `@@unique([workspaceId, externalId])`, а не
  `@unique` по одному полю.
- `@@map`/`@map` — snake_case в БД, camelCase в клиенте: так во всём проекте.
- Платформенная (не тенантная) таблица — осознанное решение; отметить комментарием, иначе
  её примут за пропущенный `workspace_id`.

## Ограничения, которые Prisma не выражает

Частичные уникальные индексы, проверочные ограничения, GIN/GiST — добавлять SQL-миграцией
вручную. Пример из AI-слоя (гарантия «ровно одна активная версия промпта»):

```sql
CREATE UNIQUE INDEX prompt_templates_active_uniq
  ON prompt_templates (COALESCE(workspace_id, '00000000-0000-0000-0000-000000000000'), key)
  WHERE status = 'active';
```

Если правило важно, оно должно жить в БД, а не в дисциплине кода.

## Команды

```bash
cd backend
bun run db:schema:build      # пересобрать schema.prisma из частей
bun run db:generate          # build + prisma generate
bun run db:migrate           # build + migrate dev (создаёт миграцию)
bun run db:status            # что применено
bun run db:push              # без миграции — ТОЛЬКО для черновой локальной работы
bun run db:migrate:deploy    # прод
```

**В прод — только `db:migrate:deploy`.** `db:push` не оставляет истории: то, что применено
на dev, невозможно воспроизвести на стенде.

## Порядок изменения

1. Правка part-файла.
2. `bun run db:migrate` — Prisma соберёт схему и создаст миграцию.
3. Проверить сгенерированный SQL глазами. Особенно: `DROP`, изменение типа, `NOT NULL` без
   `DEFAULT` на непустой таблице.
4. Прогнать `bun run db:status` и тесты.

## Обратно совместимые изменения

Раскатка кода и миграции не атомарна — между ними живут обе версии.

| Хочется | Безопасная последовательность |
|---|---|
| Добавить обязательное поле | добавить nullable → заполнить → сделать `NOT NULL` отдельной миграцией |
| Переименовать поле | добавить новое → писать в оба → перенести чтение → удалить старое |
| Удалить поле | сначала убрать все обращения и выкатить, потом удалять из схемы |
| Сузить enum | сначала перестать писать старое значение, мигрировать данные, потом менять |

Одношаговое «переименуем и выкатим» ломает работающие поды на время раскатки.

## Сид

```bash
bun run db:seed:base    # workspace + владелец (нужны SEED_OWNER_EMAIL/PASSWORD)
bun run db:seed:dev     # base + демо-данные примера домена
```

Сид **идемпотентен**: повторный запуск ничего не дублирует. Новую справочную сущность
добавлять через `upsert` по стабильному ключу, а не `create`.

Синтетические данные помечаются (`dataOrigin`), чтобы их можно было отличить от реальных и
вычистить отдельной задачей. Смешение синтетики и реальных данных под одним
источником уже приводило к неверным выводам о качестве сбора.

## Ownership

Одна таблица — один сервис-писатель. Читать могут другие через API. Если в таблицу пишут
два сервиса, граница проведена неверно: либо это один сервис, либо нужен явный владелец и
API для второго.
